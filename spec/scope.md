# 範囲の規範 — 三つの領域と、凍る面

koyu v1.0.0-rc.1 / muro 1.0 現在。**この文書が「何を約束し、何を約束しないか」の規範である。**
文法は [language.md](language.md)、意味論は [semantics.md](semantics.md)、判定の台帳は [validation.md](validation.md)。

ここに書かれた線は、他のどの文書よりも強い。spec の別の頁とここが食い違ったら、**ここが正である**。

---

## 1. 三つの領域

koyu は三つの領域からなる。**求められる品質が違うので、分けてある。**

| 領域 | 場所 | 大きさ | 品質 | 版 |
|---|---|---|---|---|
| **core** | `src/core/` | 小さい | **きれいでなければならない** | **凍る** |
| **検証** | `src/validate/` | 大きくなる | 汚くてよい | 凍らない |
| **表現・ビルド** | `src/draw/` と [ugatsu](https://github.com/kensnzk/ugatsu) | 大きくなる | 汚くてよい | 凍らない |

**依存は一方向である。**検証も表現も core に依存し、core はどちらにも依存しない。core は自分だけで完結して動く。この一方向は文ではなく `test/domains.test.ts` が機械的に守る。

分けないと二つのことが同時に起きる — **汚さが core に染み出して凍り、core の慎重さが検証と表現の成長を止める。**分けることそのものが、検証と表現が汚くてよい条件である。凍らない領域の汚れはいつでも書き直せるので安い。凍る領域の汚れは永久に残る。

> **koyu は座標を作らない。ugatsu は意味を作らない。**

---

## 2. core が持つもの

原本の言語と、その意味論と、機械への口。

- **muro の文法と意味論** — 何が書けて、書いたものが何を意味するか
- **合成** — 層の強度順序、単一値の解決、集合の編集、出所 ([composition.md](composition.md))
- **同一性** — uid とパス、関係の同一性 ([§5](#5-同一性))
- **導出** — 書かれた構成から**一意な形**を作る規則と、その参照実装 ([§6](#6-導出の契約))
- **構造整合の診断** — `check` が返す `Diagnostic[]`
- **問い** — 面積・グラフ・経路・開口面積。**ただし合否を言わない** ([§4](#4-問いは合否を言わない))
- **機械形式** — 正準JSON ([canonical-json.md](canonical-json.md))

## 3. 保証の範囲 — 「検査が通った」の意味

**`koyu check` が緑であることの意味は、次のとおりに定義される。**

> **構造層と解釈層について、宣言された不変量が成り立つ。運搬層については何も言わない。建築としての妥当性については何も言わない。**

これは判定ではなく**読解の一部**であって、壊れた JSON を JSON パーサが弾くのと同じ層にある。

### 3.1 保証するもの

| 保証 | 診断 |
|---|---|
| パスと同一性の一意性 | UID01-04 / ZON02 / 合成時のパス重複エラー |
| 参照先の存在 | REF01 / アセット未定義 / polygon の対応ゾーン (SIT04) |
| レベルの定義 | LVL01 / VRT02 |
| 区画の重なり (平面) | GEO01 / GEO02 |
| 区画の重なり (断面) | HGT01 / HGT02 |
| 合成の解決が定まること | 合成エラー (`SourceError` — [composition.md](composition.md)) |
| **形を作るのに必要な情報の充足** | SUF01-04 |
| 関係の健全性 | BND01-06 / VRT01-06 |
| 導出の一意性 (開口・seg・線・柱・縦動線の形) | OPN01-08 / SEG01-08 / LIN01-03 / COL01-02 / RUN01-05 |
| 解釈される属性の値域 | ATT01-03 / DAY01 |
| 与件の健全性 | SIT01 / SIT02 |

**断面の重なり (HGT01/HGT02) が core にあるのは、それが平面の重なり (GEO01/GEO02) の断面版だからである。**下階の天井と上階の床が同じ z を占める状態は、二つの空間の領域が重なる状態と同じ種類の矛盾であり、そこからは一意な形が作れない。「階高・軒高・斜線」のような建築的な高さの判断は保証しない — それは検証の面である。

### 3.2 保証しないもの

**採光・面積率・容積率・外皮の連続・階段の登りやすさ・扉の設置可能性・避難・接道 — その他あらゆる建築的な妥当性。**そして**運搬層の属性の意味**。

これらは存在しないのではなく、**別の面にある**。[validation.md](validation.md) と `koyu validate` が持つ。

### 3.3 緑を根拠に「動く」と主張しない

`check` が緑でも建物が使えるとは限らない。接する空間の既定は壁なので ([ADR-0014](../docs/decisions/0014-default-boundaries.md))、扉を一枚も宣言しない二階建ては**緑のまま完全に密封される**。外皮も自動では生えない。動線は `doors`、判定は `validate` が別に答える。

## 4. 問いは合否を言わない

集計とグラフの問いは core が持つ。**ただし合否を言わない。**

| 問い | core が返すもの | 検証が言うこと |
|---|---|---|
| 採光 | 床面積と有効窓面積 (`daylightInputs`) | 1/7 を満たすか (`daylight.ratio`) |
| 敷地 | 敷地面積・接道長・建築面積・延べ面積・その商 (`siteReport`) | 2m の接道 (`site.frontage`)・はみ出し (`site.escape`) |
| 縦動線 | 段数・蹴上・踏面・勾配 (`verticalRuns`) | 窮屈さ (`stair.proportion`)・勾配 (`run.slope`) |
| 外皮 | 何にも面していない外周の線分 (`envelopeGaps`) | それが穴か (`envelope.gap`) |
| 動線 | 最少扉数の経路と通行可能性 (`doorsBetween` / `passable`) | 外部へ出られるか (`access.unreachable` ほか `access.*`) |
| 柱と開口 | 通り芯から立つ柱と線分上の開口 (`columnsFor` / `placeOpening`) | 重なっているか (`column.blocksdoor`) |

**閾値は建築の側にある。**1/7 も 2m も 240mm も、原本の構成が満たすべき不変量ではない。数を返すところまでが core で、数に線を引くのが検証である。

## 5. 同一性

**uid を持つのは空間と集約 (space / zone) だけである。そして必須ではない。**

- **uid が書かれた空間**は、その uid が正典である。パスが変わっても同じものである
- **書かれていない空間**は、パスで対応づく。改名すれば対応は切れる
- **関係 (boundary) の同一性は、両端の空間から導かれる。**関係に uid は書けない — 関係は必ず二つの空間の間にあるので、両端が定まれば関係も定まる。関係ごとに uid を書けば関係の数が空間の数を上回り、「一棟が機械の視野に入る」という目的を自分で削ることになる
- **開口と内包物 (柱) の同一性は、それを含む対象と、その中で一意な名から導かれる**

必須にしないのは、**保証の強さを書き手が選べるようにするため**である。時点をまたいで指す必要がある空間にだけ付ければよい。

> **同一性には責任を持ち、内容には持たない。**

### 5.1 uid を書ける対象は閉じている

`uid` を書けるのは `space` と `zone` だけであり、**この一覧は閉じている**。台帳 ([vocabulary.md](vocabulary.md)) に `uid` が載っているのはこの二つの要素だけで、他の要素に書けば ATT03 (台帳に無いキー)、`level` に書けば構文エラーになる。**黙って無視される経路は無い。**

`acme.uid:` のように名前空間を付ければ書けるが、それは運搬層である ([§7](#7-属性の三層)) — core は見ない。**「同一性を持たせた」ことにはならない。**

### 5.2 生成の規則と、衝突しないことの範囲

**uid はパスからもモデルの中身からも導出しない。**導出すれば改名でトークンが変わり、uid の意味 (改名を跨ぐ) が消える。機械が作るときは**乱数**である — 接頭辞 `u-` + Crockford base32 の16字、合わせて 80 ビット ([ADR-0039](../docs/decisions/0039-identity-generation.md))。

```
u-7f3k9m2qx4b8dhtv
```

**保証は二段である。**

| 相手 | 保証 |
|---|---|
| 合成済みのモデル | **衝突しない。**生成器が検査し、`check` の UID03 が証明する |
| まだ合成されていない層・他のリポジトリ | **確率でしか保証しない。**80ビットなので 100 万個でも衝突確率は 10⁻¹² を下回る。確実さが要るなら合成して `check` を通す |

**付与は明示の行為である。**書き手が書くか、`newUids` / MCP の `new_uids` を呼ぶまで、どのツールも uid を書かない。`write_layer` も書かない。

### 5.3 名は、一つのものを指していなければならない

「含む対象 + その中で一意な名」が同一性である以上、**一つの名が二つを指す状態は同一性の破れである** — 合成の集合編集 (`= window W1` / `- column C1`) がどちらを指すのか決まらない。これは検査され (UID04)、合成の側でも拒まれる。

**アセットから継いだ名は、同一性の主張ではない。**`asset W1 window … name:掃き出し窓` の `name` は型の名であり、同じ建具を一枚の壁に二枚並べるのは普通の設計である。主張は、その開口の行に書かれた名だけである。

## 6. 導出の契約

形を作らないことと、形を作れないことは違う。**この記述からは、一意な形が作れなければならない。**

担保は第一に構造による — 与件が座標を与え、関係が共有面という座を与え、実体はその座に乗る。**実体は座を持って生まれる。**加えて四つを定める。

1. **導出の規則は仕様が持つ。**実装ではない。規則が消費者ごとに違えば、同じ原本から違う建物が出る。それは原本ではない。規則は [derivation.md](derivation.md) が持つ (意味論の側からの記述は [semantics.md](semantics.md) §2-4)
2. **充足性を検査する。**形を作るのに必要な情報が揃っているかは構造の整合の一部である (SUF01-04)。**妥当性の判定ではなく、完全性の検査である**
3. **参照実装を持ち、検査で回す。**`derive(model): Form` が唯一の入口であり、**見た目を持たない** — 色も書体も線幅も注記文字列も返さない。`src/draw/` と ugatsu はこの `Form` を描くだけである ([derivation.md §7](derivation.md))
4. **一意性は機械が縛れる述語である。**「一意」は文としての約束ではなく、次の含意として書かれる ([ADR-0041](../docs/decisions/0041-derivation-uniqueness.md))

   ```
   toCanonical(a) === toCanonical(b)  ⟹  derive(a) ≡ derive(b)
   ```

   **形は正準形の関数である。**正準形は「同じ建物とは何か」の定義なので ([canonical-json.md](canonical-json.md))、正準形が捨てる情報 — 線の端点の書き順・境界の宣言順・行の並び — は形を変えてはならない。変えるなら、捨ててよいものを捨てていないか、捨ててはいけないものを捨てているかのどちらかである

**「同じ構成から複数の形が出る」ことは欠陥である。**複数あってよいのは**見た目**であって、形ではない。

## 7. 属性の三層

| 層 | 例 | core の態度 |
|---|---|---|
| **構造** | パス・型・区画・レベル・関係の相手・kind | **必ず見る。**壊れていれば読まない |
| **解釈** | `h` `w` `at` `daylight` `road` `site` `style` … | 台帳 ([vocabulary.md](vocabulary.md)) が値域を定義し、**見る** |
| **運搬** | `acme.sensor` `bems.temp` `survey.measured` … | **見ない。**名前空間つきで開いている |

**運搬層は名前空間 (ドット区切り) を持つ。**`acme.sensor:23` のように書く。名前空間を持たない未知のキーは**エラー (ATT03)** である — `heigh:2400` のような一字違いが黙って効かないことを防ぐためで、これが「見ていないこと」と「見て問題がないこと」を区別できる唯一の形である。

開いていることと信頼できることは、境界が宣言されていれば両立する。宣言が無ければ、**見ていないことと、見て問題がないことが区別できない。**その状態の「異常なし」は何も意味しない。**持てるが判定しないは正当な状態であり、それを明示することが自由の条件である。**

詳細は [vocabulary.md](vocabulary.md)。

## 8. 1.0.0 が凍結する八つの面

**1.0.0 は機能の完成ではない。壊さないと約束する面の確定である。**

| 面 | 約束の内容 |
|---|---|
| **muro 1.0 の文法と意味論** | この版で読めたものは、以後も同じ意味で読める |
| **合成の規則** | [composition.md](composition.md) の六つ。同じ入力からは常に同じ結果が出る |
| **同一性** | §5 の規則。uid が同じなら同じものである |
| **属性の三層と名前空間** | §7。運搬層は見ない、という約束を含む |
| **機械形式** | **形式版を名乗る** ([canonical-json.md](canonical-json.md))。同じ入力からは同じバイト列が出る — 照合順と正規化を規範が定める。合成の結果を持ち、形を持たない |
| **導出規則** | §6。仕様として明文であり、参照実装が API として提供される |
| **構造整合の診断** | コードと severity。緑の意味が §3 の定義と一致する |
| **公開 API と CLI** | 解析・合成・正準化・問い・導出。コマンド、引数、終了コード |

### 凍結の対象でないもの

**存在してよいが、凍結対象でないことが明示されている。**

- **形の生成と描画** — `svgPlan` / `svgAxo` / CLI の `plan` `axo` / MCP の `plan_svg`。CLI の**面** (サブコマンド名・引数・終了コード) は凍るが、**SVG の中身は凍らない**。描画は `Form` を描くだけなので、**変わってはならないのは SVG ではなく `Form` である** ([derivation.md §9](derivation.md))
- **建築的な判定** — [validation.md](validation.md) の規則群と `koyu validate` の出力。増える面である
- **MCP のツール群** — 追加的に増える面として扱う
- **外部形式との往復と取り込み**
- **人のための面** — エディタ支援・オーサリング。ugatsu が持つ
- **運搬層の属性の意味**

## 9. 版の数え方

版は二本である。

- **muro の版** — 言語と意味論と合成の規則。機械形式が持つ**意味**はこの版に従う (同じ意味論の別の綴りである)
- **koyu の版** — 実装。どの muro を実装するかを宣言する

**機械形式はこの二本のどちらでもない、綴りの版を持つ** — `format` キー ([canonical-json.md](canonical-json.md))。意味論は muro が持つが、同じ意味論を別のキーで綴り直すことはありうるので、綴りの版は別に数える。

ugatsu は独立に版を持ち、従う muro の版を宣言する。検証の面は版を持たず、追加的に増える。

**muro 1.0 と koyu 1.0.0 は同時に到達する。**言語の面が確定していないのに実装の面を凍結することはできず、その逆もない。

## 10. 持たないもの

- **原本における幾何** (例外は所与 — 敷地形状の `polygon`)
- **配置の仕組み** — 内包は座を与えない。柱と機器は「どの空間に含まれるか」だけを持ち、そこから形は作れない
- **建築的な判定を原本の契約に含めること**
- **実務解像度の追求。**カバー率は価値ではない — 足せば機械の視野から外れ、目的が壊れる
- **往復互換。**出口は作るが往復は作らない
