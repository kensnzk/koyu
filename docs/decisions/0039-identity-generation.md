# ADR-0039: 同一性の生成規則 — 乱数で作り、範囲を明示し、opt-in のまま凍らせる

日付: 2026-07-27 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [方針の総覧](../policy.md) §5.3・§19-4 / 関連: [ADR-0015](0015-identity-uid.md) (uid の導入)・[ADR-0035](0035-composition-rules.md) (`name:` が集合編集の鍵)・[ADR-0038](0038-version-1-0-rc.md) (rc が名指しで残した三つ)

## 文脈

1.0.0 が凍結する八つの面の三番目は**同一性**である ([spec/scope.md §8](../../spec/scope.md))。ADR-0015 が uid を予約語彙にし、UID01〜UID03 が形と一意性を守り、`koyu diff` が uid 一致・パス不一致を改名として報告するところまでは立っていた。だが方針 §19-4 は未決を一つ残していた — **「同一性の生成規則。書き戻すときに、何から作り、どこまで衝突しないことを保証するか」**。

**面が確定していないのに 1.0.0 を名乗ることはできない** ([ADR-0038](0038-version-1-0-rc.md))。凍らせるには、生成の規則と保証の範囲を書き下さなければならない。

実測すると、確定していないのは生成だけではなかった。

**第一に、uid を書ける対象は既に閉じていた。**`uid:` を `boundary` / `opening` / `seg` / `area` / `column` / `asset` に書けば ATT03 (台帳に無いキー)、`level` に書けば構文エラーになる — 台帳 ([ADR-0033](0033-attribute-tiers.md)) が `space` と `zone` にしか `uid` を持たないからである。**無音の経路は無かった。**書けるつもりで書いたものは必ず落ちる。閉じていることが実測で確かめられたので、あとは規範として書き下せばよい。

**第二に、開口と内包物の同一性は半分しか立っていなかった。**方針 §5.3 は「含む対象 + その中で一意な名から導かれる」と言い、ADR-0035 が `name:` を集合編集の鍵にした。だが**その一意性はどこも検査していなかった。**

| 書いたもの | 起きていたこと |
|---|---|
| 一つの境界に `name:W1` の窓を二枚 | `check` 緑。`= window W1` を書いた瞬間に「not unique」で落ちる |
| 一つの空間に `name:A` の `area` を二つ | `check` 緑 |
| `name:C1` の柱を二本書いて `drop column C1` | **二本とも黙って消えた** |

最後の一つは、`applyDrop` のコメントが自ら掲げる「**消えるのは、消すと書いたものだけである**」に反していた。

**第三に、`diff` は開口を位置で対応づけていた。**キーは `(kind, edge, at)` で、`name:` を読んでいなかった。名の付いた扉の `at:` を 0.3 から 0.7 へ動かすと、出力はこうなる。

```
± boundary /L1/a | /L1/b: + door at:0.7 w:780 h:2000 name:D1 / − door at:0.3 (w:780 h:2000 name:D1)
```

**「同じ扉が移動した」ではなく「消えて生えた」と報告していた。**同一性の規則が spec にあり、それを読まない実装が隣にあった。

## 決定

**1. uid を書ける対象は `space` と `zone` の二つで、一覧は閉じている。**台帳がその唯一の出所であり、他の要素に書けば ATT03 で落ちる。`acme.uid:` のように名前空間を付ければ書けるが、それは運搬層であって core は見ない — **「同一性を持たせた」ことにはならない**。この線を [spec/scope.md §5.1](../../spec/scope.md) に書き下し、台帳が動いたら落ちるテストで縛る。

**2. 生成は乱数である。**接頭辞 `u-` + Crockford base32 の小文字16字、合わせて18字・**80ビット**。

```
u-7f3k9m2qx4b8dhtv
```

三つの選択がある。**(a) パスから導出しない** — パスが変われば uid も変わり、uid の意味 (改名を跨ぐ) が消える。**(b) 接頭辞を持つ** — 数字だけの綴りを構造的に不可能にする (UID01 は、parse の数値化が `0123` を `123` にしてトークンの区別を失うために立っている)。**(c) 綴りから何も読めない** — 種別 (space / zone) を接頭辞に入れない。uid は不透明であり、綴りに意味を持たせれば、それを読む実装が生まれる。字母に `i` `l` `o` `u` が無いのは Crockford base32 の性質で、副産物として**接頭辞の `u` は本体に現れない** — 生成された uid の `u` は必ず先頭の一つだけである。

**3. 衝突しないことの保証は二段である。**これを明示することが、この決定の中身である。

| 相手 | 保証 |
|---|---|
| 合成済みのそのモデル | **衝突しない。**生成器が既存の uid を集めて避け、`check` の UID03 が証明する |
| まだ合成されていない層・他のリポジトリ・外部システム | **確率でしか保証しない。** |

80ビットの根拠。誕生日限界で、n 個の uid が一つでも衝突する確率はおよそ n²/2⁸¹ である。一棟が機械の視野に入るという目的の上限をはるかに越えた n = 10⁶ でも 10⁻¹² を下回り、n = 10⁹ でも 10⁻⁶ を下回る。**確実さが要るなら、合成して `check` を通すこと。**一意性を実際に証明するのは UID03 だけであり、生成器はそれを代行しない。

**4. 1.0 では opt-in のままとし、生成は明示の行為として提供する。**言語は uid を要求しない。`write_layer` も、他のどのツールも、自分から uid を書かない。付与したいときに呼ぶ入口を二つ置く — 公開 API の `newUids(model, count?)` と、MCP の `new_uids`。**方針の「必要になった時点でツールが生成して書き戻す」は、これで満たされる** — 「必要になった時点」を判断するのは書き手であって、ツールではない。ADR-0015 が「evalとコーパスが全付与を要求したらツールの一括付与に広げられる (逆は破壊的)」と残した道は、そのまま開いている。

**5. 名は、一つのものを指していなければならない。**`UID04` (error) を立てる。母集団は四つ — 境界の中の開口、境界の中の `seg`、空間の中の `area`、モデルの中の `column`。名を書かない要素は同一性を主張していないので、母集団に入らない。合成の側でも `drop column <名>` が曖昧なら拒む (`editList` が `+` `-` `=` に課していた規律に合わせる)。

**アセットから継いだ名は、同一性の主張ではない。**`asset W1 window … name:掃き出し窓` の `name` は**型の名**である。同じ建具を一枚の壁に二枚並べるのはごく普通の設計であり、型の名を主張として読めば、それが衝突になってしまう。主張は、その開口の行に書かれた名だけである (`openingIdentity`)。

**6. `diff` は開口と `seg` を、名があれば名で対応づける。**名が無ければ従来どおり位置で対応づける。名で対応づいた対では、キーから外れた項 (`kind` `edge` `at`、`seg` は `edge` `at` `w`) がフィールドの変化として出る。上の例はこうなる。

```
± boundary /L1/a | /L1/b: door D1 at 0.3 → 0.7
```

**言語の版は動かない。**UID04 も `drop column` の厳格化も検査の追加であり、ADR-0017 の帰結が定義した「意味保存 = 導出物 (canonical/graph/stats/SVG) の不変を指し、診断の増減は含まない」の内側にある。曖昧でない原本の導出物は 1 バイトも変わらない。

## 代替案

**パスのハッシュから作る**案は最初に落ちる。uid が存在する理由は「パスが変わっても同じものである」ことなので、パス由来の uid は rename 耐性がゼロになる — uid を持つ意味が消え、パスを二度書いているだけになる。**同一性を内容から導く形式はすべてこの罠にある。**幾何のハッシュも、属性のハッシュも同じである。

**連番 (`sp-1` `sp-2` …)** は読みやすいが、合成とファイル分担で衝突する。層ごとに独立に採番すれば `sp-1` が二つ生まれ、それを避けるには「どこまで使ったか」を持つ中央の台帳が要る。**ステートレスであること** (MCP の全ツールが毎回ゼロから合成する — [ADR-0012](0012-mcp-server.md)) を捨てることになる。層ごとの接頭辞で回避する案もあるが、接頭辞の割り当てを誰が管理するかという同じ問題に戻る。

**UUIDv4 (128ビット・ハイフン区切り36字)** は標準で、外部システムとの join には都合がよい。棄却したのは長さである — 原本は人が読んで書くテキストであり、36字のトークンが行末に並ぶのは重い。80ビットで保証は十分足り、18字は目で追える。**IFC の GUID (`guid:`) を取り込むときはその綴りをそのまま運ぶ**ので、外部の識別子を koyu の綴りへ変換する必要は最初から無い。

**時刻を混ぜる (ULID / UUIDv7)** 案は、生成順で整列できる利点がある。だが uid に生成時刻が読めることは、**不透明性の破れ**である — 「いつ作られたか」を uid から読む実装が生まれ、そこに依存が育つ。整列が要るなら別の属性で持つべきで、同一性のトークンに二つ目の役をさせない。

**全要素への自動付与** (ADR-0015 の代替案の再訪) は、rename 耐性が要らない利用者にも行の重さを課す。さらに、採番のランダム性が「同じ構成 → 同じバイト列」([ADR-0013](0013-canonical-form.md)) と衝突する — 同じ建物を二度書き起こせば違うバイト列が出てしまう。**opt-in なら、その衝突は書き手が uid を書いた瞬間にだけ起きる。**

**`write_layer` が uid を自動で補う**案は、方針の文面 (「必要になった時点でツールが生成して書き戻す」) に最も近い読み方である。棄却したのは、`write_layer` が**全置換で書き、取り消しを持たない**からである。書き手が意図していない属性を、取り消せない書き込みで原本に混ぜる。付与は明示の行為でなければならない。

**uid の綴りを検査する (生成した形以外を拒む)** 案は、opt-in と両立しない。人が `uid:sp-a` と書くことは正当であり、生成器の綴りは**規範ではなく既定**である。UID01/UID02 が守るのは形の下限 (数字だけでない・空白が無い) だけでよい。

**UID04 を warning にする**案。曖昧な名を抱えたまま `check` を通したい、という要求はありうる。だが `= window W1` は実際に落ちるので、緑のまま編集できない状態を緑と呼ぶことになる。**severity はコードの不変属性である** ([ADR-0016](0016-diagnostic-contract.md)) — 迷うなら error 側に置き、緩めたくなったら別のコードを切る。

**アセットの `name` を開口に継がせない**案 (parse で `delete attrs["name"]`) は、同一性の話としては最も素直である。棄却したのは、それが**正準JSONを変える**からである — tower と twin の開口から `name` が消え、ADR-0017 の「意味保存」の定義 (導出物の不変) を破る。言語版を上げなければならなくなり、rc が名指しで残した三つに「言語版をもう一度上げる」を足すことになる。継承はそのままにし、**同一性を主張する名だけを別に読む**ほうが、変える面が小さい。

**`over` の `findNamed` も主張する名だけを見る**案は、対称性としては正しい。だが `- window <アセットの名>` が現に動く場合 (そのアセットが境界の中で一枚しか使われていないとき) を壊す。曖昧なときは `editList` が既に「not unique」で拒むので、**参照の解決は実効の名で行い、同一性の主張は書かれた名で読む**という非対称を受け入れた。参照は「一つに絞れるか」を問い、主張は「一つを指しているか」を問う — 別の問いである。

## 帰結と代償

**同一性の面が凍らせられる状態になった。**書ける対象・生成の規則・保証の範囲・付与の主体・名の一意性 — 五つとも [spec/scope.md §5](../../spec/scope.md) に書き下され、テストが縛っている。方針 §19-4 は回収された。

**実測が二つの穴を塞いだ。**`drop column C1` が二本まとめて消すことは無くなり、`diff` は名の付いた扉の移動を移動として報告する。どちらも「spec に規則があり、それを読まない実装が隣にある」という形の欠陥だった。

**同梱例が曖昧を持っていたことが分かった。**tower と twin は `window W1` を一つの境界に二枚並べており、UID04 の最初の版はそれをエラーにした。**それが決定5の後半 (アセットの名は主張ではない) を要求した** — 検査を弱めたのではなく、何が主張かの定義が足りていなかった。

代償。**(1) 生成された uid は読めない。**`u-7f3k9m2qx4b8dhtv` は何も語らない。人が書くなら `sp-ldk-north` のような読める綴りのほうがよく、言語はそれを許している — 生成器が作る綴りは既定であって規範ではない。**(2) 「主張する名」と「参照が解決する名」がずれる。**アセットの名で `- window` を書くことは動くが、UID04 の母集団には入らない。この非対称は [spec/scope.md §5.3](../../spec/scope.md) に明記した。**(3) 層をまたぐ衝突は確率でしか保証しない。**これは避けられない — 合成していないものは見えない。書き下したのは保証ではなく、**保証の境界**である。

三点セットで着地した: 本 ADR (なぜ) + `test/identity.test.ts` (保証) + [spec/scope.md §5](../../spec/scope.md)・[spec/semantics.md](../../spec/semantics.md) の台帳・[spec/tools.md](../../spec/tools.md) (現在形)。
