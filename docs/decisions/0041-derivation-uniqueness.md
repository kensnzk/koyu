# ADR-0041: 形は正準形の関数である — 描かれた線が絡む四つの破れを閉じる

日付: 2026-07-28 / 状態: 採用 (v1.0.0-rc.1、言語版 muro 1.0) / 起点: [spec/scope.md §6](../../spec/scope.md) (導出の契約)・[ADR-0040](0040-derive-reference.md) 代償4 / 関連: [ADR-0022](0022-lines.md) (描かれた線)・[ADR-0029](0029-order-as-meaning.md) (順序と正準化)・[ADR-0036](0036-machine-format-version.md) (機械形式)・[ADR-0016](0016-diagnostic-contract.md) (診断契約)

## 文脈

[scope.md §6](../../spec/scope.md) は「**この記述からは、一意な形が作れなければならない**」と書き、§8 は「導出規則」を 1.0.0 が凍らせる八つの面の一つに数えている。だが「一意」は文としては書かれていても、**機械が縛れる述語としては書かれていなかった。**

[ADR-0040](0040-derive-reference.md) で規則を書き下したことが、規則の破れを見せた。`derive` は当時の振る舞いを忠実に写しただけなので、写した先に**同じ原本から二つの形が出る経路が四つ**あった。どれも `line` (描かれた線) が絡む。ADR-0040 の代償4 はこれを「この段では直していない」と名指しで残した。

四つとも実測してある。以下はすべて 7fc9738 (ADR-0040 の着地点) で走らせた出力である。

### 1. a/b の向きで、線が残す側が反転する

```
space /L1/room room X1..X2 Y1..Y2       # 3000 × 6000 = 18.00㎡
boundary /L1/room /out edge:W
  line X1,Y1+2000 X1+2000,Y1            # 西南の隅を斜めに落とす
```

| 書き方 | `/L1/room` の面積 |
|---|---|
| `boundary /L1/room /out` | **16.00㎡** |
| `boundary /out /L1/room` | **14.00㎡** |

隅を落とすつもりで書いた線が、**空間と外部のどちらを先に書いたかで、落とす隅を入れ替えていた。**`check` は両方とも緑である。

### 2. 線の端点の書き順が、開口の位置を決める

```
boundary /L1/a /L1/b
  line X1,Y1+2000 X2,Y1+4000
  door w:900 at:0.25 name:D1
```

| 書き方 | 正準JSON の sha256 (先頭16桁) | 扉の中心 |
|---|---|---|
| `line X1,Y1+2000 X2,Y1+4000` | `9497e24d5219e25d` | **(750, 2500)** |
| `line X2,Y1+4000 X1,Y1+2000` | `9497e24d5219e25d` | **(2250, 3500)** |

**正準JSONがバイト同一のまま、扉が別の位置に出る。**開口の `at:` は線分の始端からの比なので、始端が書き順で決まる限りこうなる。

**これが四つのうち最も重い。**正準形の存在理由は「同じ構成なら常に同じバイト列、違う構成なら必ず違うバイト列」であり ([canonical-json.md](../../spec/canonical-json.md))、正準JSON は端点の対を解決座標順に並べ替えることで書き順を**捨てている**。捨てた情報が形を変えるなら、正準形は「同じ建物とは何か」に答えられていない。

**捨てると決めたのは [ADR-0029](0029-order-as-meaning.md) 決定2 である。**そこにはこう書いてある — 「線分は向きを持たないので、どちらから書いても**導出される凸片は同一である** (実験で確かめた)」。凸片については正しい。だが**確かめたのは凸片までだった。**線の上に載る開口は凸片ではなく、`at:` は線分の始端からの比なので、そこは同一ではなかった。正準化の判断は正しく、**その判断が形の全体に届いていることを確かめていなかった。**

### 3. `line` を持つ境界の宣言順で、面積が変わる

```
boundary /L1/a /L1/b        boundary /L1/b /L1/c
  line X2,Y1 X3,Y2            line X3,Y1 X2,Y2     # 二本は互いに交差する
```

| 宣言順 | 正準JSON の sha256 | `/L1/a` | `/L1/b` | `/L1/c` |
|---|---|---|---|---|
| a\|b → b\|c | `93e986dd89d5db48` | **27.00㎡** | 4.50㎡ | **22.50㎡** |
| b\|c → a\|b | `93e986dd89d5db48` | **22.50㎡** | 4.50㎡ | **27.00㎡** |

ここでも正準JSONはバイト同一である。正準JSONは境界の並びを内容の正準順に並べ替えて宣言順を捨てているのに、**切り分けは宣言順に効いていた。**線の切り分けは冪等ではなく、先に効いた線が縮めた領域が後の線の窓を縮めるので ([derivation.md §1.1](../../spec/derivation.md))、順序がそのまま面積になる。

### 4. 実際に切った線に「何も切っていない」と言う

```
boundary /L1/a /L1/b
  line X1,Y1 X1,Y2            # これは分離しない線 (LIN01)
boundary /L1/a /out
  line X1,Y1+1500 X2,Y1+1500  # /L1/a を 18.00㎡ → 13.50㎡ に切る
```

```
error   LIN01 Line X1,Y1..X1,Y2 does not separate /L1/a and /L1/b …
warning LIN03 Line X1,Y1+1500..X2,Y1+1500 cuts nothing (it is the same as the default adjacency line, …)
```

**4.5㎡ を実際に落とした線が「何も切っていない」と報告される。**機構は母集団の食い違いである — 診断は `drawnCut` を**切った後の `pieces`** から呼び直して窓を組み立て、その窓に**切る前の `rects`** を当てていた。窓は縮み、当てる相手は縮んでいないので、straddle していないように見える。

(「判定と操作を同じ関数に通す」ことで一度この族は閉じたつもりだったが、閉じたのは*関数*の同一であって*母集団*の同一ではなかった。)

## 決定

**四つを一つの原理に畳む。形は正準形の関数である。**

```
toCanonical(a) === toCanonical(b)  ⟹  derive(a) ≡ derive(b)
```

正準形は「同じ建物とは何か」の定義である ([ADR-0036](0036-machine-format-version.md))。だから**正準形が捨てる情報は、形を変えてはならない。**変えるなら、捨ててよいものを捨てていないか、捨ててはいけないものを捨てているかの、どちらかである。四つはすべてこの一文の系である。

**1. 描かれた線は向きを持たない。**同じ二点を結ぶ線は、どちらの端から書いても同じ線である。`canonicalizeDrawn` が `parse` の出口で端点を**解決座標の (x, then y) 昇順**へ揃える — 正準JSON が既に使っている規則と同じものである。綴り (`aRef`/`bRef`) も一緒に入れ替えるので、診断が引用する綴りは書かれたとおりのまま入れ替わる。開口の `at:` の起点はこの正準の始端になる (§2 が閉じる)。

**2. 切り分けは正準の境界順に効く。**`derivePieces` は `canonicalBoundaryOrder(model)` を走る。並びの規則は `toCanonical` と同じ (`between` の辞書順、同じ `between` は直列化順) であり、**一つの関数を両者が共有する** — 別々に書けば、いつか片方だけが動く。切り分けが順序に依存すること自体は変えない ([ADR-0022](0022-lines.md) からの設計であり、冪等にするには別の規則が要る)。変えたのは**どの順序か**である (§3 が閉じる)。

**3. `a`/`b` の向きが効いてよいのは `edge` と `swing` だけである。**外皮を切る線が残す側は、**領域を持つ側そのもの**が決める。`drawnCut` は solo の場合に `sideA` を a/b の向きで符号反転させていたが、solo の側から見た符号をそのまま返す (§1 が閉じる)。

a/b の向きは正準JSONに `a` として残るので、これは §1 の含意の話ではない — **a/b が何に効くか**の話である。向きは「どちらの空間から見た関係か」を言うのであって、形を言うのではない。

**4. 帰結は、切るその場で記録する。**`DrawnLine.effect` (`"cut"` / `"nothing"` / `"undetermined"`) を `derivePieces` が書き、`checkDrawnLines` はそれを読むだけにする。**判定と操作が同じ関数を通ることに加えて、同じ母集団を見ることを構造で保証する** (§4 が閉じる)。診断のコードも severity も母集団 (書かれた宣言) も並び (走査の順) も変わらない ([ADR-0016](0016-diagnostic-contract.md) / [ADR-0028](0028-diagnostics-per-declaration.md))。

**5. `Form` の境界の索引は正準順である。**`derive` が境界を並べる順が変われば、`FormSeg.boundary` のような索引の指す先も変わる。`derive` と、`Form` を消費する側 (`src/draw/plan.ts`、ugatsu の `PlanView.tsx` と `three/buildScene.ts`) が同じ順を見るように、`canonicalBoundaryOrder` を**公開面に出す**。これが無いと、消費者は `model.boundaries[i]` (宣言順) を `Form` の索引に当ててしまう — 実際に三箇所がそうなっていた。

### 実測 — 直した後

同じ四つを現在のツリーで走らせた結果である。

| # | 直す前 | 直した後 |
|---|---|---|
| 1 | 16.00㎡ ↔ 14.00㎡ | **16.00㎡ ↔ 16.00㎡** |
| 2 | 扉 (750,2500) ↔ (2250,3500) | **(750,2500) ↔ (750,2500)** |
| 3 | `/L1/a` 27.00㎡ ↔ 22.50㎡ | **27.00㎡ ↔ 27.00㎡** |
| 4 | 4.5㎡ を落とした線に LIN03 | **LIN03 は出ない** (LIN01 はそのまま出る) |

## 代替案

**正準JSONの側を直す — 書き順と宣言順を捨てるのをやめる。**§2 と §3 は「正準形が捨てた情報が形を変える」ことなので、捨てなければ矛盾は消える。**棄却する。**そうすると `line X1,Y1 X2,Y2` と `line X2,Y2 X1,Y1` が別の建物になり、`boundary` を並べ替えただけの差分が「構成が変わった」と読まれる。正準形の値打ちは**綴りの違いを潰すこと**にあり ([canonical-json.md](../../spec/canonical-json.md))、潰す範囲を狭めれば `diff` も合成もレイヤーの強度比較も無意味に敏感になる。**捨てる判断は正しく、形の側が追いついていなかった。**

**切り分けを冪等にする — 順序に依存しない規則を作る。**全ての線を集めてから一度に切る、あるいは各線の窓を「他の線が効く前の割付」から作れば、§3 は順序と無関係になる。**棄却する** (が、否定はしない)。線が線の結果を読むことは [ADR-0022](0022-lines.md) からの設計であり、貫通通路を二本の線で挟むような書き方はその上に成り立っている。順序非依存にするなら窓の規則そのものを設計し直すことになり、それは 1.0 の破壊的変更である。**いま要るのは「順序を決めること」であって「順序を無くすこと」ではない。**正準順を選べば、一意性は正準形の定義から従う。

**宣言順を正とし、正準JSONに境界の宣言順を残す。**「書いた順に効く」は書き手にとって素直であり、実装も変わらない。**棄却する。**境界の宣言順は合成 (レイヤーの重ね) で容易に変わる — 下層で書いた境界の間に上層が一本挟めば、以降の順序がずれる。**合成で形が動く言語は、レイヤーを持てない** ([ADR-0035](0035-composition-rules.md))。正準順なら、どの層がいつ足しても並びは内容だけで決まる。

**a/b の向きを形に効かせたまま、規範として書き下す。**「先に書いた空間の側を残す」と決めれば規則としては一意である。**棄却する。**`boundary /L1/room /out` と `boundary /out /L1/room` は同じ関係の二つの綴りであり ([ADR-0014](0014-default-boundaries.md))、正準JSONもそう扱う。綴りの違いが 2㎡ の違いになる言語は、関係を一次要素と呼べない。`edge` と `swing` が a/b を読むのは、**その二つが「どちらから見たか」を必要とする概念**だからである — 形は必要としない。

**LIN03 を診断から外す。**誤報するくらいなら黙る、という道はある。**棄却する。**LIN03 は「書いたのに効いていない線」を言う唯一の口であり、[ADR-0028](0028-diagnostics-per-declaration.md) の「書いたのに解釈されなかった値を黙って既定へ落とさない」に真正面から対応する。誤報の原因は判定の是非ではなく母集団の食い違いなので、母集団を揃えれば済む。

## 帰結と代償

**代償1: 既存の `.muro` の形が動きうる。**§1 と §3 に当たる書き方をしていたファイルは、導出される面積が変わる。同梱例 15 本では**一本も動かなかった** (`gate:examples` と `check:examples` が緑、`test/derive.test.ts` のゴールデンは §5 の索引の変更ぶんだけ動いた)。だが外部のファイルについては約束できない。**rc の段でしか払えない代償なので、いま払った。**

**代償2: `canonicalBoundaryOrder` が公開面に増えた。**[ADR-0037](0037-public-surface.md) で 137 名から 106 名へ絞った面に一つ戻したことになる。だがこれは「`Form` の索引を読むのに要る鍵」であって、無ければ消費者が並び替えを各自に書くことになる — それは ADR-0040 が閉じたはずの「組み立ての重複」が索引の側に再発することである。`O(n log n)` の並べ替えを毎回走らせるので、大きな模型で `Form` の索引を引き続ける消費者は自分で一度だけ呼んで持つ必要がある (`plan.ts` はそうしている)。

**代償3: 線の綴りの向きが、診断の文面で入れ替わる。**`line X2,Y2 X1,Y1` と書いたファイルの LIN01/LIN03 は `Line X1,Y1..X2,Y2` と引用する。**書いたとおりの綴りではあるが、書いたとおりの順ではない。**出所 (`file` と `line`) は変わらないので、行は正しく指せる。

**代償4: 切り分けの順序が「書いた順」から見えなくなった。**正準順は内容で決まるので、書き手が並べ替えても効く順は変わらない — これが狙いである。だが「なぜこの線が先に効くのか」を読み解くには `between` の辞書順を知る必要がある。線が線の結果を読む構成は元々読み解きが難しく、そこは変わっていない。

**帰結: 「一意」が機械の縛れる述語になった。**`test/uniqueness.test.ts` が上の含意を直接書く — 正準形が等しいことを**前提として確かめてから**形の一致を主張するので、前提が崩れれば「この組は何も証明していない」と落ちる。§1〜§4 の各々に、実測の数を持つ節がある。

**帰結 (副産物): 存在しない ADR への参照を消した。**`src/core/` と `test/` の 7 ファイル 9 箇所が「ADR-0027」を引いていたが、**そのADRは書かれたことがない** (0026 の次は 0028 であり、git の履歴にも一度も現れない)。指していた中身 — 線の及ぶ窓・凸片の幾何・「形を読む唯一の入口」— は実在する規則なので、[ADR-0022](0022-lines.md) と [derivation.md](../../spec/derivation.md) §1 へ向け直した。「判定と操作を同じ場所に置く」「母集団のずれ」を引いていた二箇所は本ADRの §4 を指す。**規範の所在が嘘をついている状態は、規範が無いより悪い。**

**帰結: 八つの面がすべて凍らせられる状態になった。**[roadmap](../roadmap.md) の表から 🔨 が消える。scope.md §6 の「導出の契約」は、文としての約束から、**検査できる約束**になった。
