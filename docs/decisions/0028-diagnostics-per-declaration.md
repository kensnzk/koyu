# ADR-0028: 診断の母集団は書かれた宣言である

日付: 2026-07-26 / 状態: 採用 (v0.13) / 起点: 全66コードの網羅監査 (母集団・出所・語彙台帳・三台帳の一致・CLIの数字・メッセージの実用性の6視点、所見30件)

## 文脈

ADR-0016 は診断に**コード**と**severity**の契約を与えた。契約の形は正しかったが、契約が**何に対して**結ばれているかは書かれていなかった。監査が示したのは、その空白がほぼ全ての系統に同じ穴を開けていたということである。

**穴は一つの病だった。診断の母集団が「書かれた宣言」ではなく「たまたま解釈できた値」になっていた。**

三つの顔で現れる。

**顔1: 解釈できなかった値が黙って既定へ落ちる。** `daylight` だけが DAY01 で 0/1 を強制されていて、他の★属性は素通りだった。`zone /site site:yes` と書くと `zone.attrs["site"] !== 1` が真になり、`continue` の先にある **SIT03 (建物が敷地形状からはみ出す — error)** が丸ごと走らなくなる。`space ... h:35OO` (数字の0でなく英字のO) と書くと `typeof own === "number"` が偽になり、**HGT01 (上階への食い込み — error)** が消える。どちらも check は緑になる。`ceiling:none` は天井を張り、`turn:l` は折返し階段を鏡像にし、`slope:1/12` は斜路の勾配検査を無音にする。**同じ誤りを `level` の `h:` でやると、parse がその場で構文エラーにする** — 防護が片側にしか無かった。

**顔2: 宣言の帰結ではなく、集合の帰結を数えている。** COL01 は「この柱の宣言から何本立ったか」を問うつもりで `columnsFor(model, lv).length` を数えていた。これは**そのレベルの全宣言**の合計なので、同じ階の別の宣言が一本でも立てた瞬間、一本も立たない宣言が黙って通る。VRT05/VRT06/OPN03 は `if (b.openings.length > 0)` で境界ごとに1件しか出さないので、五枚の扉が同じ一行を指す。GEO01 は逆に、どの矩形の組かを言わないまま組ごとに出すので、バイト単位で同一の診断が三件並ぶ。

**顔3: 出所が無い。** 書かれた宣言に対する診断8コード (BND05 LVL01 GEO02 COL02 HGT01 HGT02 HGT03 HGT04) が `line` を一つも持たなかった。うち5つは error である。互換層は `line` が無ければ位置接頭辞を組めないので、**error なのに「どのファイルの何行目か」が一切出ない**。HGT01/HGT02/HGT04 は同じ関数の中に空間 `s` を持っていて、隣の DAY01 は `s.line` を渡している。LVL01 と HGT03 は `Level` 型そのものが `line` を持っていなかったので、原理的に付けられなかった。

同じ病が集計にも出ていた。「延べ面積」を問う三箇所 (`stats` / `site` / MCP `model_summary`) がそれぞれ別の母集団を持ち、CLI の `stats` だけが exterior 型の空間を屋内床面積に数えていた。しかも除外されるかどうかが「隣に道路を書いたか」(半屋外の導出条件) という無関係な事情で決まっていた。

## 決定

**1. 解釈される属性の値は検査される。** DAY01 の一般化である。`spec/vocabulary.md` の★が契約なので、台帳に載っている属性の値が台帳の型に合わなければエラーにする。`ATT01` (正の数値でない) と `ATT02` (語彙にない) の二コードを切り、実装は `check.ts` の `ATTR_RULES` 一枚の表が持つ。**書いたのに解釈されなかった値を、黙って既定へ落とさない。**

型ではなくコードを二つに割ったのは、直し方が違うからである — 前者は「単位を書かない・数字の0を使う」、後者は「台帳の綴りに揃える」。severity はどちらも error である。値が読めていないという事実は、疑わしさではなく構成の不成立だからである。

**2. 診断は宣言ごとに一件、その宣言の行を指す。** 柱は `Column.decl` (どの宣言から立ったか) を持ち、COL01 は宣言ごとの本数を数える。開口と seg を咎める診断は、親の境界宣言ではなく当の `door` / `window` / `seg` の行を指し、宣言が五つあれば五件出る。GEO01 は重なった矩形の組を書かれた通り語で名指す。

**3. 集合に対する診断でも、集合を作った宣言の行は必ず指す。** BND05 (edge 限定の有無が混在) のように母集団が本質的に集合であるものは、代表の一件を `line` に、残りを `related` に載せる。「どこかで併存している」だけでは直す場所が無い。`Level` に `line`/`file` を足したのは、LVL01 と HGT03 と VER03 (underground) をこの規律の外に置かないためである。

**4. 一本も立たない柱の宣言は、理由で二つに分かれる。** 床が無い (COL01) と、先の宣言に全交点を取られた (COL02) は違う失敗である。後者を「通りの交点に床がありません」と言うと、直しようのない場所へ人を送る。COL02 は「サイズが違う and 無限定の宣言が2つ以上」という代理指標をやめ、**実際に一本も立たなかった宣言に対して**、影を作った宣言を `related` に添えて出す。

**5. メッセージは直す場所を教える。** 導出値だけを言って書かれた原因を落とさない。

- BND04 は「接していない」と断言する前に `edge` を外して線分を取り直し、取れたら「edge:N に共有辺がありません (実際に接しているのは E です)」と言う。**二室は接している** — 直すのは方角一語であって割付ではない。
- HGT02 は HGT01 と同じ三項 (`天井高 + slab = 合計 > 階高`) を出す。決め手が上階の slab のとき、旧文は「天井高3000は階高3000を超えます」という成り立たない不等式を述べていた。被覆率は免除しきい値 (99%) と衝突しないよう小数一桁で言う。
- BND06 は `edge` を本文に入れる。落としたために、同じ空間について ENV01 と正面から矛盾する二文が同時に出ていた。
- ENV01 は塞がっていない外周を方角ごとに列挙する (`N 3600mm / W 4500mm`)。`envelopeGaps` は座標つきの線分を返しているので、算出済みの情報を捨てていただけである。

**6. 「延べ面積」の母集団は一箇所が答える。** `model.ts` の `isIndoor(model, s)` が唯一の答えで、`stats` / `site` / MCP の三つが同じ関数を呼ぶ。exterior は屋内床面積に入らない。`zoneAreaM2` も同じ判定を使う — MCP の `model_summary` が敷地ゾーンを「160㎡」と報告し、同じモデルについて `site` が「3854.00㎡」と答える、という状態を終わらせる。

**7. 呼び方の問題は呼び方の問題として返す。** `-l` が解決できないレベル指定を空配列に落とすと、空配列は「一枚も描かない」を意味するので、中身の無いSVGを終了コード0で「生成しました」と印字することになる。未宣言のレベル名は宣言済みの一覧を添えて終了コード2で落とす。範囲の端点から数字の要求を外したので、`R` (屋上) のようなレベル名も端点に取れる。

## 代替案

**属性の値検査を parse の SourceError にする。** `level` の `h:` と同じ扱いになり一貫する。採らなかったのは、parse の例外が**最初の一件で止まる**ためである。診断は全件を一度に見せるほうが直す回数が少なくて済む。加えて、値の妥当性は「台帳がその属性をどう読むか」の話であり、構文ではなく意味論の層に属する。`level` 側を診断へ寄せる案もあるが、レベルの z と h はモデル全体の幾何が依存するので、壊れたまま先へ進める意味が薄い — 非対称は残るが、非対称であることに理由がある。

**★属性ごとに専用コードを切る** (`CEI01` `TRN01` …)。メッセージは最も具体的になるが、台帳が三箇所 (実装・spec・guide) にあるので、属性を足すたびに三箇所へコードが増える。属性は今後も増える語彙なので、コードの数を語彙の数に比例させない。`ATT01`/`ATT02` の本文が属性名と書かれた値を必ず含むので、具体性は本文が担う。

**DAY01 を ATT02 に畳む。** 同じ形なので魅力的だが、DAY01 は言語版の移行 (VER02 — 0.3以前は型から採光を推定していた) の説明に組み込まれていて、本文もその文脈を語っている。畳むと移行の説明が薄くなる。台帳に「daylight は DAY01 が、form は RUN05 が、縦動線の向きは RUN02 が既に守っている」と書いて重複を避けた。

**COL02 を廃止して COL01 に一本化する。** 「一本も立たない」という現象は同じだからである。採らなかったのは、直す手が正反対だからである — COL01 は床か通りの指定を直し、COL02 は宣言の順序か通りの限定を直す。severity がコードの不変属性である以上 (ADR-0016)、直し方が違うものは違うコードで言う。

**boundary の `h` を実装から外す。** 台帳が「解釈しない」と言っているのに `axo.ts` が手すり天端の高さとして読んでいた (掟7 違反)。外すのは一行だが、**読んでいる振る舞いのほうが正しい** — `air:1` の境界に高さを与えるのは手すりと腰壁を区別する唯一の手立てである。台帳の側を実装に合わせ、★を付けて値検査の対象に入れた。台帳が契約であるとは「台帳を実装に合わせて直す」ことも含む。

## 帰結と代償

**得たもの。** 一行の綴り誤りが error 検査を丸ごと無効化する、という最も高くつく黙殺が塞がった。診断は宣言ごとに出て、宣言の行を指す。「延べ面積」に対して三つの数字が返る状態が終わった。

**代償1: 診断の件数が増える。** 開口ごと・seg ごとに出るようになったので、五枚の扉を持つ垂直境界は VRT05 を五件出す。件数で驚かせる代わりに、直す場所が五つ全部わかる。

**代償2: 既存のファイルが新たにエラーになりうる。** `ceiling:none` や `site:yes` を書いていたファイルは、これまで緑だった。**それは黙って無視されていたということである**ので、エラーになるのが正しい。言語の意味論は変わっていない (書けた語の解釈は同じ) ので、言語版は上げない — 検査が増えただけである。

**代償3: 台帳が四つになった。** 実装の `DIAGNOSTIC_CODES` / `ATTR_RULES` / spec の診断表 / spec/vocabulary.md の★。`ATTR_RULES` は vocabulary.md の写しなので、乖離しうる。テストが集合一致を検査するのは診断コードだけで、属性の台帳は人が揃える — ここは弱い。属性台帳の機械照合は次の宿題である。
