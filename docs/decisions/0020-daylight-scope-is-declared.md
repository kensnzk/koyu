# ADR-0020: 採光の対象は宣言である — 型から推定せず、属性はツールの振る舞いを名指す

日付: 2026-07-26 / 状態: 採用 (言語版0.4) / 起点: `light` の対象集合と、属性名 `hab` への指摘

## 文脈

`light` (採光) の対象は「住居系の五つの型」— `unit` `room` `ldk` `bedroom` `living` — として実装されていた。この集合は三重に壊れている。

**1. MECE でない。** `room` は `bedroom` と `living` を含む。`ldk` は Living・Dining・Kitchen の合成の名であり、`living` はその構成要素である。同じ台帳に並べた瞬間に包含関係が生まれ、「どちらで書くのが正しいか」に答えが無くなる。台帳の規則3が禁じている「同じ意味に別の語を使う」を、台帳自身が作り出していた。

**2. 粒度が混ざっている。** `unit` は住戸 — 室の集合であって室ではない。`bedroom` は室である。両者を同じ集合に置くと、`light` は住戸まるごとに 1/7 を掛けたり、その中の一室に掛けたりする。実際 mansion.muro では A タイプだけが ldk/bedroom に割られ、B〜E タイプは `unit` 一つのまま同じ判定に載っていた。判定の分母が階層のどこにあるのか、モデルからは読めない。

**3. 記法の原則に反していた。** [spec/vocabulary.md](../../spec/vocabulary.md) の規則1は「構造として解釈される語を増やすのは最後の手段」と言い、`type` は開かれた語彙で、構造として解釈されるのは `exterior` と `void` だけ — と宣言している。この二つは正当である。床面積に算入するか・通れるか・外部か、という**構成の事実**に効くからだ。採光の対象かどうかはそうではない。用途の判断であり、構成のトポロジーからは出てこない。にもかかわらず五つの型が黙って解釈されていた。guide は「型は室の説明ではなく、判定の入口である」と書いていたが、正しくは**入口であるべきなのは型ではなかった**。

決定的なのは法の側である。**建築基準法2条4号の居室は「居住、執務、作業、集会、娯楽その他これらに類する目的のために継続的に使用する室」であって、室の名前では決まらない。** 納戸と称する室が実態として居室と判断されるかは審査の争点であり続けている。名前から推定する実装は、近似が粗いのではなく、**法の判断構造そのものを取り違えている**。

**そして属性の名にも同じ取り違えがあった。** 最初の修正は既存の `hab` (habitable の略) を唯一の入口に昇格させるものだったが、この名が二つの問題を持ち込む。

- **「居室」と「採光判定の対象」は同じ集合ではない。** 法28条1項の採光義務は住宅・学校・病院・診療所・寄宿舎・下宿等の居室に限られる。事務所の事務室は法2条4号の**居室であるが、採光義務は無い**。`hab:1` と書かせておいて 1/7 を掛けるのは、法概念の名で別のことをしている。最初の版はこのずれを台帳の注記で塗り潰していた — 直したはずの「名前と判定のずれ」を、属性名の側で再生産していたことになる。
- **`habitable` は英語圏で外延が違う。** IBC の habitable space は living / sleeping / eating / cooking であり、事務室を含まない。日本の居室は執務を含むぶん広い。名前が同じで範囲が違う語は、国際的に読まれうる記法では最悪の選択である。加えて `hab` という略語自体は業界の慣用ではなく、koyu が勝手に縮めたものだった。

## 決定

**1. 採光の対象は宣言である。`daylight` が唯一の入口となる。** `light` の対象は `daylight:1` を書いた空間だけであり、型は一切見ない。既定は対象外 (`daylight:0` と同じ)。五つの型の集合は実装から消える。

**2. 属性は法概念ではなく、ツールの振る舞いを名指す。** `daylight:1` の意味は「この室に採光の 1/7 判定を掛ける」であって、「この室は法2条4号の居室である」ではない。台帳 (規則3) の言う「ツールが読む属性は契約」の契約相手はツールの挙動であり、ツールが部分的にしか実装していない法概念ではない。この立て方には三つの効き目がある。

- **注記で塗り潰していたずれが消える。** 事務室に `daylight:1` を書く著者は「ここに 1/7 を掛けよ」と言っているだけで、法概念を誤用してはいない。判定の法的根拠は書き手が引き受ける — koyu は粗い早期警報であって適合判定ではない、という既定の立場と一致する。
- **外延の食い違いが問題にならない。** 「採光の判定をする室か」は法域を問わず一意に読める。
- **拡張の道が一本になる。** 用途別の割合 (令19条3項: 住宅の居室 1/7、学校の教室 1/5 等) を将来入れるなら、それは同じ属性の値の話になる。第二の軸を足さずに済む。今回は真偽値に留める (代替案を参照)。

**3. 型は完全に開かれた語彙に戻る。** 構造として解釈される space の型は `exterior` と `void` の二つだけになった。`ldk` も `bedroom` も `unit` も、`hall` や `wet` と同じ、koyu が解釈しない自由な語である — 集計の軸として `stats` が型別小計を出し、平面図に刷られるが、判定には関与しない。**判定の入口を型から追い出したことで、「どの語が構造か」の答えが二語まで痩せた。** これは規則1が求めていた方向である。

**4. 判定の分母は書き手が選ぶ。** `unit` に `daylight:1` を書けば住戸まるごとが一室として判定され、ldk/bedroom に割って書けば室ごとに判定される。どちらも正しい — **基本計画の解像度をどこに置くかは書き手の決定**であり、koyu はそれを推定しない。従来は同じ選択が「型を何と綴ったか」の副作用として黙って決まっていた。粒度は宣言の位置として可視になる。

**5. `daylight` の値は 0 か 1 に限る (診断 DAY01)。** `daylight:true` `daylight:yes` のような綴りが黙って対象外に落ちるのを防ぐ。唯一の入口になった以上、その綴り間違いは判定の全損である。

**6. 言語版を 0.4 へ上げ、旧版は判定可能な条件つきで受理する** (ADR-0017 決定3の踏襲)。0.3 以前の意味論では五つの型が対象だったので、**「推定対象だった型の空間があり、`daylight` が書かれていない」ファイルは 0.4 で判定から黙って外れる**。この条件は機械検査でき、該当すればエラー (VER02) で二択を示す — `daylight:1`/`daylight:0` を書くか、書いた上で 0.4 へ上げるか。`daylight` が明示されているファイルは新旧で意味が同一なので、旧版のまま受理される。

`LEGACY_DAYLIT` は `src/check.ts` にこの受理条件の判定のためだけに残る。**意味論には一切効かない** — 五つの型は 0.4 の言語からは消えている。

## 代替案

**集合を直す (`room` だけにする / `unit` を外す)。** 最短だが、三つの壊れのうち一つ (MECE) しか直らない。名前から法判断を引く構造が残り、開かれた語彙という宣言との矛盾も残る。そして「では `study` は？ `洋室` は？ `office` は？」に原理的な答えが無いまま、台帳が語を足し続ける圧力に晒される — 原稿が棄却した「巨大なクラス階層」への最初の一歩である。

**居室/非居室を型の第二の軸として構造化する** (`type` を居室系・非居室系に分類する)。分類を台帳に持つ点で上と同じ問題を抱え、加えて型に階層を導入する。語彙で意味を与えるという方針の放棄になる。

**属性名を `hab` / `habitable` / `居室` にする。** 最初の版はこれを採り、棄却した (決定2)。法概念と判定対象がずれること、`habitable` の外延が法域で違うこと、`hab` が業界の略語ではないことによる。**「名前から判定を推定するな」と言いながら、属性名で法概念を名乗るのは同じ誤りの再生産である。**

**三値にする (`daylight` 未指定は型から推定、明示があれば従う)。** 移行が無痛になるが、直したはずの推定が既定として残り続ける。「書かなければ推定」は最も静かな罠であり、`daylight` が唯一の入口だという主張を初日から嘘にする。

**値を割合の分母にする (`daylight:7` = 1/7、`daylight:5` = 1/5)。** 令19条3項の用途別割合をそのまま書けるようになり、事務室に書いても著者が割合を選ぶので精度が上がる。魅力的で、決定2が開けておいた道でもある。だが今回は採らない — koyu が持つのは 1/7 の粗い判定ひとつであり、補正係数も方位も隣地距離も無い状態で割合だけ精密にしても、精度が不均等になるだけである (ADR-0006 の先送りの列)。**属性の形を変えずに値だけ広げられるので、要求が出てから入れられる。** 真偽値の `1` は、分母を書く形の部分集合として素直に読み替えられる。

**`daylight` を zone から継承させる** (`use` と同じ流儀)。住戸を一行で対象にできるが、実例が要求しない — mansion/tower の住戸ゾーンは配下に `wet` `hall` を持ち、継承すれば対象外の室まで入る。継承の恩恵が最も欲しい場面で継承が誤る。ADR-0008 が `use` にだけ継承を与えたのは、`use` が集計軸 (住戸全体に一様) だからで、採光の対象性は室ごとに違う。

## 帰結と代償

**書き忘れは静かである。** これが最大の代償で、正直に開示する。`daylight` を書かなければ `light` は「採光の対象がありません」と言って**終了コード0を返す**。全室合格と区別が付かない。この罠は従来も存在したが (型を綴り間違えれば同じことが起きた)、既定が対象外になったことで踏む頻度は上がる。緩和は三つ — 対象0件のときのCLI文言を「採光の対象がありません (判定する室に daylight:1 を書きます)」に改め、`daylight()` の戻りは空配列なので API では `length` を見よ、と guide に書き、旧版からの移行は VER02 が全件を名指しする。**`check` の警告にはしない** — 採光を要する室を持たない建物 (倉庫・駐車場・機械棟) は正常であり、正常な状態に警告を出す診断は無視を学習させる。

**1/7 は住宅の割合であり、それは変わらない。** 令19条3項の用途別割合 (学校の教室 1/5 等) と、法28条1項の建築物用途による適用範囲は扱わない。ただし属性名が判定を名指すようになったことで、**これは「koyu が持つ判定は一つだけ」という正直な表明になり、法概念の誤用ではなくなった**。ADR-0006 が既に持つ先送りの列 (補正係数・隣地距離・開口の方位) に、用途別割合が一つ加わる。examples/office.muro に `daylight` を書かないのは、事務室に法28条1項の採光義務が無く、1/7 を掛ける意味が無いからである。

**移行の実測。** examples に `daylight:1` を 30 行、eval フィクスチャ (tower の uid つき複製) に 31 行加え、版を 0.4 へ上げた。展開後の空間で言えば mansion 51室・tower 66室・house 2室である。**`light` の対象集合は移行の前後で完全に一致する** — 全ての判定結果 (室数・窓面積・合否) がバイト一致で、`check:examples` も緑のままである。つまりこの変更は既存コーパスに対して意味保存であり、変わったのは**同じ答えの出どころが推定から宣言になったこと**だけである。正準JSON は `daylight` を自由属性として運ぶので形は変わらない。

**得たもの。** 「型は開かれた語彙である」が言い訳なしに言えるようになった。構造として解釈される space の型は `exterior` と `void` の二語であり、どちらも構成の事実に対応する。判定の入口は全て属性の側にあり、**そのどれもがツールの振る舞いを名指している** — `daylight` (採光判定)、`road` (接道の幅員)、`site` (敷地の集約)、`use` (集計軸)。**語彙の台帳が「何が構造か」と「その語で何が起きるか」を同時に答えられる文書になった。**
