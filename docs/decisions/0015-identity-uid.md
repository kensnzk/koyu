# ADR-0015: 同一性 — パスはアドレス、uidは寿命の長い参照

日付: 2026-07-25 / 状態: 採用 (v0.10) / 起点: 外部レビュー§4.2 ([docs/reviews/](../reviews/))、方向性計画§2.3

## 文脈

koyuのパスは三役を兼ねる: アドレス (名指し)、集計の階層 (ADR-0008)、同一性。前二役にパスは最適だが、三役目は改名・階層再編・分割統合で壊れる — パスを外部キーにするツイン戦略 (docs/horizon.md) は、renameの瞬間に蓄積済みの時系列を失う。一方、全要素UUIDはIFCの轍であり、「GUIDの対応表が要らない — パスがそのまま意味」というkoyuの貢献を自ら手放すことになる。答えは三役のうち三役目だけを、必要な要素に限って移せるようにすることである。

## 決定

**1. `uid:` を予約語彙にする (space / zone)。** 任意の不透明トークン。パスからもパス以外の属性からも導出しない (パス由来ではrename耐性がゼロになる)。モデル全体 (space/zone横断) で一意 — 重複はcheckエラーで、1つのuidにつき1本のエラーに全所有者を列挙する (スパン展開が同一uidを複製したときに原因が読めるように)。レベル範囲・スパン行にuidは書けない (展開先ごとに固有のuidが要る — 重複エラーがそれを言う)。

**2. 数字だけの形と空白はエラー。** parseは数値の形の属性値を数値化するため、`uid:0123` は数値123になり書いたトークンの区別が失われる — 不透明性がcheck以前に壊れる。よって数字だけのuidは禁じる (`sp-123` のような形にする)。空白を含むuid (`uid:"a b"`) も禁じる。

**3. renameしてもuidは動かさない。** 「改名後も同じ空間か」は幾何や名前から機械的に決まらない設計判断であり、uidを運ぶ行為がその判断の記録になる。分割は本体側が継ぎ、他方は新uid。統合は残る側が継ぐ。semantic diff (ADR-0018) はuid一致・パス不一致を「改名」として報告する。

**4. 使い分けの規範。** パスはアドレスと集計。uidは寿命がパスより長い参照 (センサー・BEMS・台帳・長期運用のjoin) のためのもの。リポジトリ内の参照 (boundary・doors・zone集計) は従来どおりパス — 内部参照のuid化は可読性を殺すのでしない。正準JSONにはattrsとして保存される (機械はそこからuid→現パスを解決する)。

## 代替案

**全要素への自動付与**は、rename耐性が要らない利用者にも行の重さを課し、採番のランダム性が「同じ構成→同じバイト列」(ADR-0013) と衝突する。opt-inで始めて、evalとコーパスが全付与を要求したらツールの一括付与に広げられる (逆は破壊的)。**sidecar台帳 (ids.json)** は原本を汚さないが、真実が二ファイルに割れる方がkoyuには重い。**alias/rename履歴の第一級化**は、Git履歴+uid不変で追える間は持たない。**boundary/openingのuid**は、宣言的同一性 (ADR-0013の対+edge) とportal graph (保留) の後の話。

## 帰結と代償

外部システムはuidでjoinし、改名に耐える。IFC取り込み時のGUID (`guid:` — ifcx-notesの方針) と同じ構文パターンで共存し、同一性の機構は増えない。実装は予約語彙の検査のみ数十行。代償: uidの一意性はcheckが守るがuidの「正しさ」(同じ部屋に同じuidを運び続けること) は人間の規律であり、ツールは検証できない — それがこの設計の含意 (同一性は設計判断) でもある。
