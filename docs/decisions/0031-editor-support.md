# ADR-0031: エディタ支援 — 文法は一枚、赤は check が持つ

日付: 2026-07-27 / 状態: 採用 / 言語版: 据え置き (koyu 0.5 — 意味論を変えない)

## 文脈

ドキュメントを Docusaurus で組むにあたり、`.muro` に色が要る。同じ色は書く場 (VS Code) にも要る。

ところが両者は文法の形式が違う。Docusaurus (v3) の既定は Prism (JavaScript の正規表現の連想配列)、
VS Code は TextMate 文法 (`.tmLanguage.json` を Oniguruma が読む) である。**Prism の定義を書いても
VS Code は読まないし、逆も読まない。**素直に書けば、語の一覧が二枚になる。

これは色の問題ではなく台帳の問題である。koyu の語彙は開かれていて育つ (ADR-0008) し、
**台帳が契約である** (掟7)。文法を二枚持てば、乖離しうる場所が spec・実装・文法A・文法B の四つになる。

もう一つ、色より重い問題がある。エディタが赤を出すには整合を知らねばならないが、
**整合を知っているのは `check` だけ**である (掟1)。エディタが独自にパースを始めれば門番が二つになり、
「エディタは緑、CLI は赤」が起きる。これは診断契約 (ADR-0016) が最も避けたかった状態である。

記法の側の事情も見ておく。`.muro` は行志向で、`#` コメント・行頭のキーワード・`key:value`・
通り参照 (`X2+600`) という単純な字句しか持たない。**正規表現で足りる**ので、
色のためにパーサを持ち出す必要はない。

## 決定

**1. 文法は TextMate 一枚を原本にする。**

`editors/vscode/syntaxes/koyu.tmLanguage.json` が唯一の文法である。VS Code はこれをそのまま読む。
Docusaurus は Prism を **Shiki** に差し替えて同じ一枚を読む — Shiki は VS Code と同じ Oniguruma で
TextMate 文法を解釈するので、**サイトとエディタの色が定義上一致する**。
npm パッケージからは `@kensnzk/koyu/syntax` で参照できる。

**2. 拡張は翻訳しかしない。**

VS Code 拡張 (`editors/vscode/extension.js`) は `koyu check --json` を呼び、
`Diagnostic[]` を VS Code の診断へ写すだけである。パーサも規則も持たない。**門番は一つ**であり、
CLI・MCP・エディタは同じ答えを見る。診断は位置を行までしか持たない (ADR-0016) ので、
下線は行全体に引かれる。

**3. 台帳の★は、自由な `k:v` と色が分かれる。**

[spec/vocabulary.md](../../spec/vocabulary.md) の★ (ツールが解釈する属性) と、運ばれるだけの自由な語を
別のスコープに割る。**書いた語が解釈されるかどうかが、書いている最中に見える。**
ADR-0028 の「書いたのに解釈されなかった値を、黙って既定へ落とさない」の、エディタ側の対応物である。
テーマによっては同じ色になる (VS Code 既定の Dark+ がそう) が、★が無色になるテーマは避けて選んだ。

**4. 語の一覧はテストが縛る。**

`test/grammar.test.ts` が、行頭に書ける語を `src/parse.ts` の `switch (head)` と、
字下げして書ける語を `indented` 分岐と、色の分かれる属性キーを台帳の★と突き合わせる。
**一致しなければ落ちる。**文法は四つめの事実の置き場になってはならない。

**5. 層を開いたら、同じディレクトリの `main.muro` を起点に検査する。**

`import` 合成 (ADR-0010) された層は単体では `grid` も `level` も見えないので、そのまま検査すれば
赤で埋まる。起点を自動で選び、返ってきた診断を**出所 (`file`) ごとに配り直す**ことで、
開いている層に、その層の赤だけが出る。

## 帰結と代償

- **Docusaurus 側に配線が要る。**Shiki は v3 の既定ではない。代償は配線とビルド時間で、得るものは文法が一枚であること。
- **色は正しさを保証しない。**文法は正規表現であってパーサではない。色が付いていても `check` は赤を出す。**答えは常に `check` の側にある。**
- **CLI が無ければ色だけになる。**意図した縮退である。読むだけの人 (ドキュメント読者・レビュアー) には色だけで足りる。
- **未保存のバッファは検査できない。**CLI はファイルを読む。保存が検査の契機になる。
- Marketplace への公開はしない (当面)。手元に置く手順は [guide/howto/editor.md](../../guide/howto/editor.md)。

## 棄却した代替

- **Prism の定義を別に書く。**Docusaurus の既定に乗れて配線が要らない。棄却の理由は一つで、語彙が育つたびに二箇所を直すことになるから。台帳が契約である以上、写しは一枚に保つ。
- **Language Server (LSP) を書く。**補完・定義ジャンプ・未保存バッファの検査まで届く。だが今要るのは色と赤であり、CLI を呼ぶ 150 行がそれを満たす。パス補完や `koyu doors` のホバーが欲しくなった時に、この決定を訪ね直す。
- **拡張の中でパースする。**速い。だが門番が二つになる (掟1)。実行時間の問題は、起きてから測って直す。
- **GitHub の色 (linguist) に登録する。**同じ文法がそのまま使えるが、登録には利用実績の閾値がある。文法が一枚である限り、条件が揃った日に出せばよい。
