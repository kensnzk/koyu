# ADR-0016: 診断契約 — checkの返りを構造化し、severityをコードに固定する

日付: 2026-07-25 / 状態: 採用 (v0.10) / 起点: 外部レビュー§5.7 ([docs/reviews/](../reviews/))、方向性計画§2.3 (D-007の恒久解)

## 文脈

checkの診断は日本語文字列の配列だった。人間には十分だが、機械には貧しい: エージェントやエディタが「どの種類の問題か」を知るには本文の正規表現照合しかなく、メッセージの言い回しを改善するたびに外部の照合が壊れる。severityも実装の中に散っていて、specと実装の食い違い (レビューD-007: void境界の警告がspecではエラーと書かれていた) を検出する機構が無かった。一方で、既存の文字列はテスト約40箇所とMCPクライアントが依存する現に働く契約であり、壊さずに構造を足す必要がある。

## 決定

**1. 一次形式は `checkDiagnostics(model): Diagnostic[]`。** 各診断は `code` / `severity` / `message` (日本語本文 — 位置接頭辞「file:N行目: 」を含まない) / `line`・`file` (出所 — 位置を持たない診断は省略) / `path` (対象の空間・ゾーン・polygonパス。境界は両パス) / `related` (重複の既出側などの関連位置)。`check(model)` は互換層になり、`line` があれば「file:N行目: 本文」、なければ本文をそのまま — 既存の文字列と件数・順序・字面が完全一致する。

**2. コード体系は領域2-3字+2桁連番** (REF/BND/LVL/GEO/VRT/OPN/SEG/ZON/HGT/SIT/UID/VER/SYN)。台帳は実装の `DIAGNOSTIC_CODES` とspec (semantics.md §5の表) が二重に持ち、テストが集合一致を機械検査する — specと実装のseverity不一致は再発しない (D-007の恒久解)。廃止されたコードは欠番として台帳に墓標を残す (BND07 —「接しているのに境界が無い」警告。ADR-0014で廃止)。

**3. severityはコードの不変属性。** 同じコードがあるときはエラー、あるときは警告 — という揺れを持たない。重さを変えたくなったら、それは意味の変更であり新コードを切る。外部の照合 (CI・エディタ・エージェント) はコードだけを見て安全に分岐できる。

**4. 例外は診断にしない — 写すのは出口だけ。** 構文・合成エラー (SourceError) はparseが投げ、checkは投げない、という既存の分担は保つ。ただし `koyu check --json` は機械向けの出口なので、SourceErrorをSYN01の1件に写して常に有効なJSONを返す (exit 1)。CLIにはあわせて `--strict` (警告があれば終了コード1) を足す — 人間向け出力は不変。MCPの `check` は `diagnostics` を追加で返す (既存の `errors`/`warnings` 文字列も残す)。

**5. 配置エラーの構造化は導出側で。** placeBand (開口・segの配置) はsrcRefを焼き込んだ文字列を返していた。`{error, code, line, file, message}` に拡張し、`error` (完成文) は互換のため残す — plan.tsの `'error' in placed` 判定と既存テストは無傷。コードは呼び手のlabelで決まる: 開口はOPN04〜08、segはSEG04〜08。

## 代替案

**文字列のまま** (現状維持) は、エージェントが門番 (check) の結果で分岐する用途 — このDSLの中心用途 — で正規表現照合を強い、メッセージの改善を破壊的変更にしてしまう。**severityを設定可変にする** (lintのprofile方式) は、「エラー = 構成が成立していない / 警告 = 疑わしい」という意味論上の区別を利用者の好みに落としてしまう — koyuのエラーは様式違反ではなく矛盾である。可変にしたい需要が現れたら、それは警告の話であり別の機構 (lint) で受ける。**コード無しでオブジェクト化だけ行う**案は、機械分岐の鍵が結局messageになり、構造化の意味が薄い。**LSP互換のrange (行+列)** は、パーサが列を持っていない今は虚偽の精度になる — 行までを契約とし、列は必要になったら足す (フィールド追加は非破壊)。

## 帰結と代償

エージェント・CI・エディタはコードで分岐し、メッセージの言い回しは自由に改善できるようになった。checkの互換層は診断から文字列を組むだけの数行で、二重実装は無い。代償: コード台帳の維持 — 検査を足すたびにコードを切り、spec表と実装の両方を更新する (怠るとテストが落ちるので、忘れる自由は無い)。severity不変の規律により、重さの変更は「新コード+旧コードの欠番化」という重い手続きになる — それがこの契約の意図であり、外部照合を黙って壊さないための代償である。

## 追記 (2026-07-26): 並びも契約だった — だから節の粒度は「走査単位」である

決定1は `check` が互換の文字列を「同件・同順」で返すと書いた。**同順**と書いた以上、
並びは契約である。ところが契約の**内容**は書かれていなかった — 何の順なのか。

`checkDiagnostics` が732行の一枚岩に育ったので、節に割ろうとして初めてそれが問題になった。
割り方には二つある。**診断コードの族で割る** (境界の検査をまとめて、開口の検査をまとめて) か、
**走査単位で割る** (`model.boundaries` を一周するループを一つの節にする) か。前者のほうが
名前は綺麗になる。実際に切って全検体で確かめた結果、**前者は並びを壊す**。

```
boundary /L1/a /L1/far t:120     ← BND04
  door w:900                     ← OPN04
  seg w:600                      ← SEG04
```

この三つは今、続けて出る。族で割ると BND04 は他の境界の BND04 と並び、OPN04 は他の
境界の OPN04 と並ぶので、**一本の境界について何が起きているかが読めなくなる**。
これは実装の都合ではなく、読み手にとっての意味の問題である。

**決定: 診断は走査の順に出る。節の粒度は走査単位であって、診断コードの族ではない。**

帰結として、一つのループを二つの節に割ってはならない。ループの `continue` は
「この対象の残りを飛ばす」を意味するので、段に切り出すときは**呼び出し側の
`continue` として残す** — 判定の綴りをヘルパの中へ持ち込むと、同じ条件が二箇所に
分かれて片方だけ直る。垂直境界が水平の検査を一切受けないこと、置けなかった開口が
hinge の軸検査も重なり検査も受けないこと、`slabMissing` がレベル対ごとに後置きで
出ること — これらはすべて `continue` が担っている意味であり、関数境界に写すときに
最も落ちやすい。

**リファクタの不変は機械で確かめる。**同梱例14本と guide の全 muro ブロックを合わせた
194検体に対し、割る前の診断367件 (code/severity/message/line/file/path/related の全フィールド)
を採取し、割ったあとバイト同一であることを確かめた。**既存のテストはこの並び替えを
一件も検出できなかった** — 同梱例には「一本の境界が複数のコードを出す」場面が無いためである。
だから恒久の網として、その場面をわざと作る模型を test に置いた。
