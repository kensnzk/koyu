# ADR-0040: 形の参照実装 — `derive(model): Form` を唯一の入口にする

日付: 2026-07-28 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [方針の総覧](../policy.md) §5.6-1・§5.6-3・[spec/scope.md §6](../../spec/scope.md) / 関連: [ADR-0032](0032-three-domains.md) (三つの領域)・[ADR-0022](0022-lines.md) (描かれた線)・[ADR-0024](0024-fabric.md) (面)・[ADR-0021](0021-vertical-circulation.md) (縦動線)

## 文脈

方針 §5.6-1 はこう書く — 「**導出の規則は仕様が持つ。**実装ではない。規則が消費者ごとに違えば、同じ原本から違う建物が出る。それは原本ではない」。§5.6-3 は「**参照実装を持ち、検査で回す。参照実装は見た目を持たない**」。[spec/scope.md §6](../../spec/scope.md) は `derive(model): Form` を名指しで約束し、§8 は「導出規則」を 1.0.0 が凍らせる八つの面の一つに数えている。

**その `derive` は存在しなかった。**形は消費者ごとに組み立てられていた。

| 消費者 | 何を呼んで、何を自分で決めていたか |
|---|---|
| `src/draw/plan.ts` | `segmentsFor` `placeOpening` `columnsFor` `runDrawsForLevel` を呼び、壁厚・欠き取りの深さ・扉の吊元・軌跡の掃き方向を自分で決める |
| `src/draw/axo.ts` | 同じ部品を別に呼び、壁厚・階高・手すりの厚みと高さを**別のリテラルで**決める |
| ugatsu `PlanView.tsx` | 同じ部品をまた別に呼び、壁厚・欠き取りの深さ・扉の吊元を三度目に決める |
| ugatsu `three/buildScene.ts` | 同じ部品を四度目に呼び、階高・開口の高さと窓台・壁を開口で割る規則を**そこだけで**決める |

部品は共有されていても、**組み立ての規則は共有されていない。**その結果を実測すると、こうである。

| 事実 | 実測 |
|---|---|
| 上部吹抜けの投影 (`type:void` の境界から下階の平面に落ちる形) | 同梱例に **11 件**あるものが、ugatsu の平面から**一つも出ていなかった** (`PlanView.tsx` が void 境界を丸ごと捨てていた) |
| 最上階の壁の上端 (階高の残余) | koyu は `(l.h ?? 2400) + (l.slab ?? 0)`、ugatsu は `l.h + slab` か室の天井高。`slab:150` だけがあり空間に `h:2700` を書いた最小例 (check は緑) で **2550 と 2700 に割れた** |
| 壁厚の既定 100mm | `plan.ts` の名前つき定数・`axo.ts` の裸のリテラル・ugatsu の二箇所 — **四箇所に別々に**書かれていた |
| 開口の z 範囲 (高さ 2000/1200・窓台 800) | **ugatsu だけが持っていた。**koyu に対になる規則が無く、台帳にも既定が無い |
| 斜めの線分に載る開口の帯 | koyu にはあり、ugatsu には無い。同梱例に斜めの線分は 49 本あるが、その上の開口は 0 件なので未観測のまま |
| `air:1` の天端高 1100mm | 両者が同じ数を持っているが、台帳 (`ATTR_LEDGER.boundary.h`) に既定は無い。**偶然一致しているだけで、契約ではなかった** |

そして core 自身が見た目を返していた。`RunDraw.arrows[].label` は `"UP"` / `"DN"` という**文字列**であり、`RunDraw.notes[].text` は `` `17段 蹴上176/踏面300` `` という**日本語の注記**である。scope.md §6 が「参照実装は色も書体も線幅も注記文字列も返さない」と書いているその面が、注記文字列を返していた。`breaks` は切断の位置ではなく**作図慣習の平行な二本の斜線**を返していた。

許容値も散っていた。`poly.ts` の `EPS` と `graph.ts` の `EPS` は同じ 0.5 を別々に持ち、`vertical.ts` は 1 を四箇所に直値で書き、`drawnShare` は軸平行の判定に定数ではなく直値の 0.5 を使っていた。値は揃っているので事故は起きていないが、**一つを動かしたときに何が動くのかを誰も言えない。**

**この状態で「導出の一致」を凍らせることはできない。**検査する対象が無いからである。

## 決定

**`derive(model, {cut?}): Form` を立て、形の唯一の入口にする。規則は [spec/derivation.md](../../spec/derivation.md) が持ち、`derive` はその参照実装である。**

**1. `Form` は見た目を一つも持たない。**返すのは座標・厚み・z 範囲・向き・**対象の同一性**だけである。色・書体・文字寸・線幅・線種・注記の言葉・作図の記号・縮尺・紙面の余白・描く順序・陰影は、一つも入らない。この線引きは [derivation.md §7](../../spec/derivation.md) が持ち、`test/derive.test.ts` が機械で縛る — 同梱例の `Form` を JSON にして、色の綴りも `UP`/`DN` も一つも現れないこと、ASCII を超える語は同一性のキー (パス・型・名) にしか乗らないことを検査する。

**2. 既存の部品は捨てず、その上に組む。**`segmentsFor` `placeOpening` `slabs` `columnsFor` `verticalRuns` `runSolids` `runDrawsForLevel` は公開面に残り、`derive` はそれらを呼んで組み立てる。**捨てたのは組み立ての重複であって、部品ではない。**

**3. 壁は「開口で割られた区間の列」として返る。**`FormBoundary.material.panels` が全高の区間・腰壁・垂れ壁を持つ。これで「壁の黒帯を紙の色で塗り潰して穴に見せる」という操作が消える — その定数が koyu で `t+30`、ugatsu で `t+40` に割れていたこと自体が、**形の欠落を見た目で埋めていた証拠**である。斜めの線分でも同じ規則が効く。

**4. 開口の z 範囲を Form が持つ。頭をまぐさ高に揃える。**扉は床から立ち上がってまぐさ高 (2000mm) に達し、それ以外の開口はまぐさ高から高さのぶん (既定 1200mm) 下がる。窓台は**頭を揃えた結果として決まる** — `sill` は運搬層なので core は見ない ([scope.md §7](../../spec/scope.md))。既定の場合の窓台は 800mm となり、ugatsu が黙って埋めていた数と一致する。**台帳は動かさない**ので言語の版も動かない (§5 参照)。

**5. 階高は屋根の頂点に揃える。**「上のレベルがあればその差、無ければその階の最大天井高 + 屋根版の厚さ」。上が無いときに屋根の頂点へ揃えるのは、`slabs()` の屋根が同じ式で架かるからである。**天井高が一つも決まらなければ階高も決まらず、そのレベルには壁も柱も立たない** — 2400 のような既定を捏造しない。SUF01 が既に error として「作れない」を言う。

**6. 平面は「分類つきの2Dエンティティ集合」として持つ。**平面は純粋な断面ではない — 扉の軌跡・上部吹抜けの投影・切断線・下りる走りは、立体をどれだけ正確に切っても出てこない。消費者に「立体から切れ」と言えば、この四つを各自が発明することになる。上部吹抜けの投影は実際にそうして 11 件落ちた。分類は `cut` / `below` / `above` / `swing` / `anchor` の五つで、各エンティティが (幾何・分類・対象の同一性) を持つ。**切断高さは Form の入力であって中身ではない。**

**7. core から注記文字列を剥がす。**`RunArrow.label: string` を `up: boolean` にし、`RunDraw.notes[].text` を `anchor` (座だけ) にし、`breaks` を「走りの幅いっぱいを横切る一本の線分」にした。段数も蹴上げも踏面も勾配も `VerticalRun` が既に数として持っており、**言葉にするのは描画側である**。これは規律の側の問題でもあった — 「機械が読む面はすべて英語である」と決めているのに、公開 API が日本語の文字列を返していた。

**8. 許容値を一箇所に集める。**`src/core/tolerance.ts` が `EPS` `AREA_EPS` `PROBE` `SPAN_EPS` `CROSS_EPS` `PARALLEL_EPS` `POINT_EPS` を持ち、`poly.ts` `graph.ts` `vertical.ts` `fabric.ts` がそこから読む。値は一つも変えていない。台帳は `TOLERANCES` で、[derivation.md §6](../../spec/derivation.md) の表はその写しである。ついでに、`vertical.ts` に死んだまま残っていた検証の閾値 (`TREAD_MIN` / `STEP_RULE` / `ESCALATOR_SLOPE` — 実体は `src/validate/runs.ts` にある) を削った。**凍る領域に判定の閾値を残さない** ([ADR-0032](0032-three-domains.md))。

**9. `src/draw/` は `Form` を描くだけにする。**`svgPlan` も `svgAxo` も `derive(model)` を呼び、そこから先は色と線種と言葉だけを決める。`plan.ts` に形の規則は一つも残っていない。副産物として、軸測図の壁が開口で割られるようになった (以前は開口を無視した角柱だった)。

## 代替案

**消費者が部品を呼び続ける (現状維持)。**`segmentsFor` も `placeOpening` も既に共有されているので、あとは「規則を spec に書き下せば揃う」— という筋である。**揃わない。**部品が共有されていても組み立てが共有されていないことが、上の表の 11 件と 150mm と四箇所の 100mm である。そして仕様だけを厚くしても、それが実装と一致していることを検査する対象が無い。scope.md §8 が凍らせると言っている「導出規則」は、検査できないかぎり約束ではない。

**描画ごと core に入れる。**`svgPlan` を core へ移せば形も見た目も一箇所になる。だが scope.md §1 の三領域が壊れる — 描画は「大きくなる・汚くてよい・凍らない」領域であり、core は「小さい・きれい・凍る」領域である。SVG の体裁・寸法線・建具の作図表現・勾配屋根の見え方は、これから精度を上げていく面であって、凍らせる面ではない。**混ぜれば汚さが core に染み出して凍る。**

**`Form` を IFC のような交換形式にする。**外部形式として設計すれば、消費者は言語から独立できる。棄却する理由は三つ。(a) 往復互換を作らないと決めてある ([scope.md §10](../../spec/scope.md))。(b) 交換形式は語彙の網羅を求め、「カバー率は価値ではない」という方針 §12 と正面から衝突する。(c) `Form` の値打ちは**対象の同一性を保ったまま形を返すこと**にあり、原本のパスと uid をそのまま持てる型でなければならない。外部形式へ写した瞬間にその紐が切れる。IFC への一方向の出口は core の外に置く ([roadmap](../roadmap.md))。

**開口の z を Form が持たない (消費者に任せる)。**そうすれば台帳にも導出にも新しい数を足さずに済む。だが scope.md §6 の「複数あってよいのは見た目であって形ではない」と正面から衝突する — 3D の開口は形である。実際いま、その数は ugatsu だけが持っている。**四つ目の道 (一つの消費者が黙って埋める) を通り続けることが最も悪い**ので、規則として書き下した。

**開口の高さ・窓台を台帳 (`ATTR_LEDGER`) の既定にする。**`opening.h` に既定 2000 を、`sill` に既定 800 を宣言する道もある。棄却したのは、それが**言語の意味論の変更**になり、版が動くからである ([ADR-0017](0017-language-versioning.md))。そして `sill` は運搬層であり、core が見た瞬間に層が変わる ([ADR-0033](0033-attribute-tiers.md))。**台帳が定めるのは「何を書いてよいか」であり、導出の定数が定めるのは「書かれなかったときに何を導くか」である。**この二つを分けたことで、壁厚 100mm も同じ棚に収まった。

## 帰結と代償

**代償1: `RunDraw` の形が変わった。**`RunArrow.label` が `up` になり、`notes` が `anchor` になり、`breaks` の中身が二本の斜線から一本の切断位置になった。これは公開面 (spec/scope.md §8 の八番目) の破壊的変更である。rc の段でしか払えない代償なので、いま払った。

**代償2: `Form` は大きい。**同梱例で最大のもの (`examples/twin`) は境界の線分が 5,305 本、壁の区間が 8,082 枚、開口が 1,380 個ある。`derive` は毎回ゼロから組み立てるので、消費者が階ごとに呼べば同じ計算を繰り返す。いまは十分速いが、キャッシュの層が要る日は来る。**その日に足すのは消費者の側であって、規則の側ではない。**

**代償3: 平面の分類が増えた。**`class` が五つに割れたので、描画側は「何を描き、何を描かないか」を自分で決めなければならない。以前は `svgPlan` が全部を塗っていた。ただしこれは代償というより**押し戻し**である — 垂れ壁 (切断面より上) を塗るかどうかは見た目の判断であり、いままでは判断していないふりをして塗っていた。

**代償4: 実装にあった欠陥は、直したものと、直さずに書き下したものがある。**

直したもの — 扉の開く向きが `into.rects` (書かれた割付) を読んでいた箇所を `regionOf(into)` (導出された形) に揃えた (他の全ての導出は形を読む)。`air:1` の平面が厚みを持たず開口で切れなかった箇所は、区間の列になったことで自然に切れるようになった。

書き下したもの — 描かれた線が絡む四つの不整合 (外皮を切る線で `boundary` の a に領域を持たない空間を書くと残す側が反転する / 線の端点の書き順が `at:` の起点を決めるのに正準JSONは書き順を正規化する / `line` を持つ境界の宣言順で導出面積が変わる / LIN03 が実際に切った線に「何も切っていない」と誤報する) は、**この段では直していない。**どれも「どちらを正とするか」の判断が要り、正準JSONの照合順や診断の母集団まで届く。`derive` はいまの振る舞いを忠実に写しており、ゴールデンがそれを固定している。**直すときは、この四つを一つの ADR で扱う。**

**帰結 (追記): `src/draw/` の載せ替えが済んだ。**`svgPlan` と `svgAxo` は `Form` を描くだけになり、形を組み立てる部品 (`segmentsFor` `placeOpening` `placeBand` `slabs` `runSolids` `verticalRuns` `runDrawsForLevel` `columnsFor` `regionOf` `levelsSorted`) を一つも引かなくなった。`WALL_DEFAULT_T = 100` は `WALL_T` として core の台帳へ移り、描画側に導出の定数は一つも残っていない。この二つを `test/draw.test.ts` が import を実際に読んで縛る。

**芯線から実体を起こす規則も core が唯一の実装を持つことにした** — `thicken` / `bandLine` / `band` / `columnRect` / `runPrism` (spec/derivation.md §7.1)。`Form` が持つのは芯線と厚みと z なので、そこから四辺形や角柱を起こす規則が消費者ごとに書かれれば、部品を共有していても組み立ては共有されない。実際、`thicken` は `derive.ts` と `axo.ts` に同じものが二本あり、傾いた版の四隅の高さは `axo.ts` だけが知っていた。平面の区間は**足あと (四辺形) と芯線の両方**を持つようにしたので、手すりを一本の線で描く側が四辺形から芯線を復元する必要も無くなった。

**載せ替えで一件の欠陥が出た。**軸測図の外接範囲を `Math.min(...pts)` で取っていたため、壁が開口で割られて区間ごとに一片になった時点で引数の数がスタックの限界 (12万強) を超え、`examples/twin` の軸測図が `RangeError` で落ちていた。畳んで取るように直し、`test/draw.test.ts` が同じ規模の模型で縛る。**「見た目は自由に変えてよい」ことと「落ちてよい」ことは別である。**

**載せ替えの前後で形は動いていない。**同梱例 9 本 × 全レベルの平面 98 枚について、載せ替え前 (ADR-0040 以前) と後で「最後に黒が残る領域」を、座標圧縮した格子の上で描き順どおりに塗り重ねて突き合わせた。77 枚が完全一致し、残る 21 枚 (`examples/complex` の全レベル) の差は合計 58.8 px² — 総塗り面積 22,924,265 px² の 260 万分の 1 である。その差の正体は一箇所の 8mm × 140mm の欠けで、**旧来の欠き取り (厚み `t+30` の紙色の帯) が直交する壁の隅へはみ出して抉っていたもの**である。載せ替え後はそこに壁が残る。壁以外の差は 61 枚の切断線 (二本の斜線が同じ枠の中で逆に傾いた — 作図慣習) と 2 枚の手すり (開口で割れるようになった) だけで、いずれも見た目である。

**帰結: 「導出の一致」が初めて検査できる面になった。**`test/derive.test.ts` が同梱例の `Form` の指紋を固定するので、形が動けば落ちる。spec の定数表と許容値表は実装の台帳の写しであり、片方だけ動けば落ちる。ugatsu が `derive` を呼ぶようになれば、koyu と ugatsu が同じ形を出していることは**呼び出しが一つであることそのもの**で保証される — 検査で確かめる必要すら無くなる。
