# ADR-0019: 位置と線 — 位置を書くのをやめ、寸法と並びを書く

日付: 2026-07-25 / 状態: 採用 (v0.11、言語版0.3) / 起点: 外部レビュー§3.2・§4.8 ([docs/reviews/](../reviews/))、[根底の再検討](../reviews/2026-07-25-foundation-rethink.md)

## 文脈

原稿と README は「形はソースではなく生成物である」と言う。外部レビュー§3.2 はここに距離を見た — ビルドが計算するのは壁線分・接合・面積・図であって、**空間の矩形領域そのものは原本に直書きされている**。P0-12 は文言を校正して距離を認めた (README は今「原本に書かれるのは空間の領域と境界の関係」と言う)。これは現在形の正確な記述だが、自己定義として固定すれば中心主張の静かな放棄になる。

同日の設計対話が同じ点を別の角度から突いた。**グリッドが座標より賢いのは共有されている時だけである。** 参照が一度しかないオフセットは座標の変装であり、通り芯が X・Y 一本ずつまで痩せた極限では `X1+3200` は座標指示と完全に等価になる。「直交グリッドに絞ったから形を書かずに済んでいる」だけなら、主張は制約の効果を語り直したものにすぎない。

敷地なりの斜めを `clip:site` で導出する案は、この批判への応答として提出され、却下された — **ビルドしないと斜めと分からないソースは、読みの原則に違反する**。ここから線引きが得られた (決定1)。そして対話は「オーサリングは対象外だが、設計する人の思考は対象である。人は空間を区切る線を描くことで曖昧な境界を実体のものとする。それが設計である」に着いた。

**批判の正体は「位置か寸法か」だった。** `X2+1600` は位置 (原点からの距離) であって、設計者が決めたもの — 寸法 — ではない。決めているのは「水回りは1600」「廊下は1800」「残りが LDK」であり、位置はそれを並べた帰結である。付け焼き刃感の出どころはここにある。

## 決定

**1. 読みの線引き。** **構成に属する事実はソースに書かれ、幾何に属する事実はビルドが導出する。** 構成 = どの空間があるか・何と接するか・境界が斜めか・どこからどこへ。幾何 = 頂点座標・面積・壁線分の位置。導出化 (幾何を muro から出す) と可読性 (構成を muro に残す) は矛盾しない — 対立して見えたのは clip 案のように**構成の事実を幾何側に隠した**ときだけである。

**2. 位置の原理 — 位置を書くのをやめ、寸法と並びを書く (このADRの中心)。** 原理は一文になる: **垂直の矩計 (順序+寸法の積み上げ) を水平へ拡張する。**

診断を本文に残す。オフセットは位置であって寸法ではない。そして**Revit は寸法を入力させ、座標を保存する** — 仮寸法に打った1600は入力補助として消え、モデルに残るのは壁の配置と形状という結果である (ロックした寸法・EQ拘束は座標の上に後付けされる第二の層で、脆く、実務で多用されない)。IFC に出せば `IfcWall` は配置と形状だけを運ぶ。帰結は日常に現れている — 半年後に「水回りは1600だったか」を確かめるには、自分が設計した建物を測るしかない。**自分で書いた数字を成果物から測り返している。**

原稿の論法がここで一段完成する。CAD は図面の線を捉えて読みを捨てた。BIM は意味を持たせて**寸法という行為**を捨てた。どちらも入力を捨てて出力を保存している。**BIM は寸法を入力させ座標を保存する。koyu は寸法を保存し座標を生成する。** 系として「往復互換を捨てる」方針の意味も変わる — IFC から本当に戻したいのは捨てられた入力であり、入力の側を原本にするなら復元する対象がそもそも無い。我慢ではなく不要になる。

そして**水平だけが取り残されていた**。垂直方向の koyu は既に寸法で書かれている (`level L1 0 h:3600 slab:600` — `levels` が出す矩計は天井高と床組み厚を積み上げた帰結であり、位置は導出されている)。ADR-0014 が「垂直は既定が床なのに水平は全部宣言」という非対称を直したのと**同じ形の非対称が、位置の層にもう一つ残っていた**。

導出の規則は**一方向・順序付き・決定的** (スプレッドシート的) とする。**制約ソルバーは採らない** — 双方向拘束は充足不能と多解の沼であり、LLM が書けば壊れる。パラメトリック CAD の果実 (編集の伝播) だけを取り、代償 (多解・脆さ) を払わない。**過剰決定 (寸法の合計が帯を超える) と不足 (残りを吸収する要素が無く足りない) はどちらもビルド (parse) のエラー**であり、`check --json` では SYN01 として現れる。**新しい診断コードは切らない。** 理由は決定4から出る — 帯は parse 時に展開され、check の時点では存在しない。check に見せるには帯の由来を `Space` か `Model` に持たせることになり、「帯は正準JSONに残さない」を破る。koyu の分担は「parse は形、check は整合」であり、破れた帯は矩形を一つも作れない = 形の問題である (`parseRegion` が `領域の幅がゼロです` を parse で投げるのと同じ族)。代償は、帯の算術エラーがコード無しの SYN01 になり、ADR-0016 の「エージェントはコードで分岐する」が帯には効かないことである — 本文 (帯幅・合計・差分・各要素の寸法) で補う。

**残りを吸収する要素 (`w:rest`) は帯に高々一つ**とし、**全要素に寸法を書いて合計を照合する「閉じた帯」を既定**とする。`rest` を既定にしない理由は、このADRが決定2で自ら述べている — 寸法は決定であって減らす対象ではない。`rest` は設計者が決めた寸法 (4800、1600) を一つ消す。加えて `rest` は検出を殺す: `w:4800` を `w:480` と打ち間違えても隣が吸収して `✔ 整合` が出る (位置で書いた版なら同じ誤りが BND04 ×8 で捕まった)。閉じた帯なら同じ誤りが「合計が 4320mm 足りません」になる。図面の「部分寸法の合計 = 総寸法」と同じ検算であり、代償は数字二つである。`rest` は残りが設計判断でないときの例外語彙として残す。


**依然として書かれるもの**を正直に線引きする: 通り芯の座標 (最初の錨。構造グリッドは共有されるので名前を持つ線として書かれて正しい) / **寸法そのもの** (1600 は決定である — 減らす対象ではなく、置き場所を位置から要素へ移すだけ) / 所与 (敷地形状、ADR-0011) / 帯に乗らない位置 (雁行の出入り等) と構成の事実 (斜め)。**減るのは「原点からの距離」だけである。**

**3. 線の三出自。** 位置を定めるものを線として見ると、出自は三種しかない。

- **共有線** — 通り芯・副芯。名前を持ち、宣言一回・参照N回。**グリッドは記法の土台ではなく、共有線という特殊例である。** 「設計者は通り芯から考えない」という違和感の正体は、特殊例を土台と偽っていたことにある。
- **所与線** — 敷地 polygon の各辺。世界から来る。
- **描画線** — 設計の行為そのもの。一つの設計判断が一行になる。

**境界は位置を持たない関係の層のままである** (ADR-0001 以来の核。ここに指一本触れない)。線はその**実現**であり、隣接からの導出が既定で、描かれたときだけ上書きされる。オントロジーの言い直しとしては、**空間が名詞、線が動詞、境界はその出会い**である。

レビュー§4.8 (共有辺・重なり・面積・敷地判定・図面生成が矩形代数へ直接依存する。Core を geometry backend から分離せよ。非直交はコーパスが要求するまで実装するな) との関係を明示する: **三出自はレビューの言う Layout 層の意味設計であり、§4.8 はその実装戦略である** — 競合しない。レビューは器の分離を求め、この ADR は器に入れる中身を決める。

**4. 今実装する範囲は、直交にも効く部分に限る。** **主役は帯 (`band`) と寸法による導出**である。帯 (一次元の並び) を宣言し、寸法で埋める:

```
band X X1+3200..X2+3200 Y1+4000..Y2        # 帯: どの範囲を、どちら向きに割るか
  space /L3..L10/A/wet  wet  w:4800 name:水回り
  space /L3..L10/A/hall hall w:1600 name:玄関
```

現状の tower は同じことを `X1+3200..X2+1600` / `X2+1600..X2+3200` と位置で書いている ([examples/tower/typical.muro](../../examples/tower/typical.muro))。消えるのは設計判断ではなく**判断の帰結**である。これはオフセット批判への直接の答えであり、矩形の区間代数の中で完結するので arrangement 計算も証拠待ちも要らない。**ソルバーではなく足し算である。**

字句の選択は設計時の草案から四点変わった。**キーワードは `chain` ではなく `band`** — 本文が一貫して「帯」と呼んでおり、koyu のキーワードは宣言する対象を名指す名詞であり、そして `chain` は寸法拘束CAD (chained constraints) の語彙、すなわち決定2が明示的に棄却した機構の名だからである。**割る向きは `dir:X` ではなく第1位置引数** (`grid X 0 6400 …` と同じ綴り方) — これにより帯の行は位置引数だけになり、`key:value` を持たない。帯はモデルに残らないので属性の運び先が無く、この形が将来の属性追加そのものを封じる。**子行は裸のパスではなく字下げした `space` 行** — 裸のパスで始まる行は言語で唯一キーワードの無い行になり、§1 の字句規則に反する。**残りの印は裸の `rest` ではなく `w:rest`** — `parseAttrs` は `key:value` でない末尾トークンを弾くので裸の `rest` は字句規則の例外になる。

**あわせて `space` 行に `w:` を書くことを禁じる。** これが無いと、帯の要素が字下げを失ったときに「領域を持たない空間」として黙って成立し、その室は全ての図から消え、`w:1600` は自由属性として正準JSONに漏れ、`check` は緑のままになる。既存コーパスに `w:` を持つ `space` 行は一本も無いので、この予約は無償である。

**実測 (このADRの唯一の測度)。** tower の A タイプを帯で書き直すと、**原点からの距離を含む通り参照が 10 個から 4 個へ (−60%)**、寸法が 0 個から 4 個へ、二行にまたがって一致させ続けねばならないトークンが 3 対から 0 へ、導出される矩形の辺が 0/16 から 4/16 へ変わる。行数は 4 行から 6 行に増える。**このADRが名指しで批判した `X2+1600` は原本から消え、その 1600 はそれを決めた要素の上へ移った。**

**副芯の命名** (`axis X2a X2+3000` — 名前を持つ共有線) は副産物として同梱してよいが、**これ単体ではオフセット批判への答えにならない** — 共有の話しかしていないからである。第一波には入れなかった。

**帯にできるものの基準 (実装して分かったこと)。** tower で帯として素直なのは二つだけで、どちらも二要素の閉じた帯である — 西列 (洋室2 2400 / 洋室1 3200、`dir:Y`) と玄関側 (水回り 4800 / 玄関 1600、`dir:X`)。**LDK はどちらにも入らない** — L字だからではなく、玄関側の帯は `Y1+4000` より北にあり LDK は南にあるからで、記法をどう変えても入らない (入れれば `/Lk/B` の領域と重なる)。バルコニー列は算術的には綺麗な三要素の帯だが、**帯にしてはならない** — その切り位置 `X3` (コーパス内60参照) と `X4+3200` (17参照) は A|B・B|C の戸境壁の延長、すなわち決定3の**共有線**であり、`w:12800` に潰すと通りが消える。対して `X2+1600` の参照はちょうど2つ、どちらもその帯自身の要素である。**参照が帯の内部で閉じている切り位置だけが内部の切り位置であり、帯にしてよい。** これが基準である。

**4b. 導出される切り位置の綴り (床規則)。** 帯の両端と直交方向の両端は書かれた綴りをそのまま使い、内側の切り位置だけを綴る。規則は「その座標**以下**で最も大きい通り芯からのオフセット」である。実測: tower のコーパスではこの規則が**100%** 一致し、examples 全体では 588 箇所中 7 箇所 (すべて `mansion.muro` の `Y2-600` / `Y2-1800` — 北の壁から**逆向きに**測った書き方) が食い違う。構造的に言えば、**この規則は先頭の通り芯より手前を除いて負のオフセットを決して生まない**ので、逆向きに寸法を書く著者は 1.2% ではなく 100% 食い違う。よって意味保存の保証には範囲がある — **順向きに寸法された帯は綴りまで一致し、逆向きに書かれたファイルは幾何が同一のまま `± 領域` として diff に現れる。** mansion.muro を第一波で書き換えないのはこのためである。

**5. 描画線は判断のみ記録し、実装は証拠待ちとする。** 記法の方向は `boundary /a /b` 配下の `line X3Y1..X4Y3` (端点はグリッド語)、所与なりは `line site.3` (境界の側で可視 — clip の修理)。**角度と生座標は導入しない** (RLVR 知見: 座標を持たせると LLM が壊れる)。実装条件は「コーパスが設計された斜めを実際に要求したとき」であり、その時は geometry backend の分離 (§4.8) を先に行う。矩形区間代数→arrangement の全面書換えが現存する最大の実装コストであり、要求の無いうちに払わない。

**自己修正を記録する**: この議論は「設計された斜め」を出発点にしたが、計画中のコーパス (basement / mixed / megablock) を見ると、設計された斜めを実際に要求する実例は一つも無い — 地下が要求するのは斜路 (垂直の話)、中間規模・特大が要求するのは所与の斜め (敷地・隅切り) までである。**斜めは発見の契機であって本体ではない。** 線の議論の本体は、グリッドの再解釈 (共有線への降格) と導出の導入 — 直交の建物に今日から効く部分 — である。

## 代替案

**文言の校正で終える (現状維持)。** P0-12 の記述は正確だが、これを終着にすると中心主張の静かな放棄になる。校正は「今の実体の正確な記述」であって「目指す実体の宣言」ではない — この区別を失わないことがこの ADR の第一の目的である。

**生座標・角度の導入。** 位置を素直に書けるようにするのは最短だが、方向が真逆である。間取り生成の RLVR 研究 (arXiv 2605.14117) は座標付き JSON を LLM が安定生成できないことを示した — ソースから数値を減らす側に立つ。

**制約ソルバー (双方向拘束)。** パラメトリック CAD の完全形だが、充足不能・多解・順序依存の沼であり、LLM が書けば壊れる。決定2で明示的に棄却する。編集の伝播という果実は一方向の足し算で足りる。

**arrangement の即時全面実装。** 描画線を今すぐ実装する案。証拠が無いまま現存最大の実装コストを払うことになり、レビュー§4.8 の規律にも反する。

**clip 案 (敷地なりの斜めをビルドで導出する)。** 構成の事実 (斜めであること) を幾何側に隠し、読みの原則を破る。決定1の線引きはこの失敗から得られた。

**言語版による字句のゲート (`band` を 0.3 未満で禁じる)。** 三つの検討案がこれを求めたが採らない。koyu は**どのキーワードにも字句の版ゲートを持たない** — `koyu 0.1` のファイルで `zone` を使っても診断は出たことがない。`band` にだけ設ければ、純追加のリリースに新機構を密輸することになる。加えて実装できない: check に置けば `DIAGNOSTIC_CODES` と semantics.md を触ることになり (下流無変更に反する)、parse に置けば `koyu 0.2` が `import` の後に来てよい以上、合成順に依存する。全キーワードを対象にする別のADRか、さもなくば無し、である。

**`src/graph.ts` の `Band` / `placeBand` を改名する。** 帯というキーワードと、境界線分上の区間を意味する既存の公開API名が衝突する。だが `placeBand` は spec/tools.md に載る公開APIであり、純追加を謳うリリースで道具の表面を壊すのは筋が悪い。二つの意味は次元が一つ違うだけの同じ概念であり、記法の書き手が TypeScript の名に出会うことはない。tools.md に一文で区別を書くにとどめる。

**帯を「空間の糖衣構文」として parse 時に潰さず、モデルに残す。** 下流 (check/plan/graph/diff) が帯を知る必要が生じ、正準JSON にも出ることになる。展開後を通常の空間にする方が小さく、「帯で書いた版」と「位置で書いた版」の semantic diff が空になるという検証手段も手に入る (ADR-0014 決定3と同じ流儀)。

## 帰結と代償

「原本に書かれるのは決定であり、幾何は帰結である」が、言い訳なしで言えるようになる。校正された現在の文言は防御であり、導出化された後の文言は攻撃である。

**代償は読み取りコストである。** 導出はソースから数値を消すため、「事務室の東端はどこか」を即読できなくなる可能性がある — 数値の書き間違いは減るが位置の読み取りは増える。**どちらが勝つかは事前に決められない。** よって baseline eval (言語0.2・tower) を先に走らせ、0.3 との前後比較で測る。悪化したら導出の適用範囲を縮める。

**可逆に設計する。** 帯と既存のオフセット記法を併存させ、どちらで書くかを強制しない。0.3 は純追加構文なので、0.2 は無条件で意味保存受理される (ADR-0017 の判定可能条件を自明に満たす)。

**tower の書き換えで実測した意味保存の範囲 (正直に開示する)。** 正準JSON は**バイト同一**、`koyu diff` は**差分なし**、`levels` / `site` / `doors` / L1・L2・L11 の平面SVG も**バイト同一**である。一方 `stats` / `light` / `graph` と L3〜L10 の平面SVG は、**集合としては同一だがバイト列が違う** — 帯が要素を幾何順 (南→北) に並べるため、洋室2 と 洋室1 の**出力上の並び順が入れ替わる**。バイト長は一致し、行をソートすれば完全一致する。正準JSON と semantic diff は順序不変なので保証には触れないが、ADR-0014 の「全出力バイト一致」より一段弱い実測であることを隠さない。**帯は宣言順が意味を持つ最初の構文である** — 正準性の property test が行を並べ替えて不変を検査していることとの関係上、この事実は記録しておく必要がある (帯の要素は並べ替えてはならない)。

**測度を一つだけ持つ** (根底再検討§2.5): 展開後モデルの位置決定のうち、ソースに数値が書かれているもの (通り参照+オフセット) と導出されるもの (幅・比・残り・所与線) の比。現状、後者は0である。**これは観測であって目標ではない** — 上げること自体を完了条件にすると、読めない導出を書く動機になる。

**変えないものを再確認する**: 境界は位置を持たない関係の層 / 一行一文 / パスはアドレスと集計 (uid は長期 join、ADR-0015) / check の門番 / 依存ゼロと小ささ / 一棟が一つのコンテキストに入ること / 解像度は基本計画レベル — 導出化は解像度を上げる方便ではない。

**残る危険**: 描けるなら何でも描く、に流れると座標の変装が線の変装に変わるだけである。描画線を実装する段では「**描画線の本数 = 設計判断の数**」を規範として持つ。
