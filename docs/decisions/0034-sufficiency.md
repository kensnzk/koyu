# ADR-0034: 充足性の検査 — 形を作るのに必要な情報が揃っているか

日付: 2026-07-27 / 状態: 採用 (v1.0.0-rc.1) / 起点: [方針の総覧](../policy.md) §5.6-2・[spec/scope.md §6](../../spec/scope.md)

## 文脈

方針 §5.6-2 は「**充足性を検査する。**形を作るのに必要な情報が揃っているかは、構造の整合の一部である。妥当性の判定ではなく、完全性の検査である」と書く。[spec/scope.md §3.1](../../spec/scope.md) は「形を作るのに必要な情報の充足」を**保証するもの**の表に載せ、診断の欄に `SUF01-04` と書いてある。

**実装にその検査は無かった。**書かれていたのはコードの綴りだけで、`DIAGNOSTIC_CODES` に `SUF` で始まる行は一つも無かった。

実測すると、こうなる。

| 測ったもの | 結果 |
|---|---|
| `examples/two-rooms.muro` の `check` | 診断 **0件** (緑) |
| 同じファイルの `slabs()` | 天井2枚・屋根2枚・**床0枚** |
| 同梱例 15件のうち、いまの規則で SUF が出るもの | **12件** (SUF01 が24件、SUF03 が11件) |
| 同梱例のうち、床が一枚も生成されないもの | **5件** (`two-rooms` と `guide/start.md` の第1〜4段) |
| guide と README の muro ブロック 250件のうち、天井高が決まらない空間を持つもの | **134件** |
| 同じ250件のうち、`slab` の無いレベルを持つもの (床が一枚も出ない) | **210件** |

教材の大半と同梱例の大半が「形の作れない原本」であり、`check` はそれを一言も言わなかった。**緑の意味が spec の定義とずれていた** — 方針 §11-5 が 1.0 の前提条件に名指した「書いたものが黙って消える経路」の一種である。ここでは書いたものが消えるのではなく、**書かなかったものが黙って消える**。

そして既存の四つのコードが、この一つの話を別の族の名で少しずつ言っていた。

| コード | 本文 | 実際に言っていること |
|---|---|---|
| HGT03 | 上階に slab が未宣言で高さ検査ができません | 立式に要る値が書かれていない |
| HGT04 | 天井高が不明で高さ検査ができません | 同上 |
| HGT05 | レベルが特定できません | z が書かれていない |
| RUN04 | 上にレベルが無いため形が生成されません | 形が一つも出ない |

どれも「不変量が破れている」という報せではない。**値が足りない**という報せである。HGT01/HGT02 が「書かれた値が矛盾している」を言うのに対し、この四つは「値が書かれていない」を言っていて、族が違う。

## 決定

**充足性を族として立てる。SUF01-04 を新設し、上の四つをここへ畳む。**

| コード | severity | 母集団 (書かれた宣言) | 形の帰結 |
|---|---|---|---|
| **SUF01** | **error** | 領域を持ち、吹抜けでも外部でも半屋外でもない空間の天井高が決まらない (空間の `h` も所属レベルの `h` も無い) | 押し出す高さが無く、**天井も屋根も生成されない** |
| **SUF02** | **error** | 領域を持つ空間のレベルが特定できない | z が決まらず、**立体が一つも生成されない** |
| **SUF03** | **warning** | 床を持ちうる空間が載っているレベルに `slab` が無い | **その階の床が一枚も生成されない** |
| **SUF04** | **warning** | 縦動線の宣言があるのに形が一つも生成されない (上にレベルが無い) | 段も走りも生成されない |

**1. 母集団は `fabric.ts` の規則と同じ形をしている。**SUF01 が吹抜け (`type:void`)・外部 (`type:exterior`)・半屋外を除くのは、その三つに `fabric.ts` が天井も屋根も架けないからである ([ADR-0024](0024-fabric.md))。バルコニーに天井高は無い。逆に**縦動線 (階段室) は除かない** — 天井は張られない (上の走りに沿って傾いていて一つの面でない。[ADR-0021](0021-vertical-circulation.md)) が、屋根は架かるので、最上階の階段室に `h` が無ければ屋根が FL+200mm に落ちる。

**2. 節は二つ、粒度は走査単位である。**`checkSpaceSufficiency` (領域を持つ空間を宣言順に一周 — SUF01/SUF02) と `checkLevelSufficiency` (レベルを z 順に一周 — SUF03)。**SUF04 は `runIssues` の走査の中に留めた** — 節はコードの族ではなく走査単位で割る ([ADR-0028](0028-diagnostics-per-declaration.md))。族で割れば、一つの空間が出す RUN02 と SUF04 が他の空間の診断で分断され、並びの契約が崩れる。

**3. HGT03・HGT04・HGT05・RUN04 は欠番にする。**severity はコードの不変属性であり、重さを変えるなら新コードを切る ([ADR-0016](0016-diagnostic-contract.md))。HGT04 (warning) は SUF01 (error) へ、HGT05 (warning) は SUF02 (error) へ、実際に重さが変わっている。畳んだあとの `checkHeights` は「書かれた値が矛盾しているか」だけを見る — 値が無ければ黙って `continue` し、それを言う仕事は充足性の節が持つ。

**4. spec に導出の規則を書き下した。**[spec/semantics.md §3](../../spec/semantics.md) に「床は `slab` だけが与える」「天井は `heff` が与える」「値が無いときに既定値を捏造せず、要素を作らない」を明記した。**規則が決定的だからこそ SUF03 は警告でいられる** — 同じ構成から複数の形が出るわけではなく、出る形が痩せているだけである。

## 代替案

**四つとも error にする。**SUF03 を error にすると、guide の muro ブロック 250件のうち 210件が落ちる。その大半は「床の厚さを教えるより先に、空間と境界と扉を教えたい」段である。そして何より、**形は決まっている** — 「`slab` が無ければ床要素を作らない」は決定的な規則であって、同じ構成から複数の形が出るわけではない。error の条件は「一意な形が作れない」ことであり ([spec/scope.md §6](../../spec/scope.md))、SUF03 はそれを満たさない。ただし黙らせもしない: `--strict` と `npm run gate:examples` は警告も落とすので、**同梱例には `slab` を書き足した**。

**四つとも warning にする。**SUF01/SUF02 を warning に留めれば教材を一行も直さずに済む。だがそれは「押し出す高さが無い」「z が無い」を*疑わしい*と呼ぶことである。立体が一つも出ない記述は疑わしいのではなく、**形が作れない**。緑の定義が「構造層と解釈層について宣言された不変量が成り立つ」を含み、その不変量に導出の契約が入っている以上、warning では定義と実装が再びずれる。

**HGT03/HGT04/HGT05/RUN04 を残したまま SUF を足す。**同じ欠けた宣言に二つの診断が並ぶ。HGT03 の母集団は SUF03 の部分集合であり (どちらも「そのレベルに `slab` が無い」で発火する)、HGT04 の母集団は SUF01 の部分集合である。一つの欠落に二つのコードを吐く台帳は、直す手を二回数えさせるだけである。

**HGT05 の綴りを残す。**HGT は「高さ」の族である。レベルが特定できないのは高さの話ではない — z が無ければ平面図にも現れず、床も壁も出ない。族の名が内容と合っていないコードは、事典の目次から引けない。

**充足性を検証の面 (`koyu validate`) へ置く。**置けない。判定は「その天井高でよいか」を問い、閾値を持ち、建築の判断である。充足性は「天井高が書かれているか」を問い、閾値を持たず、読解の一部である ([ADR-0032](0032-three-domains.md) の線)。spec/scope.md §6 が core の契約として名指している以上、ここに置く。

**言語版を上げる。**上げない。**同じファイルの意味は一文字も変わっていない** — `h` の無いレベルは前も後も「天井高が書かれていないレベル」である。変わったのは `check` がそれを声に出すかどうかだけで、[ADR-0032](0032-three-domains.md) が六コードを検証へ移したときと同じ種類の変更である。

## 帰結と代償

**緑の意味が実装と一致した。**`check` が緑であることが、「構造層と解釈層について宣言された不変量が成り立ち、**かつ書かれた構成から形が作れる**」を意味するようになった。spec/scope.md §3.1 の表の一行が、初めて実装を指すようになった。

**同梱例が実際に床を持つようになった。**`examples/two-rooms.muro` の `slabs()` は、床2枚・天井2枚・屋根2枚を返す。以前は床が0枚だった。

代償は四つある。

**(1) 同梱例と教材を直した。**examples の12ファイルと、guide/README の muro ブロック210件に `h:` と `slab:` が増えた。`guide/start.md` の第1段は4行のまま `level L1 0 h:2400 slab:150` になり、レベルは「高さ0mmに名を置く」だけの行ではなくなった — **立体を作るには階の高さと床の厚さが要る**ことを、最初の4行が言うようになった。教材の最小性は一語ぶん失われ、そのぶん最初から形が出る。

**(2) 診断コードが四つ欠番になった。**HGT03/HGT04/HGT05/RUN04 は再利用しない。同じ綴りが別の意味を持つと、過去の出力が読めなくなる ([ADR-0032](0032-three-domains.md) の代償(2)と同じ規律)。台帳の総数は 63 のまま (四つ落ちて四つ入った)。

**(3) SUF03 と SUF04 は `--strict` を付けなければ通り抜ける。**門番 (`npm run gate:examples`) は警告も落とすので同梱例は守られるが、利用者の CI では `--strict` が要る。床の無い建物が緑で通ることは、警告に留めた以上、選んだ帰結である。

**(4) SUF01 の母集団は `fabric.ts` の実装に依存している。**吹抜け・外部・半屋外を除くという判断の根拠は「その三つには天井も屋根も架からない」であって、それは仕様であると同時に実装でもある。**面の導出の規則を変えるときは、SUF01 の母集団も一緒に動かす** — 動かさなければ、天井高を書き忘れた半屋外が黙って形を失う。

三点セットで着地した: 本 ADR (なぜ) + `test/diagnostics.test.ts` の充足性3件 / `test/guide.test.ts` の節ごとの再現例 (保証) + [spec/semantics.md §3・§5](../../spec/semantics.md) / [spec/scope.md §3.1・§6](../../spec/scope.md) (現在形)。
