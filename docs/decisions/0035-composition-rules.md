# ADR-0035: 合成の六つの規則 — 層に強度を与え、暗黙の解決を残さない

日付: 2026-07-27 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [方針の総覧](../policy.md) §5.2 / 覆す: [ADR-0010](0010-assets-and-composition.md) の「レイヤー強度は不採用」

## 文脈

ADR-0010 は合成を**加算のみ**と定めた。層は空間・境界・ゾーン・アセットを足し、衝突はビルドエラーになる。判断は正しかった — 設計の分担にはまず「黙って上書きされない」ことのほうが要る。ADR-0010 自身が「上書き合成は改修・オプション違いのような差分レイヤーが実際に要求したときに、別のADRとして導入する」と道を残していた。

**要求が二方向から来た。**

第一に**as-built である。**計画の上に実測を重ねるとき、実測は計画を**上書きしなければならない**。加算しかなければ、実測を書くには計画を書き換えるしかない — つまり計画が失われる。「設計の最初から運用の終わりまで、同じ同一性が続く」という目的が、合成の側から塞がれていた。

第二に**凍結である。**1.0.0 が凍らせる八つの面の一つが「合成の規則」であり、方針は六つの規則を挙げている。実測すると、v0.15 が満たしていたのは規則5 (決定性) だけだった。しかもその決定性すら怪しい — `import` の並びを入れ替えると `columns` の先勝ちの結果が変わり、正準JSONのバイト列が変わる。**評価の順序が暗黙のまま意味を持っていた。**

暗黙の解決は、同じ入力から違う結果を生みうる。それは原本ではない。

## 決定

**六つの規則をすべて実装し、[spec/composition.md](../../spec/composition.md) を規範として立てる。**

**1. 層は明示された強度順序を持つ。**`import` 行を深さ優先で平坦化した列が層の順序であり、**後の層ほど強い**。entry は添字0で最も弱い。`model.layers` がこの列であり、`koyu layers` が印字する。

**著者が `import` 行を並べる行為が、強度の宣言である。**方針は「出現順ではなく、宣言された順序」と言うが、この二つはここでは同じものではない — **強度は走査の順ではない**。entry の行が `import` より後ろにあっても entry は添字0のままで、`over` は負ける。順序で決めていたら、`import` 行を上下に動かしただけで結果が変わってしまう。

**2. 単一の値は、最も強い層の意見が勝つ。**`over` を導入した。空間・ゾーン・境界・レベル・アセットを対象にとり、typed field (`type` `t` `air` `edge` `h` `slab`) にも自由属性にも届く。同じ層が同じ属性に二度意見を持つのはエラーである — どちらが勝つかが決まらないからで、これは「暗黙の解決を残さない」の直接の帰結である。

**3. 集合は、明示された編集で合成する。**`over` の直下に `+` (追加) / `-` (削除) / `=` (置換)、そして `drop` (空間・境界・柱の削除)。同一性は「含む対象 + その中で一意な名」なので、`name:` を持たない要素は編集の対象にできない。

**4. 定義と上書きを区別する。**`space` / `boundary` / `zone` / `asset` / `polygon` は**定義**で、重複はエラーである (ADR-0010 のまま)。`over` は**上書き**で、対象が無ければエラーである。

**5. 同じ入力からは常に同じ結果が出る。**入力には層とその順序の宣言を含む。**上書きの跡は機械形式に残らない** — `over` で `h:2400` にした模型と、最初から `h:2400` と書いた模型は、同じ正準JSONを与える。正準形が答えるのは「同じ建物か」であって「どう書かれたか」ではない。

**6. 出所が追える。**`model.attrSrc` が属性ごとに層の添字を持ち、`koyu layers --attrs` が印字する。

## 代替案

**強度を数で宣言する (`import ./x.muro strength:10`)** 案は、順序という既にある情報を二重化する。二つの層が同じ数を書いたときの規則がまた要る。

**別ブロックで順序を宣言する (`layers` ブロック)** 案は、`import` と二重管理になる。宣言と実際に読む層がずれたときに何が起きるかを決めなければならず、そのずれ自体が新しい暗黙になる。

**`over` を作らず、重複を後勝ちにする**案 — つまり ADR-0010 が棄却した案 — は、定義と上書きの区別 (規則4) を失う。綴り違いで同じパスを二度書いた事故と、意図した上書きが、区別できなくなる。

**集合の編集に専用構文を作る** (開口専用の `door-add` など) 案は、方針が明示的に禁じている — 「特殊なのは値の種類であって、規則ではない。専用構文を作らない」。

**`over` で新しい要素も定義できるようにする** (upsert) 案は書き味が良いが、対象の綴り違いが黙って新しい空間を生む。**存在しないものに意見だけを足すのは、たいてい綴り違いか、層の順序の思い違いである。**

**属性ごとではなく層ごとに勝敗を決める**案 (強い層が対象を丸ごと置き換える) は、実測の一属性を足すために全属性を書き直させる。差分を差分として書けるようにするのが目的なので、粒度は属性である。

## 帰結と代償

**as-built が書けるようになった。**計画の層はそのまま残り、実測の層が上に乗る。どちらが何を言ったかは `koyu layers --attrs` が答える。ADR-0010 の保留が回収された。

**`import` の並びが意味を持つことが明示された。**以前もこの並びは `columns` の先勝ちを通じて意味を持っていたが、それは**偶然の副作用**であって規範ではなかった。いま並びは規範であり、テストが縛っている。

代償。**(1) 言語が四語増えた。**`over` `drop` と、字下げの `+` `-` `=`。言語に足すことは高いという規律に照らすと、これは 1.0 で払う最後の大きな支払いである。**(2) 集合の編集には `name:` が要る。**同梱例の開口はほとんど名を持たないので、いま編集の対象にできない。名を書くのは書き手の選択であり、必要になった時点で書けばよい (uid と同じ opt-in の構え)。**(3) 強度が「走査の順ではない」ことは、読んで分かりにくい。**entry に `over` を書いて負けるのは驚きうる。だが `koyu layers` が順序を印字するので、驚いたときに確かめる手はある。

三点セットで着地した: 本 ADR (なぜ) + `test/composition.test.ts` の14件 (保証) + [spec/composition.md](../../spec/composition.md) (現在形)。
