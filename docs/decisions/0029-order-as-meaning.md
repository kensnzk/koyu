# ADR-0029: 順序が意味を持つ配列は並べ替えない — 正準化と差分の非対称

日付: 2026-07-27 / 状態: 採用 (v0.13) / 起点: 正準JSONとdiffの網羅監査 (6視点・所見26件)

## 文脈

ADR-0013 は正準JSONに「同じ構成からは常にバイト同一のJSONが出る」を課し、その手段として
**宣言順に意味の無い配列を内容の正準順に並べる**と決めた。`sortBySerial` がその実装である。
ADR-0018 は意味差分に「行順や綴りの揺れを差分にせず、構成の変化だけを報告する」を課した。

0.5 で三つの語が入った — 柱 (`column` — ADR-0023)、描かれた線 (`line` — ADR-0022)、
地下 (`underground` — ADR-0022)。監査が示したのは、**この三つがどちらの形式にも乗っていない**
ということだった。しかも乗せ方を間違えた箇所が一つあった。

**柱の宣言順は意味である。**同じ通りの交点に二本は立たず、先の宣言が勝つ (ADR-0023)。

```muro
column 900 L1 x:X2      # X2通りに900角
column 500 L1           # 残りの交点に500角
```

この二行を入れ替えると、X2通りの柱が900角から500角に変わる。**別の建物である。**
ところが `toCanonical` は `columns` に `sortBySerial` を掛けていたので、
二つの建物が**バイト同一の正準JSON**になっていた。ハッシュも `koyu diff` も同一と答える。
「diff・ハッシュ・レイヤー合成・外部接続はこの上に作る」という正準JSONの存在理由が、
柱について丸ごと成立していなかった。

**逆向きのずれも同じ場所にあった。**同じ宣言の中の `x:X1,X2` と `x:X2,X1` は同じ構成なのに、
書かれた順のまま出力されるので違うバイト列になっていた。
**順序の扱いが両方向とも逆になっていた** — 意味のある順序を消し、意味の無い順序を残していた。

## 決定

**1. 順序が意味を持つ配列の正準順は、宣言順そのものである。**

`columns` から `sortBySerial` を外す。並べ替えは「順序に意味が無い」ことの表明であって、
無条件の整形ではない。新しい配列を正準JSONに載せるときは、まず
**「この配列の順序を入れ替えたら別の構成になるか」**を問う。なるなら並べ替えてはならない。

**2. 意味の無い順序は、宣言の中まで正準化する。**

- 柱の `x:` / `y:` の通り名の列は**通りの並び順**に整える (辞書順ではない — `X10` は `X2` の後である)。
- 描かれた線の端点の対は、**解決座標の昇順**に並べる。線分は向きを持たないので、
  どちらから書いても導出される凸片は同一である (実験で確かめた)。
  **綴りは通り参照のまま保つ** (規則3) — 正準化するのは対の順序だけである。

**3. 三つの語を意味差分に乗せる。**

- **柱** — 位置は書かれないので、比べるものは宣言しかない。宣言のラベル
  (`900角 L1 x:X2`) を鍵に追加・削除を対応させ、**順位の入替も差分として報告する**
  (決定1の帰結 — 順位が変われば建物が変わる)。
- **描かれた線** — `boundaryFields` に `line` を足す。線は境界の実現そのものなので、
  動かせば建物の形が変わる。面積の変化として空間側に間接的に出ることはあるが、
  それは導出値であって原因ではない。**面積が偶然一致する変更 (隅切りを反対の隅へ移す) は、
  ここが無いと完全に不可視になる。**
- **地下** — `levels.changed` の比較に足す。集計 (地上/地下の床面積) と矩計が読む宣言なので、
  落とすと意味が変わる。

**4. 差分の本文は、変わった項だけを言う。**

polygon の変化は「頂点 4 → 4 / 面積 100.00㎡ → 100.00㎡」と、変わっていない数字だけを
並べることがあった (巡回正規化では違うが頂点数も面積も同じ、という形の変化)。
変わった項だけを出し、どれも変わらないなら「形: 頂点数も面積も同じ → 頂点の位置が違う」と言う。
**何も伝えない行を出すくらいなら、伝わらなかったことを言うほうがよい。**

## 代替案

**`columns` を正準化するために「先勝ち」をやめる。** 順序への依存が消えるので正準化は素直になる。
採らなかったのは、先勝ちが柱の記法の要だからである — 「基本は800角、コアだけ900角」を
二行で書けるのは、後から書いた限定が先の宣言を上書きしないという規則があるからではなく、
**先に書いた限定が勝つ**からである。順序を捨てると `column 900 L1 x:X2` を書いたあとに
`column 500 L1` と書けなくなり、全通りを列挙することになる。

**柱を位置 (添字) で対応付ける。** 差分の実装としては素直だが、一行挿入しただけで
以降の全宣言が「変わった」ことになる。ラベルで対応させ順位を別のフィールドにすれば、
挿入は「一件の追加 + 以降の順位の変化」として読める。

**線の端点も綴りごと正準化する** (解決座標で書き直す)。バイトは確実に揃うが、規則3
「書かれた表記を保存する」を破る。`X3+600,Y2-900` という綴りは設計者が通りとの関係を
言っているのであって、座標はその帰結にすぎない。正準形は語り直さない。

**柱を diff の対象にしない** (正準JSONの行diffで足りるとする)。`koyu json` の行差分は
「配列の何番目が変わった」としか言えない。`koyu diff` の主張は「差分は構成の言葉で読める」
ことなので、柱だけが構成の言葉を持たないのは主張の破れである。

## 帰結と代償

**得たもの。** 書き換えたのに差分が出ない、という最も高くつく黙殺が三つ塞がった。
別の建物が同一のハッシュを持つ状態が終わった。
順序の扱いに規則ができた — 「並べ替えは順序に意味が無いことの表明である」。

**代償1: `columns` の並びは書き手の手に残る。** 同じ柱割りを違う順序で書いた二つのファイルは、
違う正準JSONを持つ。これは**正しい** — 順序が意味である以上、違う順序は違う構成である。
ただし「意味が同じなのに順序だけ違う」場合 (交点が重ならない二宣言) も差分に出る。
順位の入替が実際に何かを変えたかを判定するには柱を導出して比べる必要があり、
それは正準JSONの層の仕事ではない。

**代償2: 柱の対応付けはラベル一致である。** 寸法も通りもレベルも同じ二つの宣言 (完全な重複)
は区別できない。重複した宣言は後の一本が一本も立たないので COL02 が言う — 診断の側で拾う。

**代償3: 台帳がまた一つ増えた。** 「順序に意味があるか」は配列ごとの性質であり、
実装 (`toCanonical`) と spec (canonical-json.md の規則1) の二箇所に書かれる。
機械照合は無い。配列を足すときに問う一行を規則1に埋め込んだのが、今できる最善である。
