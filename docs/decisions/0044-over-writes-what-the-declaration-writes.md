# ADR-0044: `over` が書ける語は、その宣言が書ける語である

日付: 2026-07-30 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [ADR-0035](0035-composition-rules.md) 規則5 / 関連: [ADR-0019](0019-band.md) (帯)・[ADR-0008](0008-vocabulary-and-level-attr.md) (`level:` は解釈される属性)・[ADR-0028](0028-diagnostics-per-declaration.md)

## 文脈

[規則5](../reference/muro/composition.md) はこう約束する — 「`over` で `h:2400` にした模型と、最初から `h:2400` と書いた模型は、同じ正準JSONを与える」。

**空間についてはこれが破れていた。**`over` の属性適用は対象の種類で分かれており、境界は `applyBoundaryAttr`、レベルは `applyLevelAttr` が typed field を持ち上げていたのに、**空間・ゾーン・アセットは汎用の `applyAttr` に丸投げされていた。**汎用の道はキーの形を一切見ないので、二つのことが起きた。

### 1. `over ... w:1000` が無音で落ちる

`space` 宣言は `w:` を拒む — 帯の要素の語であり、字下げを落とした要素が「領域なしの空間」として黙って通るのを防ぐためである ([ADR-0019](0019-band.md))。

```text
✖ w: may not be written on space (a space written by width sits indented under band)
```

**`over` はこれを通していた。**帯の要素に `over /L1/a w:1000` と書くと `check` は緑 (exit 0)、`at` は `X1..X1+1600` のまま幅は動かず、`attrs` に死んだ `"w": 1000` が残った。**「幅を直した」という書き込みが、何も直さないまま成功を報告していた。**

これは掟が名指しで禁じている失敗である — 「解釈される属性の値は検査する。**書いたのに解釈されなかった値を黙って既定へ落とさない**」。

### 2. `over ... level:L3` が空間を動かさない

`level:` は空間の所属を決める typed field で、宣言では `takeString(attrs, "level")` が取り出して検証する ([ADR-0008](0008-vocabulary-and-level-attr.md))。`over` では汎用の道を通るので、`s.level` は動かず `attrs` に文字列が残った。

```json-part
{"type": "room", "level": "L2", "at": [...], "attrs": {"level": "L3"}}
```

**空間は L2 にあるまま L3 を名乗る属性を持つ。**`check` も `--strict` も緑である。

さらにこれは[規則1](../reference/muro/composition.md)も破っていた。`applyAttr` は「値が既にあるか」を `into[key] !== undefined` で見るが、`level` は `attrs` ではなく typed field に住むので `undefined` に見え、**層の強度の判定そのものが素通りしていた** — 弱い層の `over` が強い層の定義を上書きできてしまう。

## 決定

**`applySpaceAttr` を立て、`over` が空間に書く語を宣言と同じ扱いにする。**

1. **宣言が拒む語は `over` も拒む。**`w:` は同じ言葉で断る。言葉は定数 `W_ON_SPACE` に一度だけ書き、宣言と `over` が共有する。
2. **宣言が typed field に取る語は `over` も typed field に効かせる。**`level:` は `s.level` を動かし、宣言されていないレベルなら宣言行と同じ言葉で断る。`attrs` には残さない。
3. **強度の判定は typed field についても効かせる。**`applyBoundaryAttr` と同じ形で、`attrSrc` に記録が無ければ**定義した層**を前の層として扱う。
4. **ゾーンとアセットは汎用の道のままにする。**どちらも typed field を持たず、拒む語も無い。空間だけが非対称だったのであって、汎用の道そのものが誤りではない。

## 帰結

**`over` で直した版と最初からそう書いた版が、`level` についてもバイト一致するようになった。**規則5 が空間について成立する。

**弱い層の `over` は強い層の定義に勝てなくなった。**規則1 の通りである。従来この経路だけが規則1 を素通りしていたので、**これは挙動の変更である** — 以前 `attrs` に落ちていた値は、いまは無視されるか (弱い層) 、typed field に効くか (強い層) のどちらかになる。ただし以前の挙動で「効いていた」ものは一つも無い (`attrs` の死んだ文字列を読む消費者は core に無い) ので、**導出物は変わらない。**言語の版も機械形式の版も動かない。

**回帰3件を [composition.test.ts](../../test/composition.test.ts) に入れた。**修正前のコードで実際に落ちることを確認した。

## 残っている穴

**`over asset` が参照している開口に届かない。**アセットの既定値を強い層で上書きしても、既に解決された開口の `w`/`style` は動かない (`assets` セクションは両版一致するのに開口だけが割れる)。これは適用の道の問題ではなく**解決の時点**の問題である — 開口は宣言を読んだ時点でアセットを解決し、後から上書きされたことを知らない。直すには解決を parse の出口へ遅らせる必要があり、別の ADR で扱う。

**`drop` と `import` の相対順序が結果を変える。**`drop` は走査中に生きたモデルを書き換えるので、`import` 行を一行動かすだけで緑とエラーが入れ替わる。[規則1](../reference/muro/composition.md) が「強度は走査の順ではない」と名指しで否定した操作そのものであり、これも別に扱う。
