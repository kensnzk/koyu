# ADR-0057: 測地の枠 — 位置と真北を所与として持ち、投影は持たない

- 状態: 採用
- 日付: 2026-08-05
- 対象: `origin` / `azimuth` の二宣言、正準形式 `koyu-canonical/1.2`、診断 `SIT06`

## 文脈

mm 座標が地球のどこを指すのかが、原本のどこにも書かれていない。原点も測地系も回転も無く、mm 原点 (0,0) は著者が暗黙に置いた場所である。この一点の欠落で、都市接続の全部が止まっている — PLATEAU / CityGML への配置、緯度経度からの用途地域の取得 (`site` は建蔽率と容積率を導出するが制限値を持たない)、日影と北側斜線 (法56条1項3号は条文に「真北方向の水平距離」と書いてある)、IFC の `IfcMapConversion` と `IfcSite.RefElevation`。

一方で `N` `E` `S` `W` は**軸の語であって方位磁針ではない**とリファレンスで既に約束されており、採光は方位盲であることが二度 (ADR-0006、ADR-0020) 意図的に選ばれている。測地を入れるとは、この二つを裏切らずに枠だけを足すことである。

## 決定

**1. core は枠を持つだけで、何も導出しない。** 置く理由は依存ゼロの方針ではない。**誰もが欲しがる唯一の導出 (model mm → CRS metres) こそ core にはできない**からである。それには子午線収差角 γ が要り、γ には投影が要る。線は「持たないと決めたもの」が引いている。したがって `light` `site` `graph` `edge:` は一行も変わらない。

**2. 二つの宣言に分ける。**

```
origin epsg:6677 easting:-8000.123 northing:-34000.456 elevation:2.35 vertical:6695
azimuth Y 347.5
```

融合すれば度数のキーが `epsg:` と同じ行に並び、読者は方位角をその CRS の中の角 — つまり座標北基準 — と読む。分離は決定4 の失敗に対する構造的な防御である。availability も違う: `azimuth` は企画初日に分かり単独で日影と北側斜線を開き、`origin` は測量成果を待つ。

**3. `azimuth` は真北であって座標北ではない。** 理由は「測量図がそう書いてある」ではない — 平面直角座標系で作図された地積測量図の方位矢印はむしろ座標北のことが多く、だからこそ真北測量が別途発注される。理由は二つある。**座標北は CRS 無しには定義できない**ので、`azimuth` が単独で立つなら座標北ではありえない。そして**真北の値は CRS を書き替えても意味が変わらない**が、座標北の値は任意である `origin` の有無で黙って意味が変わる — **任意の宣言の有無に、別の宣言の意味が依存してはならない。**

**4. `azimuth Y a` は「+Y 軸の真方位角、真北から時計回り、0 ≤ a < 360」と綴る。** 素案は `north <deg>` を「+Y から北へ時計回り」と定義していた。これは**逆向きの方位角**で、建築も測量も時計回りの角は北から対象へ測るから、読者の既定の読みが定義の逆になる。実害は既に出ていた — このリポジトリの中で `north -12.5`「真北からの回転角」と `north 12.5`「+Y から北へ時計回り」が同時に書かれていた。**同じ語、逆の符号、一つのリポジトリ。**方位角に統一すれば符号が無くなり、面の方位も *a* / *a*+90 / *a*+180 / *a*+270 と負号なしで出る。範囲外は畳まずに拒否する — 畳めば誤りが隠れる。位置引数 `Y` は主語を記法自身の語彙で名指し、v1 では `Y` だけを受ける。

**5. 合成の式を活字で書く。** CRS の軸は座標北に揃い、`azimuth` は真北基準だから、両者を繋ぐのは

```
model → CRS grid の回転 = azimuth(+Y) − γ(origin)
```

である。γ は系の中央経線で 0、系の端で約 0.87°、系 IX の都心では約 0.05°。0.5° あれば 100m の建物の遠い隅が 0.87m ずれる。**γ を落とす橋は必ず作られる**ので、式は橋の作者の裁量にせずリファレンスに置く。

**6. CRS は不透明な EPSG 整数で、単位は常にメートル。** EPSG コードは測地系・投影・系番号・軸順を一語で言い切るので、測地系を別に綴れば矛盾の余地ができる。2011→2024 の改称は不透明性の理由であって反証ではない — 実現ごとに別のコードが振られるので、今日 `epsg:6677` と書いたファイルは十年後も一意である。core の検査は正の整数であることだけで、コード表は持たない。値は mm ではなくメートル — `origin` はモデルの中の長さではなく、外の枠の中の点であり、外の枠は自分の数字を持つ。mm を選べば `-8000.12` → `-800012` の桁埋め誤りが 7.2m のずれとして完全に静かに通る。「CRS 自身の単位」とは書かない — core が検査できず、解釈しないと約束したコードに意味が依存してしまうから、単位はメートルと平たく決める。`lat:`/`lon:` は受けない: 地理座標は場所を留めるが枠を留めない。

**7. 高さは基準を言わずには受けない。** `elevation:` は `vertical:` (鉛直 CRS の EPSG コード) と対で必須とし、片方だけはエラーにする。無資格の高さが無いより悪いのは、平面直角座標系の CRS が 2D で鉛直軸を持たず、日本では T.P. のほか A.P. / O.P. / Y.P. が日常的に使われて 1m 超の差があり、さらに楕円体高と正標高がジオイド高 (日本で約 30〜40m) だけずれるからである。無資格の T.P. 値を楕円体高として受けた橋は建物を約 36m 埋める — `elevation:` が防ぐはずのまさにその失敗である。複合 CRS コードは受けない: `epsg:` が 2D か 3D かが不透明なコード次第になり、単位のときに退けたのと同じ欠陥が戻る。**`elevation` はモデルの z=0 の高さであり、GL でも地盤面でも平均地盤面 (令2条2項) でもない。**

**8. 枠はモデルの事実であって、実行時コンテキストではない。** ADR-0053 の `AnalysisRunContext` は方位を運ぶと書かれていたが、一つの事実に二つの出所は静かな矛盾である。境目はこう引く — **コンテキストは「この場所について世界が今なんと言っているか」(管轄・基準日・用途地域・高度地区)、モデルの枠は「この模型自身の数字が何を意味するかについて測量がなんと言ったか」。**北は構成的で、無ければ mm が繋ぎ止められていない。したがって**方位はコンテキストの列から退く**。`azimuth` 不在は `MissingInput` の `kind: "model"` で綴る — 最初の日影解析がこれをコンテキスト欠落として報告したら、境目は初日に失われる。

**9. `azimuth` の不在は 0 ではなく「未知」である。** 既存のファイルが黙って方位を獲得してはならない。0 は「知っていて、揃っている」であり、不在は「知らない」である。

**10. 新しい診断は `SIT06` (warning) 一つだけ。** 値の検査は parse 時の `SourceError` で足りる。ただし `origin` を書いて `azimuth` を書かないモデルは配置できず、回転を受け取らなかった橋は 0 と仮定して最大 360° 間違える — 両方書かないより悪い静かな失敗である。書かれたものが自己矛盾しているわけではないのでエラーではなく、`SIT04`「polygon に対応する zone が無い」と同じ「与件が不完全である」形の警告にする。逆は警告しない — `azimuth` 単独は完結した言明である。実装は `checkSite` の先頭に置く: 節の粒度は走査単位であってコード族ではない。core が導出を始めれば、この前提は変わる。

**11. 言語版は動かさない。正準形式は動かす。** 版を上げる基準はリファレンスが自分で述べている — 古い処理系がその行を語として読めず「**黙って**別の建物になる」ことである。`origin` は行頭語なので、旧処理系は `Unknown keyword: origin` を投げて騒がしく拒否する。これは保守的拡張で、今日妥当なテキストはすべて妥当なまま、正準出力も Form も変わらない。変わるのは「プログラムでなかったテキストがプログラムになる」ことだけである。先例も `zone` `stack` `polygon` `import` `band` が字句の版ゲートを持たないことで揃っている。一方**正準形式は 1.1 → 1.2** に上げる — キーが二つ増えたからで、これは規則そのままである。

**12. 枠は `Form` に入らない。** `Form` は形、枠は形の数字が何を意味するかである。入れれば凍り、そして Form 座標が地理座標だと読者に誤解させる。

## 代替案

**属性で運ぶ**案 — `zone /site geo.crs:... geo.north:...` — は core を一行も触らずに済むが、枠はゾーンの性質ではなくモデルの性質であり、設計レビューが既に「測地は継ぎ足しの属性ではなく座標系のモデルとして設計せよ」と警告していた。**`N/E/S/W` を方位に読み替える**案はリファレンスの既存の約束を破り、方位を持つ場所を二つ作る。**面ごとの真方位角を core で導出する**案は、消費者ごとに一行の算術でしかないものを、二つ目の方位の場所と引き換えに買う。**採光を方位依存にする**案は今回は取らない — 令20条の採光補正係数は d/h と用途地域だけで方位項を持たないので、`azimuth` は `light` に負債を作らない。

## 帰結と代償

グリッド非平行の建物が、敷地多角形を回して北を偽ることなく書けるようになった — 全体回転の場合に限るが、これは配管ではなく能力である。代償として、筆界点座標を持つ著者は多角形をモデル枠へ**平行移動だけでなく回転して**転記することになり、ADR-0011 が持っていた「逐語で写せる」性質が手作業では失われる。だから橋 (`koyu-geo`) が最初に持つべき道具は輸出ではなく**輸入** — 地積測量図の座標表と選んだ `azimuth` から `polygon` 行を生成することである。

平面直角座標系の成果は X 欄が北距、Y 欄が東距で通常の慣習の逆である。`easting:`/`northing:` の綴りは名前の衝突を防ぐが転記は防がない (東京の北距 −34km は東距としても合法な値である) — 妥当性の検査は EPSG 表を正当に持てる橋か検証の側の仕事として残る。磁北の転記 (日本の偏角は 5°〜9.5° 西 — γ の二桁上) も文法では防げないので、`site` と `model_summary` が値を言葉で読み上げ、平面図が北矢印を描く。**180° 誤りと余角誤りを捕まえられるのは範囲検査ではなく絵だけである。**

一つのモデルは一つの枠を持つ。敷地の中で棟ごとに向きが違う場合は書けない — ただしこれは一つのグリッドと軸平行矩形という既存の制約の継承であって、この決定が作った制約ではない。将来スコープ付きの枠を足す余地を残すため、リファレンスは「方位角は一つ」ではなく「**モデルは一つの枠を持つ**」と書く。

投影座標から転記した多角形は投影の縮尺歪みを持つ (日本の平面直角座標系は中央経線で 0.9999、系の端で約 1.0001)。1,000㎡ の敷地でシューレース面積が約 0.2㎡ ずれる — 規制の閾値の下、しかし敷地面積の記載分解能の上である。地上面積である登記の敷地面積とは一致しないので、`koyu.schematic.site.area` の ±0.05㎡ の許容は測地由来の多角形では鳴り始める。

地盤面・平均地盤面・高度地区は触れていない。地表面はモデルされていないので、高さ制限も日影の測定面 (平均地盤面 +4m / +6.5m) も道路斜線の基準も届かないままである。高度地区は都市計画の重ね合わせ、すなわち管轄と基準日であり、決定8 で整理した実行時コンテキストの担当である。

`test/fingerprints.test.ts` は「ここが落ちたら『ハッシュを更新する』では決してない」と書いている。この変更では**正準ハッシュ 15 本すべてが動き、Form ハッシュは一本も動かない** — 前者は形式版の文字列がバイトの中にあるからで、後者が「core は枠から何も導出しない」の機械による証明である。tower は枠を書いたので正準ハッシュが二度目に動くが、その Form ハッシュもやはり動かない。
