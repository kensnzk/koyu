# ADR-0048: 約束を母集団の上で縛る — 開口の並びの破れを生成器が見つけた

日付: 2026-07-30 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [ADR-0047](0047-conformance-suite.md) 残っている穴 (ケースは手書きである) / 関連: [ADR-0041](0041-derivation-uniqueness.md)・[ADR-0043](0043-uniqueness-without-lines.md) (同じ約束の一巡目と二巡目)・[ADR-0013](0013-canonical-json.md)

## 文脈

導出の約束1 はこうである。

```text
toCanonical(a) === toCanonical(b)  ⟹  derive(a) ≡ derive(b)
```

[ADR-0041](0041-derivation-uniqueness.md) が四つの破れを閉じ、[ADR-0043](0043-uniqueness-without-lines.md) が三つ閉じた。[適合試験](../../conformance/README.md)にも対を三組置いた。**どれも手で書いた一組ずつである。**

そして [canonical-property.test.ts](../../test/canonical-property.test.ts) には、記法の全構文を書く種つき生成器が既にあった。この生成器は毎回**正準形が等しい対**を作っている — 原本と、その宣言を並べ替えた版である。並べ替えても**バイト**が変わらないことは縛っていた。

**だが形の側は一度も見ていなかった。**約束の後半 (`⟹ derive(a) ≡ derive(b)`) が、母集団の上で一度も試されていなかった。

## 決定

**生成器が作る対を、形の側でも突き合わせる。**

```ts
const j0 = toCanonical(parse(original));
assert.equal(toCanonical(parse(shuffled)), j0);   // 前提
assert.equal(form(shuffled), form(original));     // 結論
```

前提を先に確かめるのは witness と同じ規律である — 正準形が違えば、その対は形について何も言っていない。

**併せて生成器の言語版を `koyu 0.5` から `1.0` へ上げた。**同ファイルは「母集団は記法の全構文である」と謳っていたが、0.5 を宣言していたので 1.0 で入った語 (`over` `drop` `+` `-` `=`) は VER04 に阻まれて母集団に入らない。**謳い文句が偽だった。**

## 一巡目で破れが出た

**現在のコード** — つまり ADR-0041 と ADR-0043 が閉じたと宣言した後のコード — で、seed=1 が落ちた。

**一つの境界に載る開口の並びが、宣言順だった。**正準形は開口を内容の正準順に並べる ([canonical-json](../reference/json/index.md) — 「宣言順に意味の無い配列も内容の正準順に並ぶ — 開口・`seg`・…」) のに、`derive` は `b.openings.entries()` を宣言順で読んでいた。

帰結は `a|b@i` のときと同じ、一段下である。**開口の同一性は「境界の ref + 境界の中の添字」なので、同じ `…@4/0` が一方では扉、他方では窓を指した。**正準形はバイト同一である。

```text
seed=1: canonically equal but the shape differs (reverse)
  /openings/1/kind = "door" vs "window"
  /openings/1/name = "玄関" vs "地窓"
  /openings/1/swing  — 一方にだけある (窓は振れを持たない)
```

`seg` も同じ構えだったので併せて閉じた。`canonicalOpeningOrder(b)` と `canonicalSegOrder(b)` を立て、`canonicalBoundaryOrder` と同じ形にした。

**幾何は動いていない。**同梱例6例で、件数・総面積 (0.001㎡まで)・開口の集合 (種類と座標と幅と z)・壁パネル・スラブがすべて修正前と一致する。動いたのは開口と `seg` の並びだけで、`office.muro` の Form ゴールデンだけが変わった (一つの境界に複数の開口を持つ唯一の同梱例である)。

## なぜ手で書いた試験は見落としたか

**witness も適合試験も、一つの境界の上で二つの開口を入れ替えていなかった。**境界を並べ替える対、空間を並べ替える対、領域の合併を入れ替える対はあった。**開口だけが抜けていた** — 抜けていることに気づく手は、母集団を生成する側にしかない。

これが「一つのケースだけでは実装の写しにすぎない」の一段上の話である。**手で選んだ対の集まりも、選んだ人が思いつかなかった軸については何も言わない。**

再現ケースは適合試験に落とした (`opening-order-declared` / `opening-order-swapped`)。マージ済みの main に受験させると落ちる。

## 二つめの変形 — 属性を `over` へ括り出す

生成器が**層の集合**を吐けるようにし、`space` と `boundary` の行から属性を剥がして、より強い層の `over` に置き直す変形を足した。`over` は定義より強い層に無ければ通らない (規則1 — entry は添字0で最も弱い) ので、entry は `import` だけを持ち、定義は base 層、`over` はその後の層に入る。単一ファイル版と正準形も形も一致しなければならない — これが[規則5](../reference/muro/composition.md)の母集団版である。

**括り出す鍵に typed field を混ぜることが要点だった。**最初は `name` だけを括り出したが、`name` は宣言でも `over` でも属性の袋に入るので、**両方の経路が同じ道を通り、経路の違いを一つも試していなかった** — 修正前のコードに受験させても素通りした。`level` (空間) と `t` `type` (境界) は parse が型のついたフィールドへ持ち上げる鍵なので、`over` の側が持ち上げを忘れていれば死んだ属性が残って別の建物になる。

広げたところ、修正前のコード (`2ca4d97`) で落ちた — seed=1 で17件を括り出した結果が別の建物になる。[ADR-0044](0044-over-writes-what-the-declaration-writes.md) が閉じた破れである。**手で書いた対は一組あったが、母集団の上では試されていなかった。**

## 三つめの変形 — `+` の合併の書き順を入れ替える

**着手して分かったのは、母集団に `+` が一つも入っていなかったことである。**生成器の空間はすべて一枚の割付 (`X i..i+1 Y j..j+1`) で、合併は一度も書かれていなかった。にもかかわらず同ファイルは「母集団は記法の全構文である」と謳っていた — [ADR-0043](0043-uniqueness-without-lines.md) が要ると名指しした三つの変形のうち、`+` の入れ替えは**変形が無いどころか対象が無かった。**

合併を持つ空間を一つ足し (L2 の空き区画に `X4..X5 Y2..Y3 + X4..X5 Y3..Y4`)、割付が二枚であることを COVERAGE で縛り、書き順を入れ替える変形を足した。

`normalizeRegionOrder` を入れる前のコード (`59576ac~1`) に受験させると seed=1 で落ちる — `/L2/hall` の凸片の並びが書き順のまま出て、**正準形はバイト同一なのに形が割れる。**[ADR-0043](0043-uniqueness-without-lines.md) が閉じた破れであり、**手で書いた witness は一組あったが、母集団の上では試されていなかった。**

## 四つめの変形 — 帯を、それが導く位置指定へ書き直す

[帯](../reference/muro/band.md)は寸法と並びから位置を導く綴りであって、別の建物ではない。生成器が毎回吐く帯 (`band X X1..X4 Y1..Y2` の三要素) の切り位置を計算し、位置指定の三行へ書き直す変形を足した。

**要点は、床規則を試験の側で独立に実装したことである。**導出された切り位置の綴りは「その座標以下で最も大きい通り芯からのオフセット」であり (`5000` なら `X2+2000`)、正準 JSON は `at` の綴りを素通しするので、**同じ座標を別の綴りで書けばバイトが変わる。**したがって実装から綴りを読んで書き戻せば round-trip を試すだけになり、規則そのものは縛られない。二度目の実装を置いて突き合わせて初めて規則が縛られる。

崩して確かめた — 床規則を「常に `X1` からのオフセット」に替えると seed=1 で落ちる。**現在のコードでは30種すべて通った。**帯と位置は、正準形も形も一致する。

## 単射性の側 — 逆命題は偽だった

「意味のある一箇所の変更で必ずバイトが変わる」の**形の側**を見ていなかった、と当初は穴に数えた。**これは穴ではない。**

その言明は約束1の**逆** (`toCanonical(a) !== toCanonical(b) ⟹ derive(a) !≡ derive(b)`) であり、規範のどこにも無い。そして**偽である。**

```text
space /L1/a room X1..X2 Y1..Y2 acme.sensor:21
space /L1/a room X1..X2 Y1..Y2 acme.sensor:99
```

運搬層の属性 ([台帳](../reference/muro/attributes.md)の tier `carry`) は正準形に載るが core が解釈しないので、形に届かない — **別のバイト、同じ形。**生成器の `MUTATIONS` にもこの変更が既に入っている。もし形の一致まで縛っていたら、その試験は正しい実装を落としていた。

閉じ方は「試験を足す」ではなく**言明を正すこと**だった。三点で留めた。

- 証人の試験 (`witness: different bytes do not imply a different shape`) — バイトが違うことと形が同じことを両方主張する。運搬層の属性が形へ漏れれば落ちる
- [約束1](../reference/form/index.md)に**含意が片向きである**ことを書いた (日英) — 「正準形の差は『形が変わった』の証拠にならない」
- このADRの記録

**穴と非性質を混同したのが誤りだった。**縛れていないものを数える前に、それが約束されているかを先に見る。

## 先行 ADR の穴のうち、これが閉じたもの

ADR は後から直さないので、閉じた勘定はここに書く。

**[ADR-0043](0043-uniqueness-without-lines.md)「witness は生成器ではない」— 閉じた。**要ると名指しされた三つの変形 (宣言の並べ替え・`+` の入れ替え・帯と位置の書き換え) が母集団の上に揃い、`over` への括り出しが四つめとして加わった。同 ADR が「先に上げる」と書いた生成器の言語版も 1.0 になった。

**[ADR-0047](0047-conformance-suite.md)「ケースは手で書いたものである」— 閉じた。**同じ性質が母集団の上で縛られた。適合試験のケースが手書きであることは変わらないが、それは**規範文に紐づいた最小の例**という役割であって、網羅の代わりではない。網羅は生成器が持つ。

**まだ開いているもの** — いずれもこの ADR の範囲外で、別に決める。
