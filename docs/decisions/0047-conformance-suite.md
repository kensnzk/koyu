# ADR-0047: 適合試験 — muro の定義を実装から独立させる

日付: 2026-07-30 / 状態: 採用 (v0.16.0、言語版 muro 1.0) / 起点: [ADR-0046](0046-one-canon.md) (正典を一つにする) / 関連: [ADR-0036](0036-machine-format-version.md) (機械形式)・[ADR-0016](0016-diagnostic-contract.md) (診断契約)・[ADR-0028](0028-diagnostics-per-declaration.md)・[ADR-0040](0040-derive-reference.md) (参照実装)・[ADR-0041](0041-derivation-uniqueness.md)・[ADR-0043](0043-uniqueness-without-lines.md)

## 文脈

**muro の定義は koyu の中にしか無かった。**規範は[公開ドキュメント](../reference/index.md)が持ち、`test/` が実装との一致を縛る。だが `test/` のケースは実装の関数を呼ぶので、**別の言語で書いた実装が受験する場がどこにも無い。**

これは二つの意味で危うい。**一つ、実装が死ねば言語も死ぬ。**規範文は残るが、それが何を意味するかを確かめる手が無い。**二つ、二人目の実装者が可能にならない。**「正しい muro 実装」を名乗る条件が定義されていないので、書いた人が自分で判断するしかない。

しかも二人目は仮定ではない。ugatsu が既に第二の消費者であり、[ADR-0040](0040-derive-reference.md) が数えた壊れ方 (上部吹抜けの投影が11件落ち、最上階の壁の上端が 2550 と 2700 に割れた) は、まさに「同じ原本から違う形が出た」ことだった。**二つの実装が同じ原本を同じに読むかを機械で確かめる場が無い**という穴が、そこで一度実害を出している。

## 決定

**`conformance/` を立て、入力と期待だけで完結するケースを置く。ケースは処理系の関数を一つも参照しない。**`koyu` を呼ぶのは薄いランナー一枚 ([test/conformance.test.ts](../../test/conformance.test.ts)) で、別の実装は同じディレクトリに対して自分のランナーを書く。形式の契約は [conformance/README.md](../../conformance/README.md) が持ち、ランナーの実装詳細は要らない。

### 期待は四つ、いずれも凍る面に属する

| 期待 | 比べ方 | なぜその比べ方か |
|---|---|---|
| 正準 JSON | **バイト一致** | 形式が照合順・正規化・数の綴りまで定めて「同じ構成からは同じバイト列」を約束している。バイトでなければその約束を試験していない |
| 診断 | 構造の一致 (並びを含む)。**`message` を含めない** | 契約は `code`・`severity`・出所・責める対象であり、**本文の字面は凍らない。**縛れば、同じ事実を別の言葉で書いた正しい実装が不適合になる |
| 形 | 構造の一致 | 凍るのは `Form` の中身であって、その JSON の綴りではない |
| 形の一点 | 名指した場所の値の一致 ([JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901)) | 導出の**規則**を縛るのに形を丸ごと置くと、二室でも300行を超えて主張が埋まる |

### 等価性と差異は対で縛る

**一つのケースだけでは、それが何であれ実装の写しにすぎない。**だから `about.json` は二つの関係を持つ。

- `sameBuildingAs` — 綴りは違うが同じ建物 (帯と位置、`over` と直書き、五枚と一枚)。正準形がバイト一致し、形を持つなら形も一致し、**二つの本文が実際に違う**
- `differentBuildingFrom` — 同じ層を別の順に並べた違う建物 (`import` の並びが強度の宣言であること)。正準形が一致**せず**、**層の中身が同じである**

後者が要るのは、**差異でしか縛れない規則がある**からである。`import` の並びが強度なら、並べ替えて結果が変わらなければ並びは何も意味していない。

### 台帳を持つ

各ケースの `about.json` が、縛る規範文を公開ドキュメントの頁とアンカーで指す。ランナーが集めて印字し、**指す頁が実在しなければ落ちる。**縛るケースを書けない規範文は規範の曖昧さであり、書き足す合図である。

### 何を入れないか

三つを、判断として除いた。**「試験できない」のではなく「適合の定義に入れない」である。**

**`koyu validate` の判定。**凍らない面であり、規則が一つ増えるたびに他実装が不適合になる試験は適合の定義として成り立たない。

**CLI と MCP。**コマンドの名前もサーバーの作りも記法ではない。別の実装が別のコマンド名を使い MCP を実装しなくても、正しい muro 実装でありうる。適合が問うのは「同じ原本から同じ意味を読むか」であって、どう呼び出されるかではない。

**出所の追跡** (合成の規則6)。正準形にも診断にも形にも現れない、プログラムから引く面である。

## 帰結

**122ケースが101の規範項目を縛る。**エラー・警告64種類 (種類・重さ・行・ファイル・対象まで)、記法26頁、合成の五規則、導出の数値の決まり、正準形の綴りの細部。

**試験が本物であることを、古いコードで確かめてある。**`2ca4d97` (この一連の修正より前) に受験させると3件落ちる — 整数に見えるキーの照合順、既定境界の `a`/`b` の向き、`+` 合併の書き順。いずれも[ADR-0043](0043-uniqueness-without-lines.md) と [ADR-0045](0045-collation-survives-serialisation.md) で直した実際のバグである。

**作りながら三つ、自分の誤りを見つけた。**

**一つ、期待値に診断の本文を入れていた。**最初の一件で気づいた。本文は凍らないので、縛れば正しい実装を落とす。

**二つ、期待値に絶対パスが残っていた。**古いコードに受験させて11件落ちたので「よく捕まえている」と思ったが、8件は `related` の中の `file` が絶対パスのままだったせいだった — **別の場所にクローンした人には全部落ちる。**適合試験として成り立っていなかった。ファイル名だけに正規化した。

**三つ、形の期待値を機械的な行数で切ろうとした。**全ケースに置いたら22,067行になったので150行で切ったところ、**バグを捕まえていた三件からも形が消えた** — 最小の建物の形が既に350行なので、行数では選別できない。基準は「そのケースの主張が形についてであるか」であって、大きさではない。

## 残っている穴

**ケースは手で書いたものである。**生成器が意味保存変形 (宣言の並べ替え・`+` の入れ替え・帯と位置の書き換え) で対を作れば、母集団の上で同じ性質を縛れる。対の形が固まったので、生成した対をそのままケースに落とす道は開いている。生成器は [canonical-property.test.ts](../../test/canonical-property.test.ts) にあるが、**いま `koyu 0.5` を宣言している**ので 1.0 の語 (`over` `drop` `+ - =`) が母集団に入らない。先に版を上げる。

**期待値は実装の出力から作った。**一件ずつ規範と突き合わせたが、規範が何も言っていない箇所を「実装がそうしているから」で固定した可能性は残る。台帳が縛る規範文を数えられるので、逆に「どの期待値がどの規範文にも紐づいていないか」を洗う余地がある。
