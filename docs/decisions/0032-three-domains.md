# ADR-0032: 三つの領域 — core は凍り、検証と表現は凍らない

日付: 2026-07-27 / 状態: 採用 (v1.0.0-rc.1) / 起点: [方針の総覧](../policy.md) 第二部

## 文脈

v0.15 の時点で、`check` は二種類のことを同時に言っていた。「境界が未定義の空間を参照している」(REF01) と「外皮に穴がある」(ENV01) が、同じ配列に、同じ `severity` で並んでいた。前者は**構成が壊れている**という読解の失敗であり、後者は**建築として疑わしい**という判断である。混ざっていること自体は不便ではなかったが、1.0 を切る段になって問題が二つ現れた。

**第一に、凍結の単位が決まらない。**1.0.0 は「壊さないと約束する面の確定」である。REF01 の意味は凍らせられる — 参照先の存在は永久に同じ意味を持つ。ENV01 の意味は凍らせられない — 外皮の判定は粗く、ADR-0025 自身が「代償: 判定は粗い」と書いている。凍らせられないものが同じ面に載っていると、**面全体が凍らせられない**。

**第二に、緑の意味が言えない。**「`check` が緑」が何を意味するかを一文で書こうとすると、「構成が矛盾していない、ただし外皮と階段と採光と敷地については建築的にも一応見ている、ただしその判定は粗い」という文になる。これは定義ではない。定義できない緑は、誰にとっても信頼できない。

同時に、逆向きの問題もあった。判定を増やしたい — 区画・避難距離・排煙・用途別の面積率。増やすたびに `DIAGNOSTIC_CODES` が伸び、spec の台帳が伸び、そのすべてが「凍る面」に見えてしまう。**core の慎重さが、判定の成長を止めていた。**

## 決定

**koyu を三つの領域に分け、依存を一方向にする。**

| 領域 | 場所 | 品質 | 版 |
|---|---|---|---|
| **core** | `src/core/` | きれいでなければならない | **凍る** |
| **検証** | `src/validate/` | 汚くてよい | 凍らない |
| **表現** | `src/draw/` と ugatsu | 汚くてよい | 凍らない |

**1. 保証の範囲を規範として書き下す。**[spec/scope.md](../../spec/scope.md) を新設し、「`check` が緑である」の意味を定義した。

> 構造層と解釈層について、宣言された不変量が成り立つ。運搬層については何も言わない。建築としての妥当性については何も言わない。

**2. 判定を core から移す。捨てるのではなく、置き場所を変える。**ENV01 / RUN06 / RUN07 / RUN08 / SIT03 / SIT05 の六コードと、`daylight()` の 1/7 の合否、CLI の接道 2m の ✔✖ を検証の面へ移した。

**3. 混同できない形にする。**型からして別にする。

```ts
core   Diagnostic { code: "BND04",          severity: "error" | "warning" }
検証   Finding    { rule: "daylight.ratio", level:    "violation" | "caution" }
```

フィールド名が違うので、二つの配列は取り違えようがない。連結しようとすれば型が落ちる。規則名は `chapter.rule` の形で、3字+2桁の診断コードと**字面でも**見分けがつく。

**4. 問いは合否を言わない。**`daylightInputs` は床面積と有効窓面積を返し、`siteReport` は接道長を返し、`envelopeGaps` は線分を返し、`verticalRuns` は蹴上と踏面を返す。**数を返すところまでが core で、数に線を引くのが検証である。**1/7 も 2m も 240mm も、原本の構成が満たすべき不変量ではない。

**5. 依存の一方向を機械で守る。**`test/domains.test.ts` が `src/**/*.ts` の import を読み、core が `validate/` や `draw/` を引いていないことを検査する。文で書いた規律は守られない。

**6. すべての判定は MCP から呼べる。**`validate` ツールを立てた。呼べない判定は、機械にとって存在しないに等しい。

## 代替案

**検証を独立した npm パッケージに切る**案は採らない。部品の境界は、版が別々に動く必要が出た瞬間に切るのが正しく、その必要はまだ無い。そして判定は何が正しいかがまだ定まっていない領域であり、定まらないうちに境界を与えれば**誤った境界のまま固まる**。切り出す条件は「二つ目の管轄が要る」「判定だけを使う利用者が現れる」「判定の版が独立に動く必要が出る」のいずれかで、その時に切る。

**同じ `Diagnostic` 型のまま `domain` フィールドで分ける**案は、混同を防げない。フィールドを一つ読み落とせば混ざるし、実際に読み落とす。型が違えばコンパイラが止める。

**HGT01/HGT02 も検証へ移す**案は採らなかった。方針の文言は「高さの整合」を保証しないと言うが、実装が実際に咎めているのは**導出された立体の相互貫入**である (下階の天井 z2870-2900 と上階の床 z2800-3000 が同時に出る)。これは §5.5 が保証すると明言する「区画の重なり」の断面版であり、平面版の GEO01/GEO02 と同じ構えである。**平面の重なりを保証しながら断面の重なりを保証しないのは、保証面として説明できない非対称**なので、core に残し、方針の側の「高さの整合」を「階高・軒高・斜線などの建築的な高さ判断」に限定して読む。

**判定を全部捨てる**案は方針が明示的に禁じている — 「捨てるのではなく、置き場所を変える」。ADR-0025 が 416空間で 34箇所の外皮の穴を見つけた実績は、判定の価値の証拠である。

## 帰結と代償

**緑の意味が一文で言えるようになった。**`koyu check` は緑を出すときに自分で「構造整合のみ — 建築的な妥当性は koyu validate が別に言います」と印字する。緑を出す場所で緑の意味を言うのが、いちばん誤解されない。

**判定を足すのが安くなった。**`VALIDATION_RULES` に一行足し、`spec/validation.md` の表と `guide/validation.md` の節を書けば終わる。言語の版は動かない。診断コードの台帳も動かない。

代償は三つある。**(1) 利用者は二つのコマンドを覚える。**`check` だけを回していた CI は、判定を見なくなる。移行は「`koyu validate` を足す」の一行だが、足さなければ静かに判定が消える。**(2) 診断コードが六つ欠番になる。**ENV01 / RUN06-08 / SIT03 / SIT05 は再利用しない — 同じ綴りが別の意味を持つと、過去の出力が読めなくなる。**(3) `check` の出力が短くなった。**同梱例のうち外皮の穴を持つものは、`check` では黙って通り、`validate` でだけ声を上げる。門番 `npm run gate:examples` は両方を回す。

三点セットで着地した: 本 ADR (なぜ) + `test/domains.test.ts` ほか (保証) + [spec/scope.md](../../spec/scope.md) / [spec/validation.md](../../spec/validation.md) (現在形)。
