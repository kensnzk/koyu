# ADR-0052: koyu core 0.18.0 で公開面を実証してから 1.0.0 を名乗る

- 状態: 採用
- 日付: 2026-08-03
- 対象: koyu core の実装版と公開面

## 文脈

koyu には独立した版がある。`.muro` が宣言する版は記法と意味論を数え、npm package の版は処理系と公開 API を数える。正準 JSON も綴りの版を別に持つ。三つを同じ数字へ揃える理由はない。

現在の実装は `@kensnzk/koyu` 0.17.0 であり、`muro 1.1` と `koyu-canonical/1.1` を実装している。次の仕事は muro の数字を動かすことではなく、koyu core 1.0.0 で守れる公開面を作ることである。

現行の TypeScript root は core、判定、描画、内部配管を一つの面から公開している。建築的判定は閉じた規則台帳を固定順で実行し、管轄、基準日、外部条件、第三者規則を受け取れない。CLI と MCP には同じ問いを別々に計算している箇所もある。この状態で 1.0.0 を名乗れば、整理前の境界を凍結する。

一方、改修を完成させただけで直ちに 1.0.0 を名乗ることもできない。型検査と単体試験が緑であることは必要条件だが、配布物からの import、CLI、stdio MCP、外部規則パック、文書、examples、canonical JSON、Form、実際の利用側まで同じ契約を見ていることの証明にはならない。

## 決定

**公開 API の大改修は koyu core 0.18.0 として完成させ、0.18.0 の全表面を実証した後にだけ 1.0.0 へ昇格する。**

### 1. muro と koyu core の版を結び直さない

本改修の基準は次のとおりである。

| 版 | この改修での扱い |
|---|---|
| muro | 独立して数える。現行の意味論を維持し、API 整理だけを理由に動かさない |
| koyu core | 0.17.0 から 0.18.0 へ進める。最終目標は 1.0.0 |
| canonical JSON | 独立して数える。綴りが変わらない限り動かさない |

`muro 1.1` か `1.2` かは、同じ原本が意味する建物が変わるときに決める。koyu core が 0.18.0 か 1.0.0 かとは無関係である。

### 2. 0.18.0 で必要な修正を完遂する

0.18.0 を「新 API を足すだけの途中版」にはしない。新しい公開面へ TS、CLI、MCP、scripts、eval、skills、examples、公開文書、テストをすべて移し、不要と決めた旧 export、旧判定契約、重複計算、互換ラッパーを同じ変更で撤去する。

後日に残すのは、実装上必要な修正ではなく **0.18.0 を実際に届けて観測した後の版昇格だけ**である。未完の実装を「1.0.0 までに直す」として残さない。

### 3. 0.18.0 の受入条件を証拠で判定する

0.18.0 は、少なくとも次を満たすまで完成としない。

- 公開 subpath と全 export が一つの機械可読台帳にあり、実装・package exports・公開文書と集合一致する
- root は最小の基本ループだけを持ち、判定、描画、Node 専用処理、内部配管を再輸出しない
- core、解析、判定、presentation、Node adapter の依存方向がテストで固定される
- 規則と解析の拡張契約を、パッケージ内部へ依存しない外部 fixture が実際に利用できる
- TS API、CLI JSON、MCP structured result が同じ operation の同じ意味を返す
- CLI と MCP が独自の閾値や面積算入を再実装しない
- 全 examples の canonical JSON と Form が、言語変更を別途決定しない限り改修前と一致する
- `npm pack` した tarball を空の一時 project へ導入し、全公開 subpath を import できる
- browser-safe root と Node 専用入口の境界が保たれる
- runtime dependency はゼロのままである
- published documentation が現在の契約だけを自己完結して説明し、手で数えた台帳を持たない
- repository の全 gate が成功する

### 4. 1.0.0 は 0.18.0 の昇格であり、別の再設計にしない

1.0.0 へ進む条件は、0.18.0 の受入条件に加えて、公開した 0.18.0 を対象に次を確認できることである。

- npm から取得した配布物で package smoke test が再現する
- CLI と stdio MCP の実利用が文書どおりである
- 少なくとも一つの外部 consumer と一つの外部 rule pack が公開 subpath だけで動く
- 0.18.0 の利用で見つかった契約上の修正がすべて回収されている
- 1.0.0 で守らない面が公開文書に明記されている

昇格時に API をもう一度設計し直さない。0.18.0 は 1.0.0 候補そのものであり、観測で欠陥が出た場合だけ 0.x のうちに直す。

### 5. 証拠の置き場所を分ける

本 ADR は理由、決定、却下案、受入条件を持つ。実行したコマンド、実測値、export の前後差分、各 gate の結果は日付つきの作業ログへ置く。公開文書は履歴を語らず、利用者へ約束する現在形だけを書く。テストは約束を機械的に固定する。

## 代替案

**改修後すぐ 1.0.0 を名乗る。**棄却する。repository 内の green だけでは、配布物、外部 consumer、stdio MCP、外部 rule pack を見たことにならない。

**互換 API を 0.18.0 に残し、1.0.0 で削除する。**棄却する。二つの公開面が並ぶ期間に古い入口が新しい利用者へ広がり、削除判断の文脈も失われる。必要な移行と削除は 0.18.0 の中で完遂する。

**muro の版を koyu core 0.18.0 または 1.0.0 に合わせる。**棄却する。記法の意味論と処理系 API の成熟度は別の約束である。

**0.17.x のまま改修する。**棄却する。公開面を全面的に切り替える版を、既存 0.17.0 の patch として扱うことは変更の大きさを正しく伝えない。

## 帰結と代償

0.18.0 には破壊的な API 整理が入る。0.x のうちに支払うべき費用であり、全 repository consumer を同時に移す。

1.0.0 までに公開版を一つ余分に経る。代わりに、1.0.0 は「テストが緑だった面」ではなく「配布して全入口を見た面」を凍結する。

作業量と証拠量は増える。だが、どの面を見たかが残らないまま 1.0.0 を名乗ることの方が高くつく。
