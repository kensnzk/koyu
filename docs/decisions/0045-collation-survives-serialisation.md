# ADR-0045: 照合順は直列化を生き延びなければならない — 整数に見えるキーの破れを閉じる

日付: 2026-07-30 / 状態: 採用 (v0.16.0、機械形式 `koyu-canonical/1.0` は据え置き) / 起点: [機械形式の規範](../reference/json/index.md) / 関連: [ADR-0036](0036-machine-format-version.md) (機械形式と形式版)・[ADR-0013](0013-canonical-json.md) (正準JSON)

## 文脈

[機械形式の規範](../reference/json/index.md)は「原本に由来するキー (レベル名・パス・アセット名・属性キー) は**照合順**に並ぶ」と約束し、照合順を「符号位置の昇順であり、これは出力される UTF-8 バイトの昇順に等しい」と定める。そして **JavaScript の罠を一つ、名指しで避けている** — 「`<` と既定の `sort` はここでは使えない」。その理由の例として 𠮟 (U+20B9F) と 﨑 (U+FA11) を挙げ、実装は `compareCanonical` を持っている。

**罠は二つあった。**

`sortObj` は `compareCanonical` で正しく並べた後、結果を `Object.fromEntries` に通していた。**JavaScript のオブジェクトは、整数に見えるキーを、挿入した順に関わらず他のキーより前へ、しかも数値の昇順に並べる。**だから `2` と `10` という名のレベルは、正しい並べ替えの後で `2` が先に出た。照合順なら `"1" < "2"` なので `10` が先である。

実測 (`2ca4d97`)。`check` は緑 (終了コード0) のまま通った。

```text
level 2 0 h:2700 slab:150
level 10 3000 h:2700 slab:150
→ "levels": { "2": {...}, "10": {...} }     照合順なら "10" が先
```

アセット名でも同じである。空間・ゾーン・敷地形状のキーはパスで `/` から始まるので、整数に見えることはない。属性キーは台帳の語 (小文字英字) か名前空間つき (ドットを含む) なので、これも該当しない。**露出するのはレベル名とアセット名の二つだけ**だが、露出した場合の出力は形式の規範に反していた。

**規範が予期した罠を避けて、別の罠に落ちていた。**しかも `compareCanonical` は正しく、テストも「代用対で正しく並ぶ」ことを縛っていた — 縛っていた場所の**後**で並びが崩されていた。

## 決定

**照合順を保つ容器は、キーの並びに規則を持たないものでなければならない。**

1. **原本に由来するキーを持つ器を `Map` にする。**`spaces` `zones` `assets` `polygons`、そして `sortObj` の返り値。`Map` は挿入順をそのまま保ち、整数に見えるキーの規則を持たない。
2. **`canonicalStringify` を書く。**`JSON.stringify(value, null, 2)` と**同じバイト**を出し、加えて `Map` を挿入順で直列化する。`JSON.stringify` は `Map` を `{}` にしてしまうので、置き換えが要る。
3. **規範に二つめの罠を書く。**この形式は他言語で実装されることを前提にしているので、罠は言語ごとに違う。規則は「言語の既定に従う」ではなく「符号位置の昇順」だと読ませる。

## 形式版は上げない

**`koyu-canonical/1.0` を据え置く。**理由は一つで、**形式は変わっていない**からである。

規範は最初から照合順を約束していた。変わったのは実装が規範に**従うようになった**ことだけである。整数に見える名を持つ文書が以前受け取っていたバイトは、この形式が認めた綴りではなかった — つまり適合する出力は一つも変わっていない。

**同梱例10件すべてでバイトが完全一致することを確かめた** (`two-rooms` `office` `mansion` `house.muro` `house/` `basement/` `tower/` `complex/` `twin/` `comparison/`)。`sortObj` と直列化の入れ替えは、適合する文書について観測できる変化を持たない。

版を上げる読み方もありうる — 規範の「majorは既存の綴りが変わったとき」を字義通りに取れば、整数に見える名を持つ文書のバイトは変わる。**その読み方を採るなら一行の変更である** (`CANONICAL_FORMAT`)。ここで据え置きを選ぶのは、「形式の版は形式の変更を数える」という定義に忠実な側だからである。適合していなかった出力の訂正を major と数えると、以後「バグを直すと major が上がる」ことになり、版が形式について何も言わなくなる。

## 帰結

**テスト自身が同じ罠に落ちることを確かめた。**回帰テストを最初 `JSON.parse` の結果に対して書いたところ、修正の前後どちらでも落ちた — パースして得たオブジェクトの `Object.keys` は、まさにこの規則を再適用するからである。**並びは生のテキストから読まなければならない。**このことは規範を読む消費者にも効くので、テストにその旨を書いた。

**残る機械形式の破れは一つである。**通り参照の綴りが素通しするため、幾何的に同一の建物が別バイトの正準形を持ち、`koyu diff` が幻の変更を報告する。これは実装の誤りではなく**設計の判断** — 規則3 (書かれた表記の保存) がそう定めている — なので、直すなら「正準形は幾何の上で正準か、綴りの上で正準か」を決め直すことになる。別に扱う。
