# 根底の再検討 — 外部レビュー吸収後の方向 (2026-07-25)

- 位置づけ: **提案**。[2026-07-25-evaluation-and-direction-plan.md](2026-07-25-evaluation-and-direction-plan.md) の続編にあたる。レビュー対応 (v0.9/v0.10, ADR-0013〜0018) が着地した時点で、muroとkoyuのあり方そのものを問い直す。同日の設計対話 — 通り芯オフセット批判・読みの原則・「空間を区切る線を描く行為が設計である」— を吸収する。
- 採用する項目は、リポジトリの規律どおり **ADR (なぜ) + テスト (保証) + spec (現在形)** の三点セットへ落として初めて決定になる。
- 対象: v0.10 (言語版0.2、テスト161本、実装約4,200行、診断コード49)。

## 0. 要旨

1. **刷新は正しかった、そして完了した。** v0.9/v0.10はレビューの「機能を増やす前に意味を固める」を全件回収した。結果として、言語版の分離 (0.1の条件つき受理)・正準性のproperty test・semantic diff・severity固定の診断コードという、**根底を動かすための安全網が、動かす前に揃った**。これは偶然ではなくレビューの順序の帰結であり、刷新の最大の価値はここにある。
2. **しかし最大の問いは、二択のまま残っている。** レビュー§3.2は「形はソースではなく生成物」という主張と実体の距離を突いた。距離の埋め方は二つある — (a) 主張を実体へ合わせる (文言の校正)、(b) 実体を主張へ近づける (位置の導出化)。リポジトリは(a)を選び、READMEは今「原本に書かれるのは空間の領域と境界の関係」と言う。**これは現在形の正確な記述であって、終着ではない。方向は(b)である。** 根拠と工程を本文に示す。
3. **順序を一つ正す。最大の未回収は編集evalであり、v0.9/v0.10の全てはその前提整備だった。** evalは30,000㎡を待たず、towerで今やる。baselineの数字が、以後の記法変更の効果を測る対照群になる。

## 1. 現在地 — 刷新の評価

### 1.1 実体を動かした唯一の変更 — ADR-0014が方向の原型である

v0.10の五本のADRのうち、四本 (uid・診断契約・言語版・semantic diff) は装備であり、一本だけが意味論を動かした。ADR-0014「接する空間の既定は壁」— 宣言は例外と属性のためにあり、**未宣言の接触は導出される**。

これは本文書が示す方向 — 書かない、導出する — を、**関係の層で先にやって成功した実例**である。注目すべきは正直に記録された代償: examplesに素のwall行は1本も無く、この変更で記述は1行も縮まなかった。価値は簡潔さではなく**意味の完全性** (「未宣言=未定義」を「未宣言=壁」にした) にあった。位置の導出化にも同じことが言える見込みが高い — 縮むのはトークンではなく、原本と生成物の境界の曖昧さである。

### 1.2 安全網の完成

根底を動かす変更 (言語版0.3) を安全に行うために必要な装備が、v0.10で全部揃った:

- **ADR-0017**: 「意味保存の場合のみ旧版を受理」を機械判定にする枠組み。0.2→0.3の移行はこの枠組みの二度目の適用になる。
- **正準性のproperty test**: 「意味同一⇒バイト同一」が常時検証される。位置の表現を変えても、この不変量が壊れれば即座に分かる。
- **ADR-0018 semantic diff**: 記法変更の前後で `koyu diff` が空なら意味保存 — 移行の検証装置そのもの。
- **ADR-0016 診断コード**: 新しい検査 (導出の過剰決定など) を、既存の照合を壊さず足せる。

**刷新は、根底の変更を可能にするために先に必要だった工事**だと総括できる。

### 1.3 抑制の判断は正しかった — ただし警戒が一つ

P1の大半 (CST/AST・LSP・formatter・portal graph・多重zone・template/instance・composition拡張) を「コーパスが要求するまで」で止めた判断は、レビュー自身の§10と整合し正しい。維持する。

警戒すべきは**校正の固定化**である。P0-12の文言修正 — 「空間の領域は原本」— は誠実だが、これが自己定義として恒久化すると、原稿の中心主張 (形は生成物) を静かに放棄したことになる。校正は「今の実体の正確な記述」であって「目指す実体の宣言」ではない。この区別を失わないことが、本文書の第一の目的である。

## 2. 残された二択 — 校正か、実体化か

### 2.1 二つの批判が同じ点を突いた

外部レビュー§3.2: 「形はソースではなく生成物」に対し、空間の矩形領域は原本に直書きされている — ビルドが計算するのは壁線分・接合・面積・図の**実体化**だけである。

同日の設計対話は同じ点を別の角度から突いた: **グリッドが座標より賢いのは共有されている時だけ**である。参照が一度しかないオフセットは座標の変装であり、通り芯がX,Y一本ずつまで痩せた極限では、オフセットは座標指示と完全に等価になる。「直交グリッドに絞ったから形を書かずに済んでいる」だけなら、主張は制約の効果を語り直したものにすぎない。

**批判の正体は「位置か寸法か」である。** `X2+1600` は位置 (原点からの距離) であって、設計者が決めたもの — 寸法 — ではない。設計者が決めているのは「水回りは1600」「廊下は1800」「残りがLDK」であり、位置はそれを並べた**帰結**である。オフセットは座標系の中で位置を刻む道具にすぎず、設計の言葉ではない。付け焼き刃感の正体はここにある。

そしてこれはBIM全体の構図の反復でもある。**Revitは寸法を入力させ、座標を保存する。** 仮寸法に打った1600は入力補助として消え、モデルに残るのは壁の配置と形状 — 結果である (ロックした寸法・EQ拘束は座標の上に後付けされる第二の層で、脆く、実務で多用されない)。IFCに出せば `IfcWall` は配置と形状だけを運ぶ。帰結は日常に現れている: 半年後に「水回りは1600だったか」を確かめるには、自分が設計した建物を測るしかない。**自分で書いた数字を成果物から測り返している。**

原稿の論法がここで一段完成する。CADは図面の線を捉えて読みを捨てた。BIMは意味を持たせて**寸法という行為**を捨てた。どちらも入力を捨てて出力を保存している。**BIMは寸法を入力させ座標を保存する。koyuは寸法を保存し座標を生成する。** 系として「往復互換を捨てる」方針の意味も変わる — IFCから本当に戻したいのは捨てられた入力であり、入力の側を原本にするなら復元する対象がそもそも無い。我慢ではなく不要になる。

**そして水平だけが取り残されている。** 垂直方向のkoyuは既に寸法で書かれている: `level L1 0 h:3600 slab:600` — `levels` が出す矩計は天井高と床組み厚を積み上げた帰結であり、位置は導出されている。ADR-0014が「垂直は既定が床なのに水平は全部宣言」という非対称を直したのと、**同じ形の非対称がもう一つ残っていた**。

### 2.2 (b) 実体化を採る三つの理由

1. **前例が成功している。** ADR-0014が関係の層でこれをやった (§1.1)。位置の層で同じ手が使えない理由はない。
2. **主張の強度。** 「原本に書かれるのは決定であり、幾何は帰結である」が、言い訳なしで言えるようになる。校正された現在の文言は防御であり、導出化された後の文言は攻撃である。
3. **LLM適性。** 間取り生成のRLVR研究 (arXiv 2605.14117) は「座標を持たせるとLLMが壊れる」ことを示した。ソースから数値を減らす方向は、この知見と同じ側にある。ただしこれは仮説であり、§5のevalで測る — 導出はソースから数値を消すため、「事務室の東端はどこか」の読み取りコストが増える可能性がある。事前に決められない。

### 2.3 測度 — 書かれた位置と導出された位置

方向を趣味の問題にしないため、最小限の観測だけ持つ: 展開後モデルの位置決定のうち、**ソースに数値が書かれているもの** (通り参照+オフセット) と**導出されるもの** (幅・比・残り・所与線) の比。現状、後者は0である (位置については。関係についてはADR-0014の既定境界が既に導出)。用途は0.2と0.3の前後で実体が動いたことの確認に限る — **観測であって目標ではない。** 上げること自体を完了条件にすると、読めない導出を書く動機になる (§7)。

## 3. 根底の言い直し — muro・koyu・線

### 3.1 muroとkoyuの分業

- **muro (.muro) = 決定の記法。** 設計者が決めたこと — 空間の名前と用途、境界の関係、共有される線、所与の線、宣言された量 (幅・比・性能) — を、決定の単位で書く。
- **koyu = 導出と検査の体系。** 決定から帰結 — 形・面積・壁線分・図・グラフ・診断・射影 — を計算する。

羅針盤を一文にする: **koyu (導出) からmuro (記述) へ情報を移す変更は疑い、逆を歓迎する。** 例外は二つだけ — **所与** (世界から来た事実。敷地polygon, ADR-0011) と、**構成の事実** (読んで分かるべきこと。§3.2)。

### 3.2 読みの線引き

同日の対話で確立した原則: **構成に属する事実はソースに書かれ、幾何に属する事実はビルドが導出する。** どの空間があるか、何と接するか、境界が斜めか、どこからどこへ — は構成であり、ソースを読んで分かる必要がある。頂点座標・面積・壁線分の位置 — は幾何であり、導出される。

この線引きは§3.1の羅針盤と両立する。導出化 (幾何をmuroから出す) と可読性 (構成をmuroに残す) は矛盾しない — 対立するように見えたのは、clip案のように**構成の事実を幾何側に隠した**ときだけである。

### 3.3 位置の原理 — 位置ではなく寸法と並びを書く

**位置そのものは書かない。位置を決める要因を書く。** 中心の要因は**寸法と並び**である。§2.1の非対称を解けば、原理は一文になる — **垂直の矩計 (順序+寸法の積み上げ) を水平へ拡張する。**

帯 (一次元の並び) を宣言し、寸法で埋める。構文はADRで決めるが方向はこれである:

```
chain X1+3200..X3 Y1+4000..Y2 dir:X    # 帯: どこからどこまでを、どちら向きに割るか
  /L3..L10/A/wet  wet  w:1600
  /L3..L10/A/hall hall w:1600
  /L3..L10/A/ldk  ldk  rest            # 残りを吸収するのは一つだけ
```

現状のtowerは同じことを `X1+3200..X2+1600` / `X2+1600..X2+3200` と位置で書いている。消えるのは設計判断ではなく**判断の帰結**である。規則は導出の原理そのまま — 一方向・順序付き・決定的。`rest` は帯に一つだけ、寸法の合計が帯を超えたらエラー、`rest` が無くて足りなければエラー (過剰決定と不足がどちらもcheckで止まる)。**ソルバーではなく足し算である** (パラメトリックCADの果実=編集の伝播だけを取り、代償=多解・脆さを払わない)。

**依然として書かれるもの** (正直に線を引く): 通り芯の座標 (最初の錨。構造グリッドは共有されるので名前を持つ線として書かれて正しい) / **寸法そのもの** (1600は決定である — 減らす対象ではなく、**置き場所を位置から要素へ移す**だけ) / 所与 (敷地形状) / 帯に乗らない位置 (雁行の出入り等) と構成の事実 (斜め)。**減るのは「原点からの距離」だけである。**

要因の残り二種は**名前** (共有される位置は名前を持つ — 副芯) と**所与**であり、位置を定めるものを線として見ると、出自が三種あるだけである:

- **共有線** — 通り芯・副芯。名前を持ち、宣言一回・参照N回。**グリッドは記法の土台から、共有線という特殊例に降格する。** 「通り芯から設計しない」という違和感の正体は、特殊例を土台と偽っていたことにある。
- **所与線** — 敷地polygonの各辺。世界から来る。
- **描画線** — 設計の行為そのもの。「人は空間を区切る線を描くことで曖昧な境界を実体のものとする」— 一つの設計判断が一行になる。境界は関係のまま (位置を持たない関係文)、線はその**実現**であり、導出 (隣接から) が既定で、描かれたときだけ上書きされる。

### 3.4 レビューの枠との合流

レビュー§4.8はこう言った: 「現在は共有辺・重なり・面積・敷地判定・図面生成が矩形代数へ直接依存する。斜め対応が新しいregion型の追加ではなくモデル全体の書換えになる。Coreをgeometry backendから分離せよ。非直交はコーパスが要求するまで実装するな」。

線の三出自はこの助言と競合しない — **三出自はレビューの言うLayout層の意味設計であり、§4.8はその実装戦略である。** Core (空間・関係・接続) は線を知らず、Layout (線とセル) が位置を担い、geometry backend (矩形区間代数、将来はarrangement) が計算する。レビューは器の分離を求め、対話は器に入れる中身を決めた。

### 3.5 再検討による一つの自己修正 — 斜めは契機であって本体ではない

同日の議論は「設計された斜め」を出発点にしたが、一歩引いて計画中のコーパスを見ると: 地下例が要求するのは斜路 (垂直の話)、中間規模・特大が要求するのは所与の斜め (敷地・隅切り) までであり、**設計された斜めを実際に要求する実例はまだ一つも無い**。

したがって:

- **ADRは今書く。** 三出自・読みの線引き・位置の原理・限界 (ソルバー不採用、自由形状は生息域外、振れた棟は保留) — 判断は安い。描画線の記法の方向 (`boundary` 配下の `line X3Y1..X4Y3`、端点はグリッド語、角度・生座標なし) もADRに記す。
- **実装は分ける。** 今実装するのは**直交にも効く部分だけ** — 主役は**帯と寸法による導出** (§3.3。オフセット批判への直接の答えであり、証拠待ちの必要がない — 矩形の区間代数の中で完結し、arrangement計算も不要)。**副芯の命名は副産物**であり、共有の話しかしていないのでこれ単体では批判への答えにならない。
- **描画線 (arrangement) は証拠待ち。** コーパスが設計された斜めを実際に要求した時、geometry backendの分離の上で実装する — レビューの規律 (Phase E) をそのまま適用する。矩形代数→arrangementの書換えは現存する最大の実装コストであり、要求の無いうちに払わない。

線の議論の本体は斜めではない。**グリッドの再解釈 (共有線への降格) と導出の導入** — 直交の建物に今日から効く部分 — が本体である。

## 4. レビュー路線への抵抗線

刷新の勢いでP1へ進む重力に、明示的に抗う。採用条件は方向性計画§2.1の「towerコーパス・MCP eval・外部検証が実際に要求するもの」を維持し、これに「**導出を進めること**」を加える。

**引き続き作らない**: CST/AST・formatter・LSP (利用者は作者とLLMのみ — LLMは診断コードとdiffで足りている) / composition演算の拡張 (加算のみ) / Program層 (原本は解決済みの決定。検証可能な意図は `compartment` の閾値引数のようにクエリのパラメータで受ける — 新しい層は作らない) / portal graph (避難profileの段まで) / 性能index (基準測定が数字で要求するまで)。

**待ち構える** (計画中のコーパスが証拠を出す見込みが高いもの — 出たら最小形で採用する):

- **多重zone** (レビュー§4.3, P1-07) — `compartment` クエリ (区画) は、防火区画・テナント・避難区画が一つのパス階層に収まらない現実に当たる可能性が高い。当たった時点で明示membershipを最小に足す。
- **vertical extent** (§4.7, P1-14) — 地下と斜路がレベル既定床の意味論を揺らす可能性。
- **as-built上書き合成** — ツイン軸の第一歩のまま (ADR-0010の保留の回収)。

この「待ち構え」の含意: 特大複合建築のコーパス作りは規模のデモではなく、**保留したレビュー項目に証拠で決着をつける装置**である。エピックとレビューはここで合流する。

## 5. 順序の修正 — evalを前へ

現行の暗黙順序 (エピック) は 地下→語彙→区画→距離→中間→特大→eval だが、これを正す: **baseline evalはtowerで、今やる。**

理由は三つ。①レビューP2-03も docs/horizon.md の分水嶺も、evalをtowerで定義している — 30,000㎡は不要である。②v0.10の成果物 — semantic diff (採点装置)・診断コード (失敗分類)・uid (改名課題)・MCPの門番 (transaction) — は**全部evalの計測装置**であり、装置が揃った直後が測り時である。③以後の記法変更 (0.3) の効果は、前後比較でしか測れない。導出化がLLMの編集を楽にするか難しくするか — 数値の書き間違いは減るが位置の読み取りコストは増える — は事前に決められず、baselineが無ければ永遠に答えが出ない。

修正後の工程:

```
1. baseline eval        tower・言語0.2。BIM-Edit型分類 (create/update/delete ×
                        direct/spatial/topological) を .muro に移植し、
                        オラクル多重 (check+light+doors+compartment) で報酬ハックを塞ぐ。
                        採点に koyu diff を使う (可読性の人手判定を補助)
2. ADR-0019 (仮)        位置と線 — 三出自・読みの線引き・導出の原理・限界。言語0.3を予約
3. 実装第一波           帯と寸法による導出 (chain)。直交で完結、arrangement不要。副芯の命名は副産物。
                        examplesで意味保存 (diff空) を検証
4. エピック続行          basement → 語彙 → compartment → …。多重zone /
                        vertical extent の要求が出たら§4の待ち構えを発動
5. 描画線               コーパスが設計された斜めを実際に要求した時。
                        geometry backend分離の上で
6. re-eval              0.2と0.3の前後比較 — 「記法の設計がエージェントの
                        成功率に効くか」の直接測定。論文の柱
```

## 6. 変えないもの

根底を動かす議論だからこそ、核を先に固定する:

- **境界=位置を持たない関係の層。** `boundary /a /b t:120` はどこに壁があるか言わない — クエリ・diff・編集がこの言語で済む。同日の対話でも、線の導入がこの層に指一本触れないことを確認した。muroの良さの中核はここである。
- 一行一文 / パス=アドレスと集計 (uidは寿命の長い参照, ADR-0015) / checkの門番 / 依存ゼロと小ささ / 一棟が一つのコンテキストに入ること。
- 三点セットの規律 (ADR+テスト+spec) / 「やらないこと」台帳 (オーサリングツール・往復互換・曲面・動的データ・事業化)。
- 解像度は基本計画レベル — 導出化は解像度を上げる方便ではない。

## 7. リスクと反証可能性

- **導出の読み取りコスト。** ソースから数値が消えると、LLMも人も位置を即読できなくなる。→ §5のbefore/afterで測る。悪化したら導出の適用範囲を縮める — この変更は可逆に設計する (導出とオフセットを併存させ、どちらで書くかを強制しない)。
- **arrangement実装の重さ。** レビュー§4.8の警告どおり、描画線は矩形代数の全面書換えである。→ 証拠待ち (§3.5) で先送りし、geometry backendの分離を保険にする。
- **線の乱用。** 描けるなら何でも描く、に流れると座標の変装が線の変装に変わるだけ。→ 「描画線の本数=設計判断の数」を規範として持つ (描画線を実装する段の課題)。
- **校正の再発。** 0.3でまた主張が実体を超えたら、同じ手続き — 外部レビューと全件検証 — で戻す。今回それが機能したことは記録に残っている。
