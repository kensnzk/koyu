## 0. 要旨

レビューの全主張を、対象コミット上で実際に検証した (全ソース読解・テスト99/99実行・最小ケースによる動的再現・npmレジストリとgitの実測)。結論:

1. **レビューは高品質で、大筋正確である。** 実装指摘 D-001〜D-011 は11件中10件が事実として確認できた (うち2件は本検証でさらに補強される)。残り1件 (D-006) は誤りではないが、仕様化済み挙動を暗黙挙動のように扱っており位置づけの補正が要る。設計批評 (§3〜§7) も実装と整合する。
2. **従うべき核心は「機能を増やす前に、意味を固める」である。** 正準JSONの意味保存 (D-001/D-002)、境界の同一性 (D-003)、検査の穴 (D-004/D-005)、MCPの書き込み規律 (D-008/D-009)、版とリリースの規律 (D-011) は、いずれも「同じ記述への複数の問い」「diffとレイヤー合成の土台」というkoyu自身の約束を裏切る欠陥であり、次の機能より先に塞ぐ。
3. **ただし全面採用はしない。** レビューのバックログ (P0〜P3、計50項目超) をすべて実装するとkoyuは小ささを失う — レビュー自身も§10でそう警告している。採用基準を「**towerコーパス・MCP eval・外部検証が実際に要求するもの**」に固定し、P0全件 + ADR4本 + 絞ったP1を先行し、残りは外部検証 (Phase C) の結果を待つ。

### 1.3 設計批評 (§3〜§7) の判定

事実に関わる主張はすべて実装と照合した。主なもの:

- **§3.2 主張と実際の乖離の表 — 支持。** 「形はソースではなく生成物」(README.md:8) に対し空間の矩形領域は原本に書かれる、「パスが同一性」(spec/language.md:39) はrenameで壊れる、「USD流」(README.ja.md:34) は実際には加算合成のみ (ADR-0010自身が「レイヤー強度は今は採らない」と明言) — いずれも文言と実体の距離の指摘として正確。
- **§4.4 境界の手書き — 確認。** towerは163本のboundary行 (展開後542) を手書きし、未宣言は警告どまり (`src/check.ts:86-88`)。「悪い中間」という評価は妥当で、ADRで決めるべき (§2.3)。
- **§4.6 doorsの粒度 — 確認。** 辺はboundary単位、wallは扉1枚以上で通行可・コストは扉数と無関係に1 (`src/graph.ts:265-275`)、経由した扉は返らない (`Route` は空間パス列のみ)。
- **§5.1 バージョン混在 — 確認。** `koyu 0.1` 宣言はパーサが検証せずそのまま格納 (`src/parse.ts:151-153`)。仕様書はv0.8.0、npmは0.5.0。
- **§6.5 丸め — 確認。** `areaM2` が空間ごとに0.01㎡へ丸め (`src/model.ts:265`)、ゾーン集計は丸め値の合計。specに丸めの規定は無い。
- **§6.6 アルゴリズム — 確認。** `queue.sort` がループ内 (`src/graph.ts:291`)、popごとのboundary全走査 (`:295`)、空間重なりの全組合せ走査、`segmentsFor` のメモ化なし。「都市スケール」の主張と実装の距離の指摘として正確。
- **§7 外部標準 — 妥当。** BOT/IndoorGML/IFC/IDS/bSDDの性格づけは一次資料と整合し、「IFCにも空間境界はある。koyuの新規性はそれをauthor形式の中心に置いたこと」という主張の強化 (§7.3) は、docs/ifc-coverage.md の自己認識とも一致する。

## 2. 方向性の修正計画

### 2.1 守るもの (変えない)

レビューの採否を判断する前提として、koyuの価値の核を固定する:

- **空間一次・境界=関係・部材形状は生成物** という中核主張 (表現は§2.2で校正する)
- **小さい実装・依存ゼロ・ステートレスMCP**
- **ADR + テスト + spec の三点セット規律**
- **直交グリッド限定・オーサリングツール非構築・動的データ非搭載・往復互換の放棄** (docs/roadmap.md の「やらないこと」)

レビュー§10「すべてのIFC概念を追加するとkoyuの価値が失われる」はこの前提と同じ側にある。以下の採否はすべて「towerコーパス・MCP eval・外部検証が実際に要求するか」を基準にする。

### 2.3 先に決めるADR (4本)

レビュー§13の15問のうち、Phase Aの実装が依存する4問を先に決める。残り (Q1, Q6, Q8, Q9, Q10, Q11, Q12, Q15) はPhase Cの外部検証の入力を待って決める。

**ADR-0014 境界の既定** (§13 Q3, Q4, Q7を吸収)
接する空間にboundaryが無いとき: 案A=既定wallを導出し例外だけ書く / 案B=必須化 (エラー)。**推奨は案A**。「床は書かない — 既定は床。例外だけ宣言」(spec/semantics.md:19) という垂直方向の意味論と対称になり、towerの163本の境界手書きの大半が消え、「壁は導出」の主張が水平でも実体を持つ。現状の「不足しても警告」は廃止する。

**ADR-0015 同一性** (Q2, Q5)
パス主義 (spec/language.md:39) は維持する — 可読アドレスとしての価値、docs/horizon.md:33「パスがそのまま意味である」という外部キー戦略は正しい。その上で、**rename耐性が必要な利用者向けに任意の `uid:` 属性を予約**する (パスから導出しない、重複はエラー、正準JSONに保存)。センサー連携・長期運用のjoinはuidを推奨し、パスはアドレスと集計の階層に役割を限定する。sidecar台帳はコーパスが要求するまで作らない。

**ADR-0016 診断契約** (Q13の一部、D-007の恒久解)
diagnosticへ `code` / 規範severity / `file`+`range` / `related` を導入し、specに診断コード台帳を持つ。specと実装のseverity不一致はconformance testで検出する。CLIは現行の日本語文字列を人間向け表示として保ち、`--json` で構造化診断を返す。

**ADR-0017 言語版と互換** (Q14)
language version (`koyu 0.1`) / tool・package version / canonical schema version を分離して定義し、**パーサは未対応のlanguage versionを拒否**する。言語を変える変更はlanguage versionを上げ、fixtureで移行を検証する。

### 2.5 Phase B — 言語基盤 (絞って先行)

**先行して採用** (Phase Aの延長として小さく入る):

- **warning policy / `--strict`** (P1-19): CI用に「警告で失敗」「コード別deny/allow」。ADR-0008:23が既に予告している `check --strict` の回収
- **lint最小** (P1-04の一部): 未知語彙のopt-in警告 (vocabulary.mdとの突き合わせ)。自由語彙は既定では守る
- **ADR-0014の実装** (境界の既定): 意味論の変更なのでlanguage versionを上げる最初の実例になり、ADR-0017の運用試験を兼ねる

**保留** (外部利用者・コーパスの要求まで作らない — レビューPhase E原則「Coreを壊さない境界を作るのが先、実装はコーパスが要求してから」の一般適用):

- CST/AST・formatter・LSP・rename (P1-01,02,03,05) — 現在の利用者は作者とLLMのみで、diffの土台は正準JSON側 (P0-01/02) が先
- semantic diff / merge (P1-20,21) — uid (ADR-0015) と正準JSONの意味保存が前提。その後に
- template/instance (P1-17)、units/quantity (P1-12)、座標系・複数グリッド (P1-13 — 測地はPhase Dの都市接続と同時)、vertical extent (P1-14)、portal graph (P1-09,10)、多重zone membership (P1-07)

### 2.6 Phase C — 外部の建築で壊す (採用 — 既定路線と合流)

レビュー§12 Phase Cは、docs/horizon.md が既に置いている分水嶺「エージェントは設計変更をcheck緑のまま完遂できるか (eval)」の具体化として採用する:

- **LLM edit eval** (P2-03): towerに対する設計変更課題群 (住戸タイプ変更・階の追加・開口変更など) を定義し、成功率・check緑だが意味が誤っている率・tool call数を測る。MCP (ADR-0012) の価値検証そのもの
- **実案件コーパス** (P2-01) と**第三者author試験** (P2-02): 「書けない要素の公開台帳」は docs/ifc-coverage.md の運用をそのまま拡張する
- **比較の公平性** (P2-04): examples/comparison の自己申告 (「徹底的にごまかした理想化最小」) を、同情報範囲のmatched-scope比較へ引き上げる
- **property-based test** (P2-10) は前倒しし、Phase AのP0-02の受け入れ検証に使う

### 2.7 Phase D — 射影 (roadmapへIndoorGMLを追加)

docs/roadmap.md の既定順序 (MCP済 → rdf/BOT → as-built上書き合成 → 測地 → ツインデモ) を維持し、**BOTの次にIndoorGML 2.0射影を追加**する (レビュー§7.2の採用)。理由: 空間中心・CellSpace/CellBoundary・二重グラフというkoyuに最も近い標準であり、経路系の問い (doors) を外部モデルと相互検証できる唯一の相手。前提としてADR-0015 (uid) が先。bSDD/IDS・IFC one-way exportはその後、コーパスの要求で。

### 2.8 採用しない・保留する提案 (理由付き)

| 提案 | 判断 | 理由 |
|---|---|---|
| Program/brief層 (§4.1, P3-01) | **見送り** | koyuの原本は「解決済みレイアウト」だと定義する (ADRで明文化)。要求と実現値の管理は外部profile/requirementsの領分。レビュー自身もP3 (コーパス要求後) に置いている |
| 多重zone membership (§4.3, P1-07) | **保留** | 防火区画・HVACゾーンの問いはまだ存在しない。問いが来たときに、パス階層+明示membershipの形で足す |
| interface/assemblyの分離 (§4.5) | **保留** | 連続壁のグルーピングを要求する問い (熱・音・防火の集計) がまだ無い。ADR-0014で「boundaryは二空間間のinterfaceである」ことだけ先に明文化する |
| portal/connector完全グラフ (§4.6) | **保留** | 当面は doors の評価範囲の明示 (§2.2) で足りる。避難profileを作る段階 (P3-08) で扉単位のedgeへ |
| polygon region backend・非直交 (§4.8, P3-02) | **保留 (レビューと同意見)** | 「斜めを実装するな、Coreを壊さない境界を作れ」に同意。geometry backendの分離設計だけPhase B後半で先行してよい |
| 時間・フェーズ・状態 (§4.11) | **一歩だけ** | 既定路線の as-built 上書きレイヤー (docs/horizon.md、ADR-0010の保留回収) を最初の一歩とし、ライフサイクル語彙はその経験の後 |
| 意図のconstraint化 (§4.12) | **一部採用** | 「検証可能な意図はプロンプトでなく機械可読に」は正しい。ただし新レイヤーは作らず、profile/requirements設計 (IDS参考) の中で扱う。文章的意図をプロンプト側に置く方針自体は維持 |
| 性能インデックス群 (§6.6) | **基準測定のみ先行** | benchmarkを先に置き (P2-13)、数字が要求するまでindex/incrementalは作らない。「都市」の主張は§2.2で先に校正済み |

### 2.9 実施順序

```
A. 意味の正しさ    P0全件 + ADR-0014〜0016           ← 次の機能追加より先
B. 言語基盤(前半)  --strict / lint最小 / 境界既定の実装
C. 外部検証        LLM eval / コーパス / 第三者試験 / matched-scope比較
D. 射影            BOT → IndoorGML → (bSDD/IDS → IFC)
B'. 言語基盤(後半) コーパスが要求したものだけ (CST/AST, semantic diff, ...)
```

各Phaseの完了条件はレビュー§12を踏襲する。Phase Aの間、新しい語彙・新しい要素は追加しない。

## 3. 成功指標 (レビュー§14から実測可能なものへ絞る)

- **意味保存**: 意味同一のモデルがバイト同一のJSONになる / JSONだけからswing・edgeの意味が復元できる (D-001/D-002の解消判定。property-based testで常時検証)
- **検査力**: 矛盾boundary・凹敷地はみ出し・面積不一致が診断コード付きで検出される (D-003/004/005の解消判定)
- **エージェント**: tower edit evalの成功率 / check緑だが意味が誤っている率 / rollback回数
- **相互運用**: BOT・IndoorGML射影のmapping coverageと、同一の問い (面積集計・到達可能性) のquery parity
- **性能**: parse/checkの基準時間とメモリを公開し、空間数に対する増加率を記録する (「都市」を語る前提)

## 付録B — 最小再現ケース

いずれも対象コミット `0d8a8a6` 上、`npx tsx src/cli.ts <cmd> <file>` で再現 (2026-07-25実施)。

### B-1. D-001: 意味の異なる二モデルがバイト同一のJSONになる

```text
# d001a.muro (抜粋)             # d001b.muro (抜粋)
boundary /L1/z /L1/a            boundary /L1/a /L1/z
  door w:800 swing:a              door w:800 swing:a
```

swing:a は「a側 (最初に書いた空間) へ開く」— aは前者で `/L1/z`、後者で `/L1/a`。扉の開く先が違う二つのモデルの `json` 出力は**バイト同一** (`between` が辞書順ソートされ、swingは `"a"` のまま残るため)。JSONからは復元不能。

### B-2. D-002: 記述順でバイト列が変わる

同一boundaryの `door at:0.25` と `door at:0.75` の記述順を入れ替えた二ファイルで、`json` 出力に差分 (openingsが記述順のまま)。意味は同一の集合。

### B-3. D-003: wall/open矛盾がcheck緑で0枚通行

```text
boundary /L1/a /L1/b
boundary /L1/a /L1/b type:open
```

`check` → `✔ 整合 — 空間 2 / 境界 2` (エラー0・警告0)。`doors /L1/a /L1/b` → `0枚` (open辺が最小コストで選ばれる)。

### B-4. D-004: U字敷地を跨ぐ矩形がcheck緑

```text
zone /site site:1 area:480
polygon /site 0,0 30000,0 30000,20000 20000,20000 20000,8000 10000,8000 10000,20000 0,20000
space /L1/hall room X2..X3 Y2..Y4    # 矩形 (2000,2000)-(28000,12000)
```

四隅はすべて敷地内 (`pointInPolygon` 4×true)、矩形上辺の中点 (15000,12000) は敷地外 — 建物が凹部から突き出しているが `check` はエラー0。

### B-5. D-005: 宣言50㎡ vs 導出100㎡でcheckエラー0

`zone /site site:1 area:50` + 10m角polygon。`check` エラー0 (exit 0)。`site` は `⚠ 不一致` を表示するが exit 0。

### B-6. D-006: 属性の後勝ち

`space /L1/a room ... use:first use:second` → `attrs.use === "second"` (エラー・警告なし)。

### B-7. D-009: 兄弟prefixディレクトリへの書き込み脱出

実MCPサーバー (`tsx src/mcp.ts`) に対し、entry `<dir>/proj/main.muro`、`layer: "../proj-escape/x.muro"` で `write_layer` を呼ぶと、`<dir>/proj-escape/x.muro` が作成され `ok:true` が返る。`resolve()` 後の `startsWith("<dir>/proj")` が `<dir>/proj-escape` にも真になるため。

### B-8. D-010: grid/levelのみの層がlayersから欠落

```text
# main.muro                # base.muro (grid/levelのみ)
import ./base.muro         grid X 0 4000 8000
import ./rooms.muro        grid Y 0 4000
                           level L1 0
```

MCP `layers` の列挙は `main.muro` と `rooms.muro` のみ — 合成に参加した `base.muro` が欠落する (grid/levelは出所ファイルを記録しないため)。
