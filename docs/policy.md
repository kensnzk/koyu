# koyu — 方針の総覧

この文書は目的と範囲の規範である。ADR は「なぜそう決めたか」を、spec は「いま何が真か」を持つ。この文書は **「何を目指し、何を分け、何を凍らせるか」** を持つ。判断に迷ったときはここに戻る。

---

# 第一部 — 目的

## 1. 目指すもの

**建物が、機械の視野に丸ごと入る原本を持っている状態。**

そこでは次が起きている。

- 設計する人も、エージェントも、運用する人も、**同じ一つのテキストを読み書きしている。**変換も同期も要らない
- **現実の観測は形を与えるが、意味を持たない。**スキャンは点の集まりであり、そこが何の部屋か、誰と誰の境か、通ってよいかを知らない。意味はこの原本から来て、両者は同一性で結ばれている
- 建物は孤立したファイルではなく、**ネットワークの一点である。**空間と空間、建物と建物、建物と都市が、同じ形の関係で繋がる
- **設計の最初から運用の終わりまで、同じ同一性が続く。**三年前にセンサーが結んだ空間を、いまも同じものとして指せる

これが目的地である。以下のすべての決定は、ここへ向かうためにある。

## 2. なぜこの形なのか

**幾何は、これから現実側から取れる。**スキャン、SLAM、写真測量、splat——形を得る手段は安くなり続ける。取れるようになるものを、わざわざ原本に書いて持つ理由はない。

**点群からは決して出てこないものがある。**ここが何の空間か。この境界は誰と誰の境か。この扉は通ってよいのか。いつからそうなのか。**意味と関係と同一性は、観測では得られない。書くしかない。**

したがってこの記述は、書くしかないものを持つ。**形を原本に持たないことは妥協ではなく、役割の定義である。**

そして、書くしかないものだけを持てば軽い。軽ければ一棟が丸ごと機械の視野に入る。**軽さは目的ではなく、役割から出る結果である。**

## 3. 四つの柱

値打ちは、次の四つを**同時に**備えていることにある。どれか一つを取り出せば、既にあるものと変わらない。

**3.1 自由に書け、機械が丸ごと読める。**空間の構成を一次の主題としながら、それだけですべてを語り尽くそうとはしない。書きたいものが書ける自由を持つ。制約はただ一つ、**一棟が機械の視野に入る大きさであること。**

**3.2 MCP が操作・検証・問いの面である。**読む、書く、確かめる、問う——機械が原本に対してすることは、すべてここから届く。

**3.3 合成が USD のように定義されている。**分担して書く、例外を差分として書く、計画の上に as-built を重ねる。**時間と分担のために合成があり、大きさのためではない。**

**3.4 表現とビルドが分離されている。**原本は意味を持ち、形を持たない。形は消費者が作る。

# 第二部 — 三つの領域

## 4. なぜ分けるのか

**三つの領域は、求められる品質が違う。**

| 領域 | 大きさ | 品質 | 版 | 変更の値段 |
|---|---|---|---|---|
| **core** | 小さい | **きれいでなければならない** | 凍る | 極めて高い |
| **検証** | 大きくなる | **汚くてよい** | 凍らない | 安い |
| **表現・ビルド** | 大きくなる | **汚くてよい** | 凍らない | 安い |

分けないと、二つのことが同時に起きる。**汚さが core に染み出して凍り、core の慎重さが検証と表現の成長を止める。**どちらも避けたい。

**分けることそのものが、汚くてよい条件である。**凍らない領域の汚れは、いつでも書き直せるので安い。凍る領域の汚れは永久に残るので、値段が桁違いに違う。

**依存は一方向である。**検証も表現も core に依存し、core はどちらにも依存しない。core は自分だけで完結して動く。

## 5. koyu core — 小さく、きれいに、凍る

原本の言語と、その意味論と、機械への口。**ここだけが凍る。**

### 5.1 モデル

| 層 | 何か | 座標 | 実体 |
|---|---|---|---|
| **与件** | 通り芯、レベル、敷地形状 | **持つ。唯一の絶対の出所** | 持たない |
| **関係** | 二つの空間の間に何があるか | 与件から一意に決まる | **原則としてここに宿る** |
| **空間** | 名前・用途・意味を担う | 持たない。与件を参照して相対的に位置づく | 持たない |

> **与件が座標を与え、関係が実体を持ち、空間は名を持つ。**

**空間**は、識別子、用途、名称、宣言（採光を要する、屋内である等）、そしてどの区画を占めるか——通り芯への参照であって座標ではない——を持つ。

**関係**は二つの空間の共有面という座を与え、実体はそこに乗る。水平には壁・カーテンウォール・手すり・ガラス間仕切り・開放。垂直には床・天井・スラブ・屋根・吹抜け・階段・スロープ・EV・エスカレーター。厚み、仕様、耐火、遮音、勾配、天端高——実体に属する値は関係が持つ。開口は関係の上の区間として置かれる。

**理由** — 関係は座を与え、空間の属性は座を与えない。実体を空間側に置けば、どの面に乗るかを導出側の規則で補うことになり、そこが曖昧さの入口になる。上下のスラブを、下の空間が天井として、上の空間が床として別々に主張できる状態は原本ではない。**関係なら所有者が一つに定まる。**

**帰結** — 外部は空間でなければならない。屋根が関係であるためには空が、接地する床が関係であるためには地盤が、相手の空間として存在する必要がある。

**与件だけが座標を持つ。**通り芯、レベル、敷地形状は測量と決めごとに由来する所与であり、設計の生成物ではない。**書かれるのは与件であり、書かれないのは設計の生成物である。**これで「形は書かない」と「敷地形状は書く」が矛盾しなくなる。

**関係に宿らない物**——通り芯の交点に立つ柱、空間に置かれる機器——は、型への参照と、どこに属すかで持つ。座を持てるものは与件を座として置かれ、座を持たないものは**どの空間に含まれるかという内包だけ**を持つ。内包からは形が作れない。必要なら消費者が外部の情報から図に起こす。

**理由** — 内包は意味であって場所ではない。逆に内包から場所を導こうとすれば配置の仕組みが必要になり、**この記述は配置の道具になってしまう。**内包が座を与えないと定めることが、その入口を閉じる。

### 5.2 合成の規則

USD に倣い、次を定める。**この六つが揃ってはじめて合成が使える。**

1. **層は明示された強度順序を持つ。**出現順ではなく、宣言された順序。強い層の意見が勝つ
2. **単一の値は、最も強い層の意見が勝つ。**厚みも仕様も用途も、上書きは一つの規則で説明される
3. **集合は、明示された編集で合成する。**追加、削除、置換。暗黙のマージをしない。**同じ座に複数の意見がありうるもの——柱、開口、内包物——はすべてここに属す**
4. **定義と上書きを区別する。**新たに定義する層と、既にあるものへ意見だけを足す層は、別の書き方を持つ
5. **同じ入力からは常に同じ結果が出る。**入力には層とその順序の宣言を含む
6. **出所が追える。**最終的な値を、どの層のどの行が与えたかを示せる

**規則3が、これまで特殊扱いされてきたものを普通にする。**同じ場所に複数の層が意見を持ちうるものは、暗黙の勝ち負けではなく明示された編集で解決される。**特殊なのは値の種類であって、規則ではない。**専用構文を作らない。

**理由** — 問題は合成があることではなく、解決の順序が暗黙であることである。暗黙の解決は、同じ入力から違う結果を生みうる。それは原本ではない。

### 5.3 同一性

**uid を持つのは空間だけである。そして必須ではない。**

- **uid が書かれた空間**は、その uid が正典である。パスが変わっても同じものである
- **書かれていない空間**は、パスで対応づく。改名すれば対応は切れる
- **関係の同一性は、両端の空間から導かれる。**関係に uid を書かない
- **開口と内包物の同一性は、それを含む対象と、その中で一意な名から導かれる**

**理由** — 外部が指したいのは空間である。関係は必ず二つの空間の間にあるので、両端が定まれば関係も定まる。関係ごとに uid を書けば、関係の数は空間の数を上回り、機械の視野に入るという目的を自分で削ることになる。

必須にしないのは、**保証の強さを書き手が選べるようにするため**である。時点をまたいで指す必要がある空間にだけ付ければよい。必要になった時点でツールが生成して書き戻す — **生成は乱数であり、付与は明示の行為である** (自分から uid を書くツールは無い。[ADR-0039](decisions/0039-identity-generation.md))。衝突しないことを保証できるのは合成済みのモデルの中までで、その外は確率でしか保証しない。

**同一性には責任を持ち、内容には持たない。**

### 5.4 属性の三層

| 層 | 例 | 態度 |
|---|---|---|
| **構造** | パス、区画、レベル、関係の相手、種別 | 必ず見る。壊れていれば読まない |
| **解釈** | 天井の高さ、開口の幅と位置 | 台帳が値域を定義し、見る |
| **運搬** | 仕様の自由文字列、勾配、割付、センサー値、実測、点検記録、第三者の任意属性 | **見ない。**名前空間つきで開いている |

**理由** — 開いていることと信頼できることは、境界が宣言されていれば両立する。宣言が無ければ、**見ていないことと、見て問題がないことが区別できない。**その状態の「異常なし」は何も意味しない。**持てるが判定しないは正当な状態であり、それを明示することが自由の条件である。**

### 5.5 保証の範囲

**書かれたものがデータとして矛盾していないことだけを言う。建築として妥当かは言わない。**

**保証するもの** — パスと同一性の一意性、参照先の存在、レベルの定義、区画の重なり、合成の解決が定まること、形を作るのに必要な情報の充足。これらは判定ではなく読解の一部であり、壊れた JSON を JSON パーサが弾くのと同じ層にある。

**保証しないもの** — 採光、面積率、高さの整合、外皮の連続、扉の設置可能性、避難、その他あらゆる建築的な妥当性。運搬層の属性の意味。

**したがって「検査が通った」の意味は、次のとおりに定義される。**

> 構造層と解釈層について、宣言された不変量が成り立つ。運搬層については何も言わない。建築としての妥当性については何も言わない。

### 5.6 導出の契約

形を作らないことと、形を作れないことは違う。**この記述からは、一意な形が作れなければならない。**

**担保は、第一に構造による。**与件が座標を与え、関係が共有面という座を与え、実体はその座に乗る。**実体は座を持って生まれる。**

構造に加えて、三つを定める。

1. **導出の規則は仕様が持つ。**実装ではない。規則が消費者ごとに違えば、同じ原本から違う建物が出る。それは原本ではない
2. **充足性を検査する。**形を作るのに必要な情報が揃っているかは、構造の整合の一部である。妥当性の判定ではなく、完全性の検査である
3. **参照実装を持ち、検査で回す。**すべての例が形になることを継続的に確かめる。参照実装は見た目を持たない

**機械形式は合成の結果を持ち、導出の結果は持たない。**規則が仕様にあり、参照実装が API として提供される以上、消費者が意味を再実装する必要はない。

### 5.7 問い

集計とグラフの問いは core が持つ。**ただし合否を言わない。**開口面積と床面積を返す。経路と扉を返す。面積を返す。合否は検証の領域が言う。

## 6. 検証 — 汚くてよい。増やす

建築的な判定。採光、面積率、高さの整合、外皮の連続、扉の設置可能性、避難、到達可能性、そしてまだ思いついていないすべて。**MCP の面として、koyu の内に置く。**

**独立した部品にはしない。**部品の境界は、版が別々に動く必要が出た瞬間に切るのが正しく、その必要はまだ無い。そして判定は何が正しいかがまだ定まっていない領域であり、定まらないうちに境界を与えれば誤った境界のまま固まる。切り出す条件は「二つ目の管轄が要る」「判定だけを使う利用者が現れる」「判定の版が独立に動く必要が出る」のいずれか。

**汚くてよい。**規則が粗くても、管轄が一つしかなくても、精度が足りなくても、増やしてよい。試して捨ててよい。**凍らないから安い。**

**汚くてよい条件は一つ。判定の結果が、原本の保証と混同されないこと。**判定の出力は、それが判定であって core の保証ではないことが常に読み取れる形で返る。診断の体系を core と分ける。

**すべての判定は MCP から呼べなければならない。**呼べない判定は、機械にとって存在しないに等しい。

## 7. ugatsu — 汚くてよい。精度を上げる

形の生成と、描画と、人のための面。座標・高さ・開口位置・勾配の生成、2Dと3D、図面としての体裁、診断の提示、判定の提示、オーサリング支援。

> **koyu は座標を作らない。ugatsu は意味を作らない。**

**汚くてよい。**寸法線も、通り芯記号、建具の作図表現、縮尺、勾配屋根、複雑な納まり——精度は少しずつ上げればよい。**凍らないから安い。**

**汚くてよい条件は一つ。描けないことが、書けないことと混同されないこと。**何を描き、何を描かないかを列挙して持つ。これが無ければ、描画側の限界が記述側の限界として原本に持ち込まれ、**原本が表現に引きずられる。**

**人のための面はここが引き受ける。**エディタ支援、オーサリング、編集。**人のためだけの層を core に厚く積まない。**

## 8. 依存と成長の向き

```
        ┌─────────────┐
        │  koyu core  │  小さい・きれい・凍る
        └──────┬──────┘
               │ 一方向
        ┌──────┴──────┐
        │             │
   ┌────▼────┐   ┌────▼────┐
   │  検証   │   │ ugatsu  │  大きくなる・汚くてよい・凍らない
   │ (MCP)   │   │         │
   └─────────┘   └─────────┘
```

> **言語は増やさない。検証と表現は増やす。**

言語に足すことは高い。解析・合成・機械形式・仕様・文書の五箇所を同時に触り、凍結後は破壊的変更になりうる。検証と表現に足すことは安い。面を一つ増やすだけで、言語の版は動かない。**新しい判定も、外部データとの突き合わせも、新しい問いも、図面の質も、行き先はここである。**

# 第三部 — 1.0.0

## 9. 1.0.0 とは何か

**1.0.0 は機能の完成ではない。壊さないと約束する面の確定である。**

判断は三問で足りる。

1. **その面は、この先変わらないと言えるか。** 言えないなら 1.0 に入れない
2. **その面が壊れたとき、誰の何が壊れるか。** 誰も壊れないなら、そもそも面である必要がない
3. **その面が正しいと言える根拠があるか。** 根拠のない面を凍結することは、誤りを凍結することである

三番目が最も重い。**面を凍結するとは、その面の意味を凍結することである。**意味が曖昧なまま凍結された面は、以後どの利用者にとっても信頼できない。

**したがって 1.0.0 は core だけを対象とする。**検証も表現も、成長を約束する領域であって、凍結を約束する領域ではない。

## 10. koyu 1.0.0 が凍結する面

| 面 | 約束の内容 |
|---|---|
| **muro 1.0 の文法と意味論** | この版で読めたものは、以後も同じ意味で読める |
| **合成の規則** | §5.2 の六つ。同じ入力からは常に同じ結果が出る |
| **同一性** | §5.3 の規則。uid が同じなら同じものである |
| **属性の三層と名前空間** | 運搬層は見ない、という約束を含む |
| **機械形式** | 版フィールドを持つ。同じ入力からは同じバイト列が出る。合成の結果を持ち、形を持たない |
| **導出規則** | 仕様として明文であり、参照実装が API として提供される |
| **構造整合の診断** | コードと重さ。緑の意味が §5.5 の定義と一致する |
| **公開 API と CLI** | 解析、合成、正準化、問い、導出。コマンド、引数、終了コード |

**MCP のツール群は、この八つとは別の面である。**追加的に増える面として扱い、凍結の対象としない。建築的な判定はここに属す。

**約束しないもの** — 形の生成と描画、建築的な判定、外部形式との往復と取り込み、人のための面、運搬層の属性の意味。**存在してよいが、凍結対象でないことが明示されている必要がある。**

## 11. 1.0 に到達する作業

1. **判定を core から分離する。**構造整合だけが core の診断に残り、判定は MCP の面へ移る。**捨てるのではなく、置き場所を変える**
2. **属性の三層と名前空間を宣言する。**運搬層を見ないことを、仕様に書く
3. **合成の規則を定義する。**層の強度、単一値の解決、集合の編集、定義と上書きの区別、決定性、出所。**暗黙の解決を残さない**
4. **同一性を第一級にする。**粒度、生成規則、不変性の保証範囲
5. **緑の意味を実装と一致させる。**書いたものが黙って消える経路、宣言していない側が黙って落ちる経路、種別の綴り違いが黙って通る経路——**この種の経路が残っている限り、1.0 は切れない**
6. **機械形式に版を与える。**合成の結果を持ち、形を持たないよう整理する
7. **導出規則を明文化し、参照実装と充足性の検査を持つ**
8. **公開面を整える。**動作環境の宣言、公開経路、同梱物。仕様を同梱する。使われていない面・意味の定まっていない面を残さない

## 12. 完成の判定

次がすべて言えるとき、koyu 1.0.0 である。

- **緑の意味の定義が、実装の挙動と一致している**
- 同じ入力から同じ結果が出る。合成の解決に暗黙の順序が無い
- すべての例が、参照実装で形になる
- MCP がどのような入力でも停止せず、契約どおりに応答する
- 公開されている面に、使われていないもの・意味が定まっていないものが無い
- **検証と表現が core の外にあり、core がそれらに依存していない**

## 13. ugatsu 1.0.0

**役割** — 形を作り、見せ、人が触れるようにする。意味は作らない。

**凍結する面**は四つだけである。

| 面 | 約束の内容 |
|---|---|
| **入力** | muro 1.0 と機械形式 1.0 を読む |
| **導出の一致** | 参照実装と同じ形を作る。見た目の質はここに足すが、形は変えない |
| **配布の形** | 単一の HTML であり、それがそのまま公開されるものである |
| **範囲の明示** | 何を描き、何を描かないかが文書にある |

**図面の精度は凍結の対象ではない。**寸法線も作図表現も縮尺も、1.0 の後にいくらでも上げてよい。1.0 が要求するのは、**上げていける形になっていること**だけである。

# 第四部 — その後

## 14. 版の数え方

版は二本である。

- **muro の版** — 言語と意味論と合成の規則。機械形式は同じ意味論の別の綴りなので、この版を共有する
- **koyu の版** — 実装。どの muro を実装するかを宣言する

ugatsu は独立に版を持ち、従う muro の版を宣言する。検証の面は版を持たず、追加的に増える。

**二本は別の約束なので、同時に到達する必要はない** ([ADR-0042](decisions/0042-two-version-lines.md))。muro の版は「このように書かれたファイルは、この意味であり続ける」を約束し、koyu の版は「この実装の面を壊さない」を約束する。現に muro は 1.0 に到達し、koyu は 0.x のまま — **言語は確定し、実装はまだ何も凍結を約束していない。**

## 15. 投資の順序

**core を固めることが先である。**言語、合成の規則、同一性、機械形式、導出の契約、構造整合。ここが定まらないうちに判定や外部連携を積めば、土台が動くたびに積んだものが崩れる。

**1.0 の後は、検証と表現を伸ばす。**そこは汚くてよく、速くてよく、捨ててよい領域である。core はもう動かない。

## 16. 範囲

### 16.1 持たないもの

- **原本における幾何**
- **配置の仕組み**（内包は座を与えない）
- **建築的な判定を原本の契約に含めること**
- **実務解像度の追求。**カバー率は価値ではない。足せば機械の視野から外れ、目的が壊れる

### 16.2 水準を定めるもの

**相互運用 — 出口は作る。往復は作らない。**

- 作る：安定した機械形式（版つき）、外部参照の鍵としての同一性、グラフの出力、読み取り専用の射影
- 作らない：往復互換、外部形式の完全な取り込み、カバレッジの主張、他形式との大きさの比較。**必要なのは「一棟が入る」という絶対値であって、比較ではない**
- 外に置く：既存資産からの取り込みは、一方向の変換としてコアの外に置く

**人のための面 — ugatsu が持つ。**

## 17. 変更の規律

新しい語・機能の採否は、次の五問だけで決める。

1. **それは実体を持つか。** 持つなら関係か与件に座を持つ。空間には置かない
2. **それは与件か。** 与件でない座標は書かない
3. **同じ場所に複数の意見がありうるか。** あるなら合成の集合編集（§5.2-3）に載せる。専用構文を作らない
4. **それは判定か。** 判定なら検証の面であって、muro ではない
5. **それは形か。** 形なら ugatsu であって、muro ではない

**「実在の建築が書けるようになるか」は判定に使わない。**「実例が要求したら採否を決める」という留保つきの決定を書かない。留保は、そのまま拡張の入口になる。

## 18. 既存の形式との関係

空間をノード、境界を関係とするモデルは新しくない。W3C BOT の `bot:Space` と `bot:Interface`、IndoorGML のセル空間と双対グラフ、IFC の `IfcSpace` と `IfcRelSpaceBoundary` は、どれも近い形をしている。合成の仕組みは USD が持つ。**近さは隠すべき弱点ではなく、設計上の狙いである。**近い形をしているからこそ、それらへの射影が自明になる。

新規性は個々の要素にではなく、**それらを同時に備えていること**にある。

| | 既存 | この記述 |
|---|---|---|
| **立ち位置** | 部材モデルや CAD から派生する射影・交換形式 | **人と機械が直接書く原本。**派生元を持たない |
| **大きさ** | 一棟が機械の視野に入らない | **一棟が丸ごと入る** |
| **合成** | 建築の意味論を持つ形式は合成を持たず、合成を持つ形式は建築の意味論を持たない | **両方を持つ** |
| **同一性** | ファイル内の識別子。時点をまたぐ保証は形式の外 | **不変の同一性が第一級** |

## 19. まだ定めていないこと

1. **層の強度をどう宣言するか。**入れ子の層、参照された層の扱いを含む
2. **集合として扱う値の一覧。**どの種類の値が §5.2-3 の編集対象かを、閉じた一覧として定める
3. **運搬層の名前空間の綴り**
4. **検証の診断体系を core とどう分けるか。**判定の出力が core の保証と読まれないための、具体的な形
