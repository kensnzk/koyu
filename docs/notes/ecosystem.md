# エコシステムの地図 — koyu から外へ出る道

日付: 2026-08-04 / 状態: ブレスト (未決定。ADR は一本も書かれていない)

[horizon.md](../horizon.md) は三軸 (LLM・オントロジー・デジタルツイン) を**構想**として書いた。この文書はその先で、**「koyu の外側に何を作るか」を実装可能な単位に割る**ための地図である。対象は koyu のプロダクトの中ではない — **出す・繋ぐ・入れる・問う**の四方向で、koyu が世界のどこに刺さるかを列挙し、使える OSS を並べ、デモの形にする。

原則は horizon.md と同じ一つだけ。**koyu は小さいままでいる。** 接続は koyu に機能を足すことではなく、koyu が既に持っているものを外の世界の結節点にすることである。

---

## 0. 前提 — 接ぎ手は五つしかない

外と繋がるとき、koyu が差し出せるものは五つに限られる。**エコシステムの設計とは、この五つのどれをどこに刺すかを決めることに尽きる。**

| 接ぎ手 | 実体 | 性質 | 外の世界での役回り |
|---|---|---|---|
| **正準JSON** | `koyu-canonical/1.2` — バイト同一・キーはコードポイント昇順・NFC | 凍る。すべての射影の起点 | あらゆる変換の**入力**。ここから先は誰が書いても同じ結果になる |
| **パス** | `/L5/A/ldk` | 人間可読で、意味そのもの | **外部キー**。GUID 対応表が要らない |
| **uid** | 空間とゾーンにだけ付く任意の識別子 | rename を跨いで生き延びる | **長期のジョイン**。時系列蓄積の主キー |
| **空間グラフ** | 隣接・通行可能性・経路・境界セグメント (`graph`) | 導出。宣言されていない | **行動の地図**。ナビゲーション・避難・空間構文 |
| **Form** | 形の唯一の導出 (`form` / `poly.ts`) | 生成物。原本に無い | 幾何ネイティブな世界 (glTF/USD/CityJSON/IFC) への唯一の橋 |

補助的にもう一つ、**台帳** (`ATTR_LEDGER`) がある。これは接ぎ手ではなく**契約**で、外の辞書 (bSDD/Uniclass/Brick) と語彙を突き合わせるときの照合表になる。

### 動詞は四つ

接続を四つの動詞に割ると、リスクと置き場所が自動的に決まる。

| 動詞 | 何をするか | 一方向か | リスク | 置き場所 |
|---|---|---|---|---|
| **出す** (射影) | koyu → 外の形式。RDF・IFC・CityJSON・glTF・HBJSON | 一方向。生成物 | **低**。壊れても原本は無傷 | 橋のリポジトリ。core には置かない |
| **繋ぐ** (接合) | パス/uid を外部キーにして、外のデータを koyu の**上に**重ねる | 双方向だが、データは持たない | **低**。koyu は何も抱えない | デモ側 / 外のプラットフォーム |
| **入れる** (受入) | 外 → `.muro`。IFC・点群・GIS の敷地 | 一方向。だが**人が読む文字**を吐く | **高**。生成された muro が読めなければ主題が崩れる | 橋のリポジトリ。人のレビューを前提に |
| **問う** (応答) | MCP/API で外のエージェントに答える | 読み取り + `write_layer` | **中**。実装済み。次は合奏 | `src/mcp.ts` (実装済み) |

**「出す」と「繋ぐ」はほぼ無料で、「入れる」だけが難しい。** そして最も説得力があるのも「入れる」である。この非対称が、この後の優先順位のすべてを決める。

### 置き場所の規律 — なぜ core に足さないか

- **依存ゼロは絶対** (法8)。Turtle・GeoJSON・OBJ・PGM は**文字列を組み立てるだけ**なので依存ゼロで書けるが、IFC・glTF・CityGML は書けない。この線引きをまたぐ実装を core に入れると、いつか誰かが `npm i` を足す。
- **凍る面を増やさない** (法6・[stability.md](../reference/stability.md))。射影の綴りは変わる。BOT は v0.3.2 の Public Draft で、IFC5 は alpha である。**まだ動いている標準への射影を凍らせてはいけない。**
- したがって橋は `skills/` と同じ扱い — **リポジトリにはあるが npm パッケージには入らない**、あるいは別リポジトリ (`koyu-bridges`)。

**唯一の例外が測地である** (軸3)。これだけは原本に書かれるべき所与であり、core に入る。

## 軸1 — オントロジー: 拡張ではなく整列

koyu のオントロジーへの答えは既に出ている ([ifc-coverage.md](../ifc-coverage.md) の「対応の思想」): 巨大なクラス階層ではなく、少数の解釈語+開かれた語彙+導出。だから接続は語彙を増やす方向ではなく、**外の語彙体系に自分を説明させる**方向になる。

### 射影先の地図

| 標準 | 何のための語彙 | koyu の何が対応するか | 距離 |
|---|---|---|---|
| **BOT** (W3C LBD, `https://w3id.org/bot#` v0.3.2) | 建物のトポロジー | `bot:Site/Building/Storey/Space` ← level とパス階層 / **`bot:Interface` ← boundary** / `bot:adjacentZone` ← 隣接 / `bot:containsZone` ← パス階層 | **極近**。boundary はほぼ `bot:Interface` の authorable な表面記法である |
| **OMG + FOG** (幾何の管理・ファイル形式) | 「意味」と「形」を分離して繋ぐ | **`omg:hasGeometry` の先に Form の生成物を置く**。原本に形が無いという方針と、この二つの語彙は同じ思想 | **極近**。koyu の主張がそのまま既存語彙で言える |
| **OPM** (Ontology for Property Management) | 属性の版と出所 | **レイヤー合成の出所** (`koyu layers --attrs`) | **近**。属性が「どのレイヤーから来たか」を持つ点が構造的に一致 |
| **BEO / PRODUCT / PROPS** (IFC 由来の要素・属性) | 建築要素の分類 | spec 語彙の値の受け皿 | 中。koyu は物を一次要素にしないので、射影は薄くてよい |
| **FSO** (Flow Systems) | 設備の流れ | 対象外 (PS/機械室は空間として書けるだけ) | 遠 |
| **SAREF / SAREF4BLDG** (ETSI) | デバイス・センサ | 軸2の受け皿。koyu 側は空間だけ提供 | 中 (軸2で使う) |
| **Brick Schema** (1.4〜) | BMS のポイントと機器 | `brick:Room/Floor` ← 空間・level。`brick:hasPart` ← パス階層 | 中。**ASHRAE 223P との接続機構が 1.4 で入った** |
| **ASHRAE 223P** | 設備トポロジー (標準化進行中) | 対象外。Brick 経由で触れる | 遠 |
| **RealEstateCore / DTDL** | 不動産のデジタルツイン | 軸2。DTDL は JSON-LD なので正準JSON からの射影が素直 | 中 (軸2で使う) |
| **bSDD** (buildingSMART Data Dictionary) | 分類辞書 (IFC/Uniclass/各国コード) | **台帳の外側**。`bsdd.` 名前空間属性で参照する | 近。REST API があるので照合は機械化できる |
| **IndoorGML 2.0** (OGC 正式標準) | 屋内空間の**セルと双対グラフ** | **空間 = セル、空間グラフ = 双対グラフ**。2.0 は概念モデルと符号化を分離し JSON 符号化を許した | **極近**。軸3に置くが、思想はここ |

### 決定的な観察が三つある

1. **`bot:Interface` は koyu の boundary そのものである。** IFC では `IfcRelSpaceBoundary` が付随的な関係で、書き出しから真っ先に落ちる。BOT では界面が一級の概念で、koyu では一級の**辺**である。**koyu は BOT の authorable な表面記法だと言い切れる。** これは論文でのオントロジー上の位置づけそのものになる。

2. **OMG/FOG は「形は生成物」を既存語彙で言い直す道具である。** `omg:hasGeometry` の先に `fog:asGltf` / `fog:asObj` を置けば、「意味のグラフは軽く、形は外部リソース」という構造が W3C の語彙で表現される。**koyu が特殊なのではなく、koyu はこの分離を原本の段階でやっているだけだ**、と言える。

3. **OPM とレイヤー出所の一致は偶然ではない。** どちらも「属性は値ではなく、値と出所の対」という同じ発見をしている。`koyu layers --attrs` の出力が、そのまま OPM のグラフになる。

### デモ

**D1 — 問いの一致 (question parity).** 最も安価で最も厳密なデモ。

```text
koyu doors examples/tower/main.muro /L5/A/ldk /out   →  2
SPARQL over tower.ttl (BOT+koyu射影)                  →  2
```

同じ問いを二つの言語で聞き、答えが一致することを**試験にする**。`conformance/` と同じ作法で、「射影が忠実である」を機械が握れる形にする。隣接・経路・面積・階層の四つで十分。**これができれば「オントロジーに対応した」は主張ではなく事実になる。**

**D2 — 台帳から SHACL を生成する.** `ATTR_LEDGER` (解釈語・型・値域) から SHACL shapes を吐き、生成した Turtle を pySHACL で検証する。台帳が人間の契約であると同時に機械の契約になる。horizon.md の「台帳の機械可読化」の具体形。

**D3 — bSDD 照合.** 台帳の spec/type 語彙を bSDD の API に問い合わせ、「この語は Uniclass/IFC のどれに当たるか」の対応表を `vocabulary-map.muro` として生成する。**コアの語彙は一語も増えない** — 名前空間属性 (`bsdd.class:...`) で運ぶ (法7)。

### OSS

| 名前 | 言語 / ライセンス | 役回り | koyu が依存できるか |
|---|---|---|---|
| **N3.js** | JS / MIT | RDF/JS 準拠のパーサ・シリアライザ。Turtle/TriG/N-Quads | 橋なら可。core は不可 |
| **Oxigraph** (js) | Rust→wasm / Apache-2.0 | **ブラウザで動く SPARQL 1.1**。デモの心臓 | 橋・デモのみ |
| **Comunica** | JS / MIT | メタクエリエンジン。複数ソースへの SPARQL | デモのみ |
| **quadstore** | TS / MIT | LevelDB 裏の RDF ストア | デモのみ |
| **rdflib** / **pySHACL** / **owlready2** | Python / BSD等 | 検証・推論。D2 の実装 | 橋のみ |
| **brickschema** (py) | Python / BSD | Brick モデルの生成・推論 | 橋のみ |
| **bSDD API** | REST/GraphQL | 分類辞書の照合 | デモのみ (ネットワーク) |

**書き出しだけなら依存はゼロでよい。** N-Triples と Turtle は文字列連結で書ける。SPARQL を回すのはデモ側の仕事である。この線を守れば `koyu rdf` を CLI に足すことすら可能だが、**BOT が Public Draft である間は凍らせない。**

### 分水嶺

**D1 の四つの問いが SPARQL で同じ答えを出すか。** 出れば「BOT への射影は忠実」が試験になる。出なければ、koyu の boundary か BOT の Interface のどちらかを誤解している。

## 軸2 — デジタルツイン / ツイングラフ: パスがジョインキー

horizon.md の三分割 (静的な実測 / 動的な状態 / 行動の地図) を、実装単位に割る。**重要な更新: 上書き合成 (レイヤー強度) は実装済みである** — horizon.md 執筆時点では ADR-0010 の保留だったが、六つの合成規則が揃い `over`/`drop` が landing した。**as-built レイヤーは今日書ける。**

### 三層に割る

| 層 | 何を持つか | 原本に入るか | 機構 |
|---|---|---|---|
| **as-built (静的な実測)** | 竣工実測寸法・確定仕様 | **入る** | `import ./as-built.muro` を最後に置く (後のレイヤーが強い)。**今日できる** |
| **state (動的な状態)** | 温度・人感・電力・予約 | **入らない** | パス/uid が外部キー。データは外のプラットフォームに残る |
| **behaviour (行動の地図)** | 経路・避難・ロボット | **導出** | 空間グラフ + 扉位置 |

### ツイン・マニフェスト — 一つのペイロード、多くの受け皿

外のツイン基盤はどれも「空間の一覧を登録しろ」と言う。**受け皿ごとに変換を書くのではなく、中間の一枚を定義する。**

```jsonc
// koyu twin examples/tower/main.muro  (仮)
{ "path": "/L5/A/ldk", "uid": "...", "level": "L5", "type": "room",
  "area_m2": 24.3, "centroid": [x, y, z], "polygon": [...],
  "attrs": { "name": "LDK", "daylight": 1 },
  "adjacent": ["/L5/A/bed1", "/L5/corridor"], "doors": 2 }
```

これ一枚から機械的に落ちる先:

| 受け皿 | 変換 | 難度 |
|---|---|---|
| **Brick / RDF** | `brick:Room` + `brick:hasPart` | 低 (軸1と共有) |
| **DTDL / Azure Digital Twins** | RealEstateCore の `Room`/`Level` インスタンス。DTDL は JSON-LD | 低 |
| **FIWARE / NGSI-LD** | Smart Data Models の `Building`/`BuildingSpace` エンティティ | 低 |
| **Eclipse Ditto** | Thing の階層 | 低 |
| **Home Assistant** | **areas / floors**。`.storage` か API で流し込む | 低。**デモとして最も安い** |
| **W3C WoT Thing Description** | 空間を Thing の親に | 中 |

**Home Assistant は過小評価されたデモ標的である。** OSS で、誰でも 10 分で立ち、フロアと部屋の概念を持ち、時系列とダッシュボードが付いてくる。「koyu の 22 行から、部屋が並んだスマートホームができる」は動画一本で終わる。

### デモ

**D4 — パス = 外部キーの一枚もの.** `koyu plan` の SVG に、`path,timestamp,value` の CSV を重ねて室を着色する自己完結 HTML 一枚。GUID 対応表が一行も無いことが画面で分かる。**依存ゼロ・ビルド不要・共有可能。** 最も安く「ツイン」が言える。

**D5 — 設計と実測の差分.** `koyu diff design.muro as-built.muro` が「/L5/B が北に 600 広がった。専有面積は +3.2㎡」と出す。**品質記録が構成の言葉で出る。** 合成が実装済みなので、これは新機構ゼロで書ける。

**D6 — ロボットが歩く.** 空間グラフと扉位置から、
- **占有格子** (`.pgm` + `.yaml`) → ROS 2 Nav2 の `map_server` がそのまま食う。**PGM は文字列とバイト列を書くだけで、依存ゼロで生成できる。**
- **ナビグラフ** (ノード=空間、辺=通行可能な境界、重み=距離) → JSON/GeoJSON
- **3D シーン** (Form → glTF → USD) → Isaac Sim / Gazebo

「**22 行のテキストから、ロボットが歩くフロアが立ち上がる**」。メッシュから歩行グラフを復元するのが業界の逆問題で、**koyu は原本が最初からグラフである**という主張の、最も分かりやすい実演になる。フィジカル AI の訓練環境は「建物が企画とルールの分布として存在する」B 方向 (horizon.md) の完全体でもあり、二つの軸がここで合流する。

### OSS

| 名前 | 言語 / ライセンス | 役回り |
|---|---|---|
| **Home Assistant** | Python / Apache-2.0 | 最短のツイン受け皿。areas/floors/履歴/ダッシュボード |
| **Eclipse Ditto** | Java / EPL | Thing 管理のツイン基盤 |
| **FIWARE Orion-LD + Smart Data Models** | C++/JSON-LD / AGPL・Apache | NGSI-LD のツイングラフ。EU 系スマートシティの本命 |
| **RealEstateCore / opendigitaltwins-building** | DTDL(JSON-LD) / MIT | 不動産ツインの事実上の標準語彙 |
| **InfluxDB / TimescaleDB / Grafana** | 各種 | 時系列と可視化 |
| **MQTT (Mosquitto) / Sparkplug B** | C / EPL | 現場のデータ配管 |
| **ROS 2 (Jazzy/Kilted) + Nav2** | C++/Python / Apache-2.0 | 占有格子とナビゲーション |
| **NVIDIA Isaac Sim** | Python/USD / オープンソース化済 | フィジカル AI の訓練環境。OpenUSD がシーン層 |
| **Gazebo / MuJoCo / Genesis** | 各種 / Apache-2.0 等 | 物理シミュレーション |
| **OpenUSD (usd-core) / tinyusdz** | C++/Python / Apache-2.0 | USD 書き出し。Isaac/Omniverse への入口 |

### 分水嶺

**D4 で、対応表を一行も書かずに外のデータが室に着くか。** 着けば「パスがアドレス空間である」は実証済みになる。着かなければ、パスの安定性 (rename) の問題が露呈しているので uid の運用規則を先に固める。

## 軸3 — GIS・都市: ここだけコアが要る

**軸3のすべてが一つの欠落で止まっている — 測地座標と真北 (ifc-coverage.md の F、MUN-159)。**

### コアに入る唯一のもの

必要なのは基準点一つと回転角一つだけである。

```muro-part
# 案 (未決定)
origin  jgd2024/IX  x:-8000.0 y:-34000.0   # 平面直角座標系の系番号と座標
north   -12.5                               # 真北からの回転角 (度)
```

これが入った瞬間に、以下が**全部**繋がる。

- 建物全体が JGD2011/JGD2024 平面直角座標系に載る → WGS84 に載る → 地図に載る
- 日影・斜線・延焼ラインの実計算が可能になる (方位が定まる)
- PLATEAU / CityGML の座標系に乗る
- zone が不動産 ID に対応づく

**注意: 測地系が動いた。** 2024 年に「測地成果 2024」が公表され、名称は JGD2011 から **JGD2024** に変わった。EPSG は JGD2011 で緯度経度 6668、平面直角座標系 6669–6687。**属性の綴りは版を持たせるべきで、系番号だけを書いて測地系を暗黙にしてはいけない。**

なお座標変換そのものは依存ゼロで書ける (平面直角座標系のガウス・クリューゲル逆算は 50 行程度)。**だがそれを core に入れる必要はない** — core は基準点を**持つ**だけでよく、投影は橋の仕事である。

### 射影の梯子

| 出口 | 何を出すか | 難度 | 依存 |
|---|---|---|---|
| **GeoJSON** | 敷地ポリゴン + 建築面積の輪郭 + 各室のフットプリント | 極低 | ゼロ (文字列) |
| **CityJSON** | LOD1 (箱) / LOD2 (屋根が入れば) / **LOD3-4 相当 (室内!)** | 中 | ゼロ〜低 (JSON) |
| **CityGML 3.0** | 同上の XML 版 | 中 | citygml4j 等 |
| **glTF → 3D Tiles** | Cesium / deck.gl に載る | 中 | py3dtiles 等 |
| **IndoorGML 2.0** | セル空間 + **双対グラフ** | 低 | ゼロ (2.0 は JSON 符号化可) |

### IndoorGML との一致は偶然ではない

OGC IndoorGML 2.0 は「**物ではなく、活動が起きる空 (empty space) に注目する**」と言い、3D セルを双対変換してノードにする。**これは koyu の空間と空間グラフの、一字一句の言い換えである。** 2.0 で概念モデルと符号化が分離されたので、koyu の正準JSON は IndoorGML 2.0 の一符号化として提示できる余地がある。

**そして koyu は CityGML の世界で異様に強い。** 都市モデルは LOD1/LOD2 (外形) までしか無いのが普通で、LOD4 (室内) はほぼ存在しない。koyu は**室しか持っていない**。「PLATEAU の街に、内部を持つ唯一の建物を置く」は、koyu の非対称性がそのまま絵になる。

### 日本の所与

| 出所 | 何が取れるか | koyu の何に効くか |
|---|---|---|
| **PLATEAU** (国交省) | CityGML の 3D 都市モデル。全国。属性 (用途・構造・建築年) 付き | 周辺の建物・地形。デモの背景そのもの |
| **国土数値情報** | **用途地域・建蔽率・容積率**・防火地域のポリゴン | **`site` の入力**。緯度経度から自動で制約が引ける |

## 軸4 — 既存BIM: 二方向は対称ではない

### 出す — 素直だが、価値は限定的

| 出口 | 何が出せるか | 何が出せないか |
|---|---|---|
| **IFC4 (SPF)** | 空間構造 (Project/Site/Building/Storey/Space)、**IfcRelSpaceBoundary**、境界から押し出した壁、開口と建具 | 材料層構成・構造・設備・納まり。**実施の情報は原本に無い** |
| **IFC5 (ifcx)** | 同上の JSON 版 | 同上 |

出す価値は「業界のパイプラインに渡せる」だが、**渡した先で koyu の主張は失われる** (向こうは物の言語なので)。だから優先度は高くない。

**ただし IFC5 には構造的に重要な符合がある。** IFC5 は ECS + JSON + **レイヤー合成**で、hello-wall では 631 バイトの差分レイヤーで耐火性能を足せる ([comparison/README](../../examples/comparison/README.md))。**これは koyu の import 合成と同じ機構である。** つまり:

> **koyu は IFC5 のレイヤーの authoring front-end になれる。**

IFC5 が alpha である今、この位置取りを主張するのは早すぎもせず遅すぎもしない。**ただし alpha に追随する実装を凍らせてはいけない。**

### 入れる — 難しく、そして最も説得力がある

**これが「逆問題」である。** 実務の IFC には `IfcSpace` が無いことが珍しくない。二経路ある。

| 経路 | 条件 | 手順 | 難度 |
|---|---|---|---|
| **A: 空間がある** | `IfcSpace` + `IfcRelSpaceBoundary` が書き出されている | 空間を取り、境界を辺にし、**矩形グリッドにスナップする** | 中。非矩形室が壁 |
| **B: 空間が無い** | 壁だけがある | 壁の芯線から平面を分割し、閉領域を室として検出する | 高。だが古典的な問題で解法はある |

**受入は「正しい方向に劣化する」。** 幾何を捨て、構成を残す。40MB を 200 行にする。この非対称こそが主題である。

そして**判定は既にできる**。`examples/comparison/` が使った物差しをそのまま当てればよい — 面積・隣接・扉の数が、元の IFC と生成された muro で一致するか。

### デモ

**D9 — 40MB を 200 行に.** 実務規模の Revit 書き出しを食わせ、**人が読める `.muro`** を吐く。左右に並べた画面で、行数・トークン数・そして「読めるかどうか」を見せる。**素材はこのリポジトリには無い** — `examples/comparison/` にあるのは手書きの `two-rooms.ifc` (7.3 KB) と `.ifcx` (20 KB) だけで、実務規模の IFC は調達からになる。

**D10 — 同じ問いに同じ答え.** 生成した muro と元の IFC が、面積・隣接・扉数で一致することを試験にする。D1 (SPARQL の問いの一致) と同じ作法。**「変換した」ではなく「意味を保った」が言える。**

**D11 — BCF で返す.** `validate` の Finding を **BCF** (BIM Collaboration Format — zip + XML) で書き出し、業界の指摘管理に流す。BCF は仕様が小さく、IfcOpenShell に実装がある。**小さいのに、業界の作法に乗ったという事実が大きい。**

### Speckle に乗る — コネクタを自分で書かない

> **この節は [speckle.md](speckle.md) が引き取った。** 調べ直した結果、置き場所 (軸4 の一節) も優先度 (7) も間違っており、下の記述には誤りが三つある — Automate は **OSS でも自ホストでもない**、ライセンスは Apache-2.0 **だが例外が二つある**、そして **`IFC_samples/` はこのリポジトリに無い**。判断は [speckle.md](speckle.md) を読むこと。

Revit/Rhino/Grasshopper/ArchiCAD/Blender/QGIS のコネクタを自前で書くのは無理である。**Speckle が既に全部持っている。** GraphQL API と Python SDK があり、Automate (関数を差分に対して自動実行する仕組み) がある。

- `koyu → Speckle`: 生成した Form を Speckle にプッシュ → Rhino/Revit で開ける
- `Speckle → koyu`: Grasshopper で描いた敷地・ボリュームを取り込む
- Speckle の **IFC 取り込み** (IfcOpenShell、IfcSpace を 3D 幾何つきで取り出す) を挟むと、**下の「入れる」が STEP を一行も読まずに書ける** — この非対称の反転が、Speckle を前に出す最大の理由である ([speckle.md](speckle.md) §5)。

| 名前 | 言語 / ライセンス | 役回り |
|---|---|---|
| **IfcOpenShell** (+ ifcopenshell-python) | C++/Python / LGPL | IFC の読み書きと幾何。**受入の本命** |
| **IfcTester** | Python / LGPL | **IDS** による IFC の要件検証 |
| **web-ifc** (ThatOpen) | C++→wasm/JS / MPL-2.0 | ブラウザで IFC を読み書き。**既に comparison で使用済み** |
| **ThatOpen Components** | TS / MIT | Three.js + web-ifc のビューア基盤。デモの見た目 |
| **Bonsai (旧 BlenderBIM)** | Python / GPL | Blender 上の IFC オーサリング。**空間検出の実装がある** |

### 分水嶺

**D9 で出た `.muro` を、人が「これは読める」と言うか。** 言えば主題が実証される。言わなければ、受入のスナップ規則か、そもそも解像度の選び方 (どこまでを一室とするか) を設計し直す。

## 軸5 — シミュレーション: 性能を外注する

koyu は性能計算をしない (法2・`validate` は建築的判断であって熱計算ではない)。**だから外に出す。** そして koyu の空間は、性能ツールが要求する形にほぼそのまま落ちる。

| 出口 | 形式 | koyu の何が対応するか | 距離 |
|---|---|---|---|
| **Honeybee / EnergyPlus** | **HBJSON** | `Room` = 閉じた立体 (Face の集合)、`Aperture` = 開口。**Form がそのまま Room になる** | **極近** |
| **Radiance** (採光) | Honeybee 経由 | 開口と方位。`light` の実計算版 | 近 |
| **JuPedSim / Vadere** (避難) | ジオメトリ + 出口 | **空間グラフと扉がそのまま入力**。`runs` が既に二方向避難を見ている | **極近** |
| **FDS** (火災) | 直方体グリッド | 室と区画。koyu は矩形なので相性がよい | 近 |
| **OpenFOAM** (CFD) | メッシュ | Form → STL | 中 |
| **depthmapX** (空間構文) | 平面ポリゴン | 可視グラフ・isovist。**空間グラフの視覚版** | 中 |

**D12 — 22 行から避難シミュレーション.** `examples/complex/` (延床 31,606㎡) を JuPedSim に流し、避難時間を出す。`validate` の二方向避難ルールが「規則として通る」と言い、シミュレーションが「実際に何秒かかる」と言う。**規則と現象の二層が、同じ原本から出る。**

**D13 — HBJSON 一発.** Form → HBJSON → EnergyPlus。「テキスト 400 行から年間エネルギー消費量」。距離が近いので実装が安い。

## 軸6 — エージェント基盤: MCP の先

MCP サーバーは実装済み (12 ツール)。**次は「一つのサーバー」から「合奏」へ。**

### 2026 の MCP の変化が三つ効く

- **ステートレスな HTTP コア** (2026-07-28 RC) — `koyu-mcp` は最初からステートレス (毎回ファイルから合成する) なので、**設計がそのまま新仕様に合う**。stdio から HTTP に出すのが素直になる。
- **MCP Apps (サーバー側 UI)** — `plan_svg` が「SVG ファイルを返す」から「**会話の中で平面図が出て、室をクリックできる**」に変わる。デモの見栄えが一段変わる。
- **Tasks 拡張 (長時間処理)** — シミュレーションや大規模な受入を非同期で回せる。

### D14 — 四つのサーバーで一つの企画

エージェントに MCP を四本繋ぐ: **koyu** (設計と検査) / **GIS** (PLATEAU・用途地域) / **IFC** (既存棟の読み取り) / **twin** (稼働実績)。

> 「この敷地に事務所ビルを企画して、容積率と日影を確認して、隣の既存棟の形は IFC から取れ」

**これがエコシステムのデモそのものである。** koyu は四本のうちの一本にすぎず、**しかし唯一「書ける」一本**である — 他は読むだけ。この非対称が koyu の位置を説明する。

### D15 — Speckle Automate / GitHub Actions の CI

PR に `.muro` の変更が来たら `check` `validate` `diff` が走り、平面図の差分が PR にコメントされる。**建物のコードレビュー。** 実装は小さく、絵は強い。

## 軸7 — ポートフォリオ: 正準JSON がそのままデータになる

見落とされがちだが、**正準JSON は列指向データベースにそのまま入る**。1000 棟を一つのテーブルにすれば、施設管理の規模の問いが SQL 一本になる。

**D16 — 1000 棟を一クエリ.** DuckDB に正準JSON を読み込み、「全ポートフォリオで二方向避難を満たさない室」「用途別の面積効率の分布」を一行で問う。**koyu の一棟あたりが小さいことが、ここで規模の武器に変わる。** OSS: DuckDB (MIT)、Parquet、Apache Arrow。

## 規律 — これを破ると主題が壊れる

1. **依存ゼロを破らない** (法8)。橋は npm パッケージの外に置く。`skills/` と同じ扱い。
2. **凍る面を増やさない** (法6)。BOT は v0.3.2 の Public Draft、IFC5 は alpha、ASHRAE 223P は策定中。**動いている標準への射影を stability.md に載せない。**
3. **射影は一方向である。** 生成物を原本に戻さない。唯一の例外が受入 (軸4) で、それは**人が読んでレビューする文字**を吐くから許される。
4. **外の語彙はコアに入らない** (法7)。bSDD も Brick も PLATEAU も、名前空間属性 (`bsdd.` `brick.` `plateau.`) で運ぶ。**台帳の語は一語も増やさない。**
5. **生成物をコミットしない。** Turtle も glTF も CityJSON も、`out/` に出して捨てる。原本は `.muro` だけである。
6. **「繋がった」と「働く」を混同しない** (法2 の系)。射影が出ることと、向こうの世界で意味を保っていることは別である。**だから D1 と D10 の「問いの一致」が要る** — 変換が出力を持つことではなく、意味を保つことを試験にする。
7. **貼る出力は実際に走らせたものだけ** (法10)。この文書の表の空欄は、埋めるときに実測する。
