# 2026-07-25 — 外部レビューと意味の保証 (ADR-0013, v0.9)

## 追記 — 境界の既定・同一性・診断契約・言語版・semantic diff (ADR-0014〜0018, v0.10)

レビューの残り提案から、koyuの核を強くするものだけを一気に着地。実装前に6レンズの敵対的設計レビューを回し、二つの思い込みが折れた: examplesに素のwall行は1本も無く「スリム化」は空集合 (価値は記述量でなく**意味の完全性** — 未宣言の接触は「未定義」ではなく「壁」)、そして0.1の無条件受理は「黙って意味を変え、警告も消す」最悪の組合せになるため**条件つき受理** (導出が起きる0.1はエラー) に。

- **ADR-0014 境界の既定**: 水平の「既定は壁」— 垂直の「既定は床」と対称に。宣言は例外と属性のため。examples全出力 (SVG26枚・doors・stats・light・site) のバイト一致で意味保存を実測
- **ADR-0015 uid**: パスはアドレス、uidは寿命の長い参照。数字形と空白は禁止、重複は所有者列挙の1エラー
- **ADR-0016 診断契約**: checkDiagnosticsが一次 (49コードの台帳、severity不変)。check --json / --strict。specの表と実装の一致はテストが守る
- **ADR-0017 言語版**: 三版分離。0.2へ。旧版は「意味保存の場合のみ」を機械化
- **ADR-0018 semantic diff**: `koyu diff` — 「基準階の床材1変更が8行」「uid改名は1行」。不変量: toCanonical同一⇒diff空

テスト114→161本。原稿の約束「差分は構成の言葉で読める」が動く形になった。

外部のDSL設計レビューを受領し、指摘11件 (D-001〜D-011) を全件、最小ケースで検証した — 原文と検証・方向性の計画は [docs/reviews/](../reviews/) に収めた。10件が事実、1件 (属性の後勝ち) は仕様化済み挙動への異議。重かったのは、正準JSONが境界の向きを捨てて「swingの違う二モデルがバイト同一」になること、wall/openの矛盾宣言がcheck緑で通ること、MCPのwrite_layerが書いてから検査するため壊れた原本が残ること。

回収はADR-0013として着地 (v0.9): 正準JSONへ `a` キーを保存し宣言順に依らない正準順を定義、境界の同一性 (対+edge) の重複をエラー化、凹敷地の包含と敷地形状の妥当性検査、宣言面積の照合をcheckへ、同一行の属性重複と未対応版をエラー化、write_layerを検査先行+atomic+実体パス検査に、`model.layers` で合成の参加記録を完全に。specを現在形へ書き直し (void上側の非voidは実装どおり警告へ訂正)、リリース情報 (lockfile・CITATION・README数値) を同期してテストで守る。テスト99→114本。

レビューの残りの提案 — 診断契約、境界の既定 (接する空間の自動wall)、同一性 (任意uid)、言語版ポリシー — は次のADRの問いとして計画に積んである。

## 追記2 — 根底の再検討と生成の方向 (方針)

レビュー対応が着地した時点で、muroとkoyuのあり方そのものを問い直した。原文は [docs/reviews/2026-07-25-foundation-rethink.md](../reviews/2026-07-25-foundation-rethink.md)。

**刷新は前提工事だった。** v0.9/v0.10で揃ったもの — 言語版の分離 (ADR-0017)・正準性のproperty test・semantic diff (ADR-0018)・severity固定の診断コード (ADR-0016) — は、いずれも根底を動かす変更を安全に行うための装備である。刷新の最大の価値は機能ではなく、**動かす前に安全網が揃ったこと**にある。

**方向は「実体を主張へ近づける」。** レビュー§3.2 (「形は生成物」と言いながら空間の矩形領域は原本に直書きされている) への応答は二つあり、リポジトリはP0-12で(a)文言の校正を選んだ。これは現在形の正確な記述であって終着ではない — 固定化すれば中心主張の静かな放棄になる。採るのは(b)実体化、すなわち**位置を名前と導出へ移すこと**である。

**位置の原理。** 批判の正体は「位置か寸法か」だった。`X2+1600` は原点からの距離であって設計者が決めた寸法ではない。決めているのは「水回り1600・廊下1800・残りがLDK」であり、位置はその帰結である。**BIMは寸法を入力させ座標を保存する。koyuは寸法を保存し座標を生成する。** 垂直方向は既にそうなっており (`level L1 0 h:3600 slab:600` の積み上げが矩計を出す)、**水平だけが座標系のまま取り残されていた** — ADR-0014が直した非対称と同型のものが、もう一つあった。原理は一文になる: 垂直の矩計を水平へ拡張する。

**線の三出自。** 位置を定めるものを線として見ると出自は三種ある — **共有線** (通り芯・副芯。宣言一回・参照N回)、**所与線** (敷地polygonの辺)、**描画線** (設計の行為そのもの)。ここで**グリッドは記法の土台から共有線という特殊例に降格する**。「設計者は通り芯から考えない」という違和感の正体は、特殊例を土台と偽っていたことにあった。境界は位置を持たない関係の層のままで、線はその実現である。

**斜めは契機であって本体ではない。** 計画中のコーパス (basement/mixed/megablock) を見ると、設計された斜めを実際に要求する実例は一つも無い (敷地・斜路は所与/垂直の話)。よって判断はADR-0019に今書き、**実装は直交にも効く部分に限る** — 主役は帯と寸法による導出 (`chain`)、副芯の命名は副産物、描画線 (矩形区間代数→arrangementの全面書換え) は証拠待ちである。

**生成の方向 (方向B) とルール。** 「敷地と企画だけを書き、muroはLLMが生成する」方向は、詳細度を上げる方向Aと真逆に見えて同じ軸の両極である (どちらも書くものを減らし導出を増やす)。muroに入るルールは**決定的な展開に限る** — 選択はエージェントの仕事で、選択の結果がmuroに書かれる。整理は [docs/horizon.md](../horizon.md) の「軸1の先 — 生成」に恒久化した。

**工程を一つ正す。** 最大の未回収は編集evalであり、v0.9/v0.10の全てはその計測装置の整備だった (diff=採点、診断コード=失敗分類、uid=改名課題、MCPの門番=transaction)。**baseline evalは30,000㎡を待たず tower で先に走らせる** — baselineが無ければ記法変更 (0.3) の効果は永遠に測れない。
