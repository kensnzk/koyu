# 2026-08-03 — koyu core 0.18.0 API 改修

## 目的

koyu core 1.0.0 で守れる API 境界を作る。まず 0.18.0 として全変更を完成させ、全表面の実証後に 1.0.0 へ昇格する。

作業ブランチ: `codex/api-architecture-overhaul`

## 確定した決定

- muro の版、koyu core の版、canonical JSON の版は独立して数える
- 現在の API 改修は koyu core 0.18.0 を対象とする
- 0.18.0 で必要な実装修正、repository consumer の移行、不要 API の削除まで完遂する
- 1.0.0 は公開した 0.18.0 の全表面を実証した後にだけ昇格する
- 意思決定は ADR、実行事実は本ログ、現在の契約は published documentation、保証は test に置く

根拠と昇格条件は `docs/decisions/0052-release-0-18-before-1-0.md` に記録した。

## 実装前に確認した判断

2026-08-03 に次を確認し、実装に着手した。

- JavaScript/TypeScript の公開入口は root、`/model`、`/diagnostics`、`/graph`、`/form`、`/analysis`、`/diff`、`/vocabulary`、`/validate`、`/validate/builtin`、`/draw`、`/node` の 12 入口とする
- root には composition、structural diagnostics、canonicalisation、Form derivation とその最小型だけを残す
- analysis は明示的な context/profile から判定の無い事実を作る
- validation は明示的な RuleSet/Profile と analysis artifact を使い、完全な AssessmentReport を返す
- プロセス全体の mutable global registry は置かず、呼び出し側が local immutable registry を渡す
- 法規に依存する CLI/MCP の判定は profile を必須とし、jurisdiction は推定しない。CLI では profile 欠落を usage error (`exit 2`) とする
- 旧 `validate(model)`、旧 rule ID、不要 export、compatibility wrapper は 0.18.0 内で利用者を移行して削除し、後続版に延期しない

公開境界の理由は `docs/decisions/0053-public-surface-cutover.md`、analysis/assessment の詳細契約は `docs/decisions/0054-assessment-protocol.md` に記録した。

続いて built-in migration の三点を確認した。

- 旧判定は法令 namespace へ昇格させず、`koyu.schematic.*` の design-lint rule とする
- access の type/use による現行推論を `koyu.analysis.access@1` で保存し、parity migration に新しい外部 route context を混ぜない
- 旧 `run.slope` は ramp の declared-slope rule と escalator の usual-slope rule に分割する

この結果、六つの neutral analysis、十六の built-in rule、`koyu.ruleset.schematic-screen@1`、`koyu.profile.schematic-screen@1` を実装対象とする。判断と受入条件は `docs/decisions/0055-builtin-schematic-assessment.md` に記録した。

### Phase 2: explicit analysis and assessment protocol

Phase 2 commit: `70b5c66` (`feat: add explicit assessment protocol`)

次の generic protocol を追加した。legacy `validate(model)` と package export map は、この段階ではまだ切り替えていない。

- `src/analysis/json.ts`: JSON-only boundary、deterministic clone、Unicode scalar-value comparator
- `src/analysis/contracts.ts`: context、analysis artifact、evidence、analysis report の型
- `src/validate/contracts.ts`: Rule、RuleSet、Profile、registry、AssessmentReport の型
- `src/validate/assessment.ts`: local immutable registry、preflight、per-call analysis session、`runAnalysis`、`assess`
- `test/assessment-contract.test.ts`: protocol の機能・敵対入力契約
- `test/assessment-acceptance.test.ts`: ADR 受入条件から独立に作った acceptance matrix

実装レビューでは、通常入力だけでなく次の境界不良を実際の failing fixture で発見してから修正した。

- 対象 analysis の解決が core diagnostics より後だったため、構成エラーでも model を走査し得た
- context entry、artifact/evaluation union、evidence/source/missing identity の余分な field が一部で捨てられていた
- JSON clone の `__proto__` key、`-0`、Unicode surrogate-pair ordering
- caller-owned array method、constructor 経由、symbol brand による registry preflight bypass
- optional effective/jurisdiction の `null` と余分な field、実在しない calendar date
- symbol、non-enumerable field、accessor を effective/jurisdiction または registry/component identity に埋める bypass
- context decoder result に symbol/function または hidden accessor を埋める extension boundary bypass
- hostile Error proxy と非 Error throw から arbitrary object/stack が漏れる経路

registry、component、reference、context と decoder result は、宣言した enumerable data property だけを受理する。`run`、`decode`、`evaluate` 以外の getter を構成値として実行しないことを zero-read fixture で固定した。

| 検証 | 実測結果 |
|---|---|
| `node --import tsx --test test/assessment-contract.test.ts test/assessment-acceptance.test.ts` | 32 tests、32 pass、0 fail |
| 上記2 suite + `test/domains.test.ts` | 39 tests、39 pass、0 fail |
| `npm run typecheck` | success |
| `npm test` | 630 tests、630 pass、0 fail |

acceptance matrix は required/optional context、provider/rule/model precondition、独立 rule の継続、AnalysisReport の JSON round-trip、二 registry/profile の逆順・再入実行、per-call cache、effective/jurisdiction の work-before-fail、dependency post-order、rule-set/rule/finding/diagnostic order、暗黙の `asOf` 補完禁止を含む。
