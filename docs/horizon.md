# 地平の設計 — デジタルツイン・オントロジー・LLM接続

日付: 2026-07-23 (2026-07-25 生成の節を追加) / 状態: 構想 (ADR-0012がLLM接続の第一手を採用)

原稿「建築を書く」の「地平」の節を、v0.7の実装 (合成・出所・正準JSON・敷地形状・ショーケース) の上に具体化する。三軸に共通する原則を先に言う: **koyuは小さいままでいる。** 接続はkoyuの中に機能を増やすことではなく、koyuが既に持つもの — 人間可読パス・空間グラフ・正準JSON・checkの門番 — を外の世界の結節点にすることで実現する。

## 軸1: LLM接続 — 建物をエージェントの作業対象にする

設計基準「LLMが一つのコンテキストで読み切り、正しく部分編集できるか」は数字で答えが出た (examples/comparison/README.md): 延床4,786㎡の一棟が原本8,099トークン、同じ場面でIFC4は14倍・IFCXは25倍、実務のIFC出力はコンテキストに載らない。ここから先は「読める」を「働ける」にする段である。

**第一手: MCPサーバー (ADR-0012 — 実装済み)。** `koyu-mcp` がstdioでモデルを公開する。ツールは要約 (`model_summary`)・検査 (`check`)・レイヤーの読み書き (`layers` / `write_layer`)・グラフの問い (`doors` / `stats` / `light` / `site` / `levels`)・平面生成 (`plan_svg`)。エージェントの作業ループはgitのそれと同型になる: **読む → レイヤーを書き換える → checkが門番として通す/弾く → 問いで帰結を確かめる。** 書き込みは.muroに限定し、履歴はgitが持つ (OwnerHistoryを持たない方針の帰結がここで効く)。依存ゼロの方針を守るため、MCPはSDKなしの手書きJSON-RPC 2.0で実装した — パーサを自作した時と同じ賭けである。

**第二手: エージェント評価 (eval)。** 「Bタイプを2住戸に割れ。採光と避難を保て」という課題を与え、check/light/doorsをオラクルに合否を測る。記法の設計 (一行一文・出所つきエラー・宣言と検査) がエージェントの成功率にどう効くかを測定できる形にする — 論文の実験の柱。towerがベンチマーク盤面になる。

**第三手: 差分の言葉 (M4と合流 — 済、ADR-0018)。** `koyu diff` が「/L5/B が北に600広がり、Cが縮んだ。専有面積は±0」を出せば、エージェントの自己検証とPRレビューが同じ言葉を使える。正準JSONの安定性 (バイト同一) が土台。v0.10で着地: 改名はuidで検出、素wall宣言と省略 (既定壁) は差分にしない。

## 軸1の先 — 生成: 企画から構成へ (方向B)

軸1は「エージェントが既にある建物を編集できるか」を問う。その先に、書かれるものをさらに減らす方向がある — **何も書かない。あるのは敷地とコンセプト (企画) と方向性だけで、muro は LLM がルールベースで生成し、結果がジオメトリとしてビルドされる。** これを方向Bと呼ぶ。位置の導出化 (ADR-0019) を方向Aとすると、両者は真逆に見えて同じ軸の両極である。

**二段のビルド。** ビルドは **企画 → 構成 (LLM が生成) → 形 (koyu が導出)** の二段になる。原稿が言う「原稿の非一意性」(同じ構成から複数の形が出る) が一段上がり、**同じ企画から複数の構成**が出る、になる。形の非一意性が欠陥でなかったのと同じ理由で、構成の非一意性も欠陥ではない — それが案である。

**A と B は同軸の両極である。** どちらも「書かれるものを減らし、導出を増やす」。違いは**どこでピン留めを止めるか**だけで、A は設計者が全てをピン留めしピンの語彙 (線の規定方法) を細かくする方向、B はピンが敷地と企画しかない方向である。**同じ muro の上に両極が載る — 言語は分岐しない。** 一言でいえば、A は muro をより良い**決定の記法**にし、B は muro をより良い**生成の標的**にする。両方が要求する性質 (可読性・決定的ビルド・オラクル・小さいコンテキスト) は同一である。

**三つの役割。** 生成の世界に現れるものを三つに分ける — **要件** (企画の検証可能な部分) は**制約する**のでオラクル側に置く / **ルール** (決定的な展開) は muro に書かれる / **選択** (探索) はエージェントの仕事で、選択の結果が muro に書かれる。この三分がこの節の骨格である。

**ルールの入場基準 — muro に入るのは決定的な展開だけ。** 選択も条件分岐も含まないものだけが muro に入る。「廊下は1.8m、残りを住戸で等分」は決定的なので入る。「住戸をなるべく南に」は最適化なので入らない (LLM が解き、解を muro に固定する)。**数式は入るがマクロは入らない。** 選択までを文法に取り込んで結果より読めなくなった shape grammar (Stiny 以降、CGA/CityEngine) の轍を踏まない — **選択をエージェントに出す**のが LLM 時代の差分である。萌芽は最初からある: `level L4..L10 pitch:3000` (等差)、スパン展開 `/L2..L9/A`、`stack`、ADR-0014 の既定境界 — みなルールである。基準階機構が抵抗なく受け入れられたのは、「2〜9階は同一」という**決定そのものがルールの形をしていた**からで、問いは「ルールを書くか」ではなく「**ルールの語彙をどこまで登るか**」である。

**確率は write の前にある。** 確率的なのは LLM の選択であり、それは書き込みの前に起きる。**書かれた muro は決定的な不動点**で、ビルドは何度でも同じ建物を出す。同じ企画からの複数案は複数の muro であり、それは **git のブランチ**である — 原稿の「設計案の比較はブランチの比較になる」が、B で文字どおりになる。

**Lean 対応。** 企画 = 定理、muro = 証明 (witness)、check/light/site/doors = カーネル、LLM = 証明探索。この対応はソルバー拒否 (ADR-0019 決定2) と整合する — **解く (創造的・確率的) のはエージェント、確かめる (決定的・安価) のは koyu** である。koyu が小さいままでいられるのは、賢さを全部エージェント側に置けるからだ、と言い直せる。

**要件は muro の外に置く。** 足りないのは要件ファイル一つである — 企画の検証可能な部分 (「1ユニット約○○㎡」「全戸採光」「二方向避難」) の機械可読形。これは muro の中ではなく**上**に置く。muro の原本は解決済みのレイアウトであるという定義 (レビューの Program 層への回答) を破らないためで、教義は「文章的な方向性 → プロンプト、検証可能な要件 → 要件ファイル」である。**形式は未定とし、今は決めない** — eval の生成課題 (T06 とその拡張) が要件をアドホックに書く経験から決めるべきで、先に決めれば使われない層になる (レビュー Program 層と同じ轍)。参考にする外部標準は buildingSMART IDS。

**「常に生成される」の射程。** 探索フェーズでは文字どおり真である (案をサンプルし、比較し、選ぶ)。しかし実建築ではどこかで**選択 = コミット**が起き、選ばれた muro が固定されて以後は A の世界 (人が線を足し詳細度を上げる) へ収束する — **B は A の上流フェーズである。** 一方、**仮想世界・シミュレーション・フィジカル AI の訓練環境では永遠に B のままでいられる** — 建物が「企画とルールの分布」として存在し、必要な時に整合した個体が生成される。これが B の完全体で、実建築とは別の出口である。

**本命はおそらく中間 — 固定点+生成。** 設計者が parti だけ書き (数本の線・主要ゾーニング・コアの位置)、残りを LLM が充填し、check が守る。人が線を一本引き直したら、その線を不可侵として周りを再生成する — **エスキスの機械化**である。**器は既にある**: import 合成 (ADR-0010) で `human.muro` (人の決定・不可侵) と `generated.muro` (生成層・再生成可) を合成すればよい。新機構を待たず、今日から実験できる。

**梯子。** 登り方には順序がある — **位置の導出 (幅/比/残り) → 反復・充填の導出 (repeat/fill) → 型 (unit type = ルール束)**。二段目の最初の需要は megablock (43戸) が出す見込みで、三段目はレビューが保留した template/instance (P1-17) の**真の正当化**になる — 基準階の便利機能としてではなく、ルールの単位として要る。先例がある: **木割書 (『匠明』1608〜)** は堂塔を図ではなく比例規則として記述し、柱間を与えれば全部材の寸法が導出される。muro のルール層はその現代形である。器は `types.muro` (住戸型 = ルール束) を import で複数プロジェクトが共有する形 — **型の共有**で、ADR-0010 がそのまま器になる。

**未知を正直に置く。** どこまで登ると muro が読めなくなるかは分からない。分かるのは eval の前後比較だけである。頂上 (敷地+企画+ルールだけ) に届くかも未知で、届かなくてもよい。**終着像はおそらく muro = 所与 + 少数の決定 (parti) + 多数のルール** — それは依然として muro である。A も B も、現在の muro (解決済みの構成) を中点として、規定の語彙を細部側と企画側へ伸ばす同じ運動である。

## 軸2: オントロジー — 拡張ではなく整列

koyuのオントロジーへの答えは既に出ている: 巨大なクラス階層ではなく、少数の解釈語+開かれた語彙+導出 (ifc-coverage.mdの「対応の思想」)。だから接続は語彙を増やす方向ではなく、**外の語彙体系への整列**として設計する。

**BOT (W3C Linked Building Data の Building Topology Ontology) への射影。** BOTはkoyuと同じ形をしている — bot:Space、bot:adjacentZone、bot:Interface (二つのZoneの界面!)。koyuのboundaryはbot:Interfaceの、authorable な表面記法だと言える。`koyu rdf` で正準JSONからTurtleを生成する (一方向・生成物): 空間=bot:Space、垂直=bot:Storey階層、境界=bot:Interface、隣接=bot:adjacentZone。SPARQLで問える形になり、リンクトデータ (PLATEAU・不動産ID) と同じ土俵に載る。W3C系の既存語彙に自分を説明させることは、論文でのオントロジー上の位置づけそのものになる。

**外部辞書への参照は属性のレイヤー。** 室用途コード (日本の建築基準法系・BOMA・Uniclass・bSDD) への対応は `dict:` 系属性または対応表ファイル (vocabulary-map.muro的なレイヤー) で持ち、コアの語彙は増やさない。「同じ意味に別の語を使わない」台帳の規則を、外の辞書との間でも守る。

**台帳の機械可読化。** spec/vocabulary.md (人間の契約) から vocabulary.json (機械の契約) を生成し、MCPの `model_summary` やエージェントのプロンプトに同梱する。エージェントが語彙の解釈可否を確かめてから書けるようになる。

## 軸3: デジタルツイン — パスがジョインキーになる

原稿の言葉は「実測を設計の上に重ねる一枚のレイヤー」。合成 (ADR-0010) が実装された今、これは文字通りレイヤーの話になる。ただし二種類を区別する:

**静的な実測 (as-built) は上書きレイヤー。** 竣工時の実測寸法・確定仕様は `as-built.muro` として合成する — これはADR-0010で見送った「上書き合成 (レイヤー強度)」を最初に要求するユースケースになる。設計値と実測値の差分そのものが品質記録である。

**動的な状態 (センサー・稼働) は原本に入れない。** 温度・人感・予約・電力は時系列であり、git-textの原本に書くものではない。koyuの貢献は**アドレス空間**である: `/L5/A/ldk` という人間可読パスが、IoTプラットフォーム・BEMS・予約システムの外部キーになる。GUIDの対応表が要らない — パスがそのまま意味である。ただし**寿命がパスより長いjoin (renameを跨ぐ蓄積) は任意の `uid:` を使う** (ADR-0015 — パスはアドレスと集計、uidは長期の同一性)。実証は小さくできる: 室ごとの計測値CSV (path,timestamp,value) をugatsuの平面にオーバーレイする一枚。

**グラフは行動の地図。** passable() の空間グラフ+扉の位置は、そのままロボット・避難シミュレーション・フィジカルAIのナビゲーションの骨格である (原稿の予告)。メッシュから歩行グラフを復元する業界の逆問題を、koyuは原本が既に持っている。

**都市への接続は測地から。** polygon (ADR-0011) で敷地の形は入った。残るのは測地座標と真北 (MUN-159) — 一点の基準座標+回転角があれば、建物全体がPLATEAU/CityGMLの座標系に載り、zoneが不動産IDに対応づく。日影・斜線・延焼ラインの実計算もこの一歩の先にある。

## 順序と分水嶺

0. **baseline eval (先行)** — tower・言語0.2 で現行記法の成功率を数字にする。分水嶺: 0.3 との比較で記法の設計が成功率に効くと言えるか。
1. **MCP (済)** — エージェントが働ける。分水嶺: エージェントは設計変更をcheck緑のまま完遂できるか (eval)。
2. **rdf/BOT出力** — 小さい (正準JSONの射影)。分水嶺: SPARQLでdoorsと同じ問いに答えられるか。
3. **上書き合成 (as-builtレイヤー)** — ADR-0010の保留の回収。分水嶺: 設計/実測の差分が構成の言葉で出るか。
4. **測地 (MUN-159)** — 都市接続の鍵。分水嶺: PLATEAUの上にtowerが正しく置けるか。
5. **ツインデモ** — パス=ジョインキーの可視化。ugatsuに受け皿。

軸をまたぐ含意: MCPのツール群はそのままオントロジーの「解釈の実装」であり (doorsが答えられることがboundaryの意味論)、ツインの問い (「いまLDKに誰かいるか」) はグラフの問いに時制が付いただけである。三軸は別々の機能ではなく、同じ原本の三つの読み方である — 面積・避難・区画が同じ記述の異なる読み方であるのと同じように。
