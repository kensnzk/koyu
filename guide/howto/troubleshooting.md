# よくある詰まり

出たメッセージから原因と直し方を引く。

エラー文言は完全一致で検索できる。人向けの出力は `ファイル:行目: 本文` の形で出るので、以下の表は本文だけを載せている。診断コード (BND04 など) を出したいときは `koyu check <file> --json` を使う — 人向けの出力にコードは出ない。

以下の出力例のファイルパスは、実際には絶対パスで出る。読みやすさのためファイル名だけに縮めてある。

## 前提

- `npx tsx src/cli.ts check <file.muro>` が走ること。
- 終了コードは、エラーがあれば1、緑なら0。警告だけなら0 (`--strict` を付けると1)。

## 症状の索引

### check がエラーで止まる

| 症状 (本文) | 原因 | 直し方 | さらに詳しく |
|---|---|---|---|
| `未定義の通り名です: X1` | `grid` が無い、または通り参照を使う行より後にある | `grid X` と `grid Y` を、それを使う最初の行より前に書く | [1](#1-未定義の通り名です) |
| `空間が接していないため境界を導けません: /L1/a \| /L1/b` | 角だけで触れている。接触には長さのある共有辺が要る | 矩形を重ねて辺を共有させるか、その `boundary` 行を消す | [2](#2-空間が接していないため境界を導けません) |
| `境界線分が複数あります。edge:N/E/S/W で辺を指定してください (/L1/living \| /out)` | 外部との境界は室の外周の複数の辺に割れる | 開口に `edge:` で辺を選ぶ。`N`=+Y・`S`=−Y・`E`=+X・`W`=−X | [3](#3-境界線分が複数あります) |
| `領域は X?..X? と Y?..Y? の2つで指定します` | ほとんどの場合、型 (第2位置引数) の書き忘れ。領域の1つ目が型として読まれている | `space <パス> <型> X?..X? Y?..Y?` の順に書く | [4](#4-領域は-xx-と-yy-の2つで指定します) |
| `空間の領域が重なっています: /L1/home と /L1/home/ldk` | 領域を持つ空間の下に、領域を持つ子空間を置いている | 親を `zone` にする。`zone` は幾何を持たない | [5](#5-空間の領域が重なっています) |
| `未定義の空間を参照しています: /L1/bath` | パスの綴り違い、またはその空間を宣言したレイヤーを `import` していない | パスを直すか `import` を足す | [6](#6-未定義の空間を参照しています) |
| `door には幅 w:(mm) が要ります (アセット側でも可)` | 開口に幅が無い | `door w:800` と書くか、幅を持つ `asset` を参照する | [spec/language.md §4](../../spec/language.md) |

### check は緑なのに正しくない

| 症状 | 原因 | 直し方 | さらに詳しく |
|---|---|---|---|
| `⚠ /L1/a は領域を持ちますが、レベルが特定できません` | `level` が宣言されていない。**パスに `/L1/` と書いてもレベルの宣言にはならない** | `level L1 0` を書く | [7](#7-レベルが特定できません) |
| `plan` が生の Node スタックトレースを吐く (`Error: レベルが定義されていません`) | 同上 — `level` が一つも無い | `level L1 0` を書く | [8](#8-plan-が生のスタックトレースを吐く) |
| `Error: レベル L2 に領域を持つ空間がありません` | `plan -l` のレベル名違い。レベル名は大文字小文字を区別する | `koyu levels <file>` で名前を確かめる | [8](#8-plan-が生のスタックトレースを吐く) |
| `check` は緑だが `doors` が「到達できません」を返す | 接する空間には扉のない既定の壁が導かれる。扉は自動では付かない | 通したい組に `boundary` を書き、字下げで `door` を置く | [9](#9-check-緑なのに到達できません) |
| `check` は緑だが外皮が一枚も無い | 外部 (領域を持たない空間) との接触には既定が導出されない | `/out` への境界を1本ずつ書く | [10](#10-check-緑なのに外皮が無い) |
| 型を変えたのに採光の判定が変わる/変わらない | 型は開かれた語彙で、綴り違いは黙って通る | ツールが構造として読む型を確かめる | [11](#11-型と属性キーの綴り違いは黙って通る) |
| 属性が効かない (`nmae:` など) | 属性キーの綴り違いも黙って運ばれる | 台帳 ([spec/vocabulary.md](../../spec/vocabulary.md)) と照合する | [11](#11-型と属性キーの綴り違いは黙って通る) |
| 空のファイルが `✔ 整合 — 空間 0 / 境界 0` を返す | 何も書かれていない構成は成立している | 緑を「書けている」証拠にしない。`stats` か `graph` で中身を見る | [12](#12-空のファイルも緑になる) |
| `敷地面積の宣言と導出が食い違います` (SIT05) | `zone` の `area:` (測量値) と `polygon` の面積が ±0.05㎡ 超ずれている | どちらかを直す。測量値が正なら頂点を直す | [敷地を書いて建蔽率・容積率を出す](site-and-far.md) |
| `check` の境界数と正準 JSON の `boundaries` が合わない | `check` は導出後の本数、正準 JSON は書かれた構成のみ | 食い違いではない。導出後を見たいときは `graph` | [13](#13-check-の境界数と正準-json-が合わない) |

## 直し方

### 1. 未定義の通り名です

`grid` は宣言の順序が効く数少ない行である。`boundary` は空間を前方参照できるが、`grid` と `level` は使う行より前になければならない。

```muro-bad
level L1 0
space /L1/a room X1..X2 Y1..Y2
```

```text
✖ nogrid.muro:2行目: 未定義の通り名です: X1
```

`grid X` も `grid Y` も無い。順序だけの誤りでも同じ文言になる。

```muro-bad
space /L1/a room X1..X2 Y1..Y2
grid X 0 3600
grid Y 0 4000
level L1 0
```

```text
✖ order.muro:1行目: 未定義の通り名です: X1
```

**直し方。** ファイルの先頭に基盤の宣言をまとめる。合成しているときは base 層 (entry) に置く。

```muro-part
grid X 0 3600
grid Y 0 4000
level L1 0
```

`X5` のように存在しない通り名を書いたときも同じ文言が出る。`grid X 0 3600 7200` は `X1` `X2` `X3` の3本しか作らない。

### 2. 空間が接していないため境界を導けません

角で触れているだけの二室は接していない。境界の壁芯線分は矩形の共有辺として導かれるので、**長さのある辺を共有していなければ線分が導けない**。

```muro-bad
grid X 0 3600 7200
grid Y 0 4000 8000
level L1 0 h:2400 slab:150
space /L1/a room X1..X2 Y1..Y2
space /L1/b room X2..X3 Y2..Y3
boundary /L1/a /L1/b t:120
```

```text
✖ corner.muro:6行目: 空間が接していないため境界を導けません: /L1/a | /L1/b
```

二つの矩形はこうなっている。

```text
        X1        X2        X3
  Y3     +---------+---------+
         |         |   /L1/b |
  Y2     +---------●---------+
         | /L1/a   |
  Y1     +---------+
```

`●` が唯一の接点で、長さがゼロである。診断コードは BND04。

**直し方。** どちらかの矩形を伸ばして辺を共有させるか、その `boundary` 行を消す。

### 3. 境界線分が複数あります

室の外周のうち、他の空間と接していない残りが外部との境界になる。角の室なら南と西のように複数の辺に割れるため、開口をどこに置くか決まらない。

```muro-bad
grid X 0 3600
grid Y 0 4000
level L1 0 h:2400 slab:150
space /L1/living living X1..X2 Y1..Y2 name:居間
space /out exterior name:外部
boundary /L1/living /out t:150
  door w:900
```

```text
✖ edge.muro:7行目: 境界線分が複数あります。edge:N/E/S/W で辺を指定してください (/L1/living | /out)
```

**直し方。** 外壁に開口を置くときは `edge:` で辺を選ぶ。

```muro-part
boundary /L1/living /out t:150
  door w:900 edge:S
```

方角は最初に書いた空間の矩形から見る。`N`=+Y (北)・`S`=−Y (南)・`E`=+X (東)・`W`=−X (西)。X は東が正、Y は北が正である。境界行そのものを一つの辺に限定したいときは `boundary` 側に `edge:` を書く。

診断コードは開口が OPN05、`seg` が SEG05。線分が一本も無いときは OPN04 (`開口を置ける境界線分がありません`) になる。

### 4. 領域は X?..X? と Y?..Y? の2つで指定します

このメッセージは領域の書き方を指しているが、原因はたいてい型の書き忘れである。`space` の第2位置引数は型で、必須である。書き忘れると領域の1つ目 (`X1..X2`) が型として読まれ、残りが1つになる。

```muro-bad
grid X 0 3600
grid Y 0 4000
level L1 0
space /L1/a X1..X2 Y1..Y2
```

```text
✖ notype.muro:4行目: 領域は X?..X? と Y?..Y? の2つで指定します
```

**直し方。** パスと領域の間に型を書く。

```muro-part
space /L1/a room X1..X2 Y1..Y2
```

### 5. 空間の領域が重なっています

住戸を室に割るときの定番の詰まりである。`space` は領域を持つので、領域を持つ親の下に領域を持つ子を置くと必ず重なる。

```muro-bad
grid X 0 3600 7200
grid Y 0 4000
level L1 0 h:2400 slab:150
space /L1/home unit X1..X3 Y1..Y2 name:住戸
space /L1/home/ldk ldk X1..X2 Y1..Y2 name:LDK
space /L1/home/bed bedroom X2..X3 Y1..Y2 name:寝室
```

```text
✖ 空間の領域が重なっています: /L1/home と /L1/home/ldk
✖ 空間の領域が重なっています: /L1/home と /L1/home/bed
```

**直し方。** くくりは `zone` で書く。`zone` は幾何を持たず、パス接頭辞で配下を束ねるだけなので重ならない。面積はいままでどおり `/L1/home` で合計される。

```muro
grid X 0 3600 7200
grid Y 0 4000
level L1 0 h:2400 slab:150
zone /L1/home name:住戸
space /L1/home/ldk ldk X1..X2 Y1..Y2 name:LDK
space /L1/home/bed bedroom X2..X3 Y1..Y2 name:寝室
```

```text
✔ 整合 — 空間 2 / 境界 1
```

`examples/tower/` はこの形をとっている。診断コードは GEO01 / GEO02。

### 6. 未定義の空間を参照しています

```muro-bad
grid X 0 3600 7200
grid Y 0 4000
level L1 0 h:2400 slab:150
space /L1/a room X1..X2 Y1..Y2
space /L1/b room X2..X3 Y1..Y2
boundary /L1/a /L1/bath t:120
```

```text
✖ ref.muro:6行目: 未定義の空間を参照しています: /L1/bath
```

診断コードは REF01。合成しているときは、その空間を宣言したレイヤーが `import` されているかも確かめる。エラーは常に出所レイヤー名つきで返る。

### 7. レベルが特定できません

**パスの先頭に `/L1/` と書いても、レベルを宣言したことにはならない。** `level` 行が別に要る。

```muro-part
grid X 0 3600
grid Y 0 4000
space /L1/a room X1..X2 Y1..Y2
```

```text
⚠ nolevel.muro:3行目: /L1/a は領域を持ちますが、レベルが特定できません (パス先頭か level: で指定します)
✔ 整合 — 空間 1 / 境界 0 (警告 1)
```

警告文はパスの書き方を指しているが、直すのは足りない `level` 行である。診断コードは HGT05。終了コードは0なので、CI では `--strict` を付けないと素通りする。

**直し方。** `level` 行を足す。ただし**その `level` を使う `space` 行より前に置く**こと。後に置くと、同じ警告が出たまま素通りする。

```muro-part
grid X 0 3600
grid Y 0 4000
level L1 0
space /L1/a room X1..X2 Y1..Y2
```

パスの先頭でレベルを表さない書き方 (`/home/bed1` のように用途で束ねる) をするときは、空間側に `level:L1` を書く。`examples/house.muro` がこの形である。

### 8. plan が生のスタックトレースを吐く

`check` が緑でも `plan` は落ちることがある。描画は `check` の検査対象ではない。

```sh
npx tsx src/cli.ts plan nolevel.muro -o out.svg
```

```text
Error: レベルが定義されていません
    at svgPlan (src/plan.ts:29:21)
    at main (src/cli.ts:140:19)
```

(実際にはこの上に該当ソース行の引用が付き、下にも数行のフレームが続く。ここでは要点だけを抜粋している。)

原因は `level` 行が一つも無いこと。`level L1 0` を足す。`check` が緑でも `plan` が通るとは限らない — 描画まで確かめてから次に進む。

レベルはあるのに落ちるときは、`-l` に渡した名前を疑う。**レベル名は大文字小文字を区別する。**

```text
Error: レベル l1 に領域を持つ空間がありません
```

```text
Error: レベル L2 に領域を持つ空間がありません
```

前者は `L1` を `l1` と書いた場合、後者は存在しないレベルを指した場合。宣言されているレベル名は `koyu levels <file>` で確かめる。`-l` を省略すると最初のレベルが描かれる。

### 9. check 緑なのに到達できません

接する空間の間には、宣言が無ければ扉のない壁が導かれる ([ADR-0014](../../docs/decisions/0014-default-boundaries.md))。**扉は自動では付かない。** 二階建ての家を書いて、外皮と階段だけ宣言すると、`check` は緑のまま全室が密閉される。

```text
✔ 整合 — 空間 5 / 境界 7
```

```text
/L2/bed から /out へは到達できません
```

`graph` を見ると、書いていない壁が見える。

```text
/L2/bed (寝室)
  | 壁 → /out  (spec:EW)
  | 壁 → /L2/hall
```

`spec:` が付いていない `| 壁` の行が導出された既定の壁である。

**直し方。** 通したい組に `boundary` を書き、字下げで `door` を置く。宣言するとその組の既定の導出は止まる。

```muro-part
boundary /L2/bed /L2/hall t:120 spec:LGS
  door w:800
```

「到達できません」は、起点か終点のパスが存在しないときにも同じ文言で返る。まず `graph` でパスの綴りを確かめる。手順の全体は [動線と避難を問う](doors-and-escape.md)。

### 10. check 緑なのに外皮が無い

既定の壁が導かれるのは、**領域を持つ空間どうし**が接している組だけである。`/out` のような領域を持たない空間との組には導出されない — どの外部に面しているかは名指しが情報だからである。

```muro-part
grid X 0 3600 7200
grid Y 0 4000
level L1 0
space /L1/a room X1..X2 Y1..Y2 name:居室A
space /L1/b room X2..X3 Y1..Y2 name:居室B
```

```text
✔ 整合 — 空間 2 / 境界 1
```

境界1本は室の間の既定の壁で、外周には一枚も壁が無い。それでも緑になる。

**直し方。** 外部空間を宣言し、外周の室から1本ずつ境界を書く。外部は方角・性格ごとに割ると `edge:` の指定が楽になり、敷地の問いも立てられるようになる ([敷地を書いて建蔽率・容積率を出す](site-and-far.md))。

```muro-part
space /out exterior name:外部
boundary /L1/a /out t:150 spec:EW
boundary /L1/b /out t:150 spec:EW
```

内壁は自動、外壁は手書き — この非対称は意図されたものである。

### 11. 型と属性キーの綴り違いは黙って通る

型 (`space` の第2位置引数) は開かれた語彙である。ツールが構造として解釈するのは次だけで、それ以外は自由語として運ばれる。

| 型 | 解釈 |
|---|---|
| `exterior` | 外部。領域なし可。床面積に算入しない |
| `void` | 吹抜け。床面積に算入せず、通行もしない |

`hall` も `wet` も `room` も `ldk` も自由語で、検査も警告もされない。採光の対象になるかどうかも型では決まらない — `daylight:1` を書いた室だけが判定される。浴室に `daylight:1` を書けば、型が `wet` のままでも判定に入る。

```muro-part
space /L1/bath wet X1..X2 Y1..Y2 nmae:浴室 daylight:1
```

```text
✖ /L1/bath	bath	窓 0.00㎡ / 床 14.40㎡ = 窓なし (必要 1/7 ≈ 2.06㎡)
✖ 1室中 1室が不足しています
```

`daylight:1` を落とすと、型を一字も変えずに判定から外れる。

```text
採光の対象がありません (判定する室に daylight:1 を書きます)
```

属性キーの綴り違いも同じく黙って通る。上の例の `nmae:浴室` はエラーにならず、正準 JSON にそのまま乗る。表示名は付かず、パスの末尾 (`bath`) が使われている。

```text
      "attrs": {
        "nmae": "浴室"
      }
```

**直し方。** ツールが読む属性は [spec/vocabulary.md](../../spec/vocabulary.md) の台帳が契約である。効かない属性はまず台帳と照合する。判定を明示したいときは `daylight:1` / `daylight:0` で採光の対象を直接指定できる。

### 12. 空のファイルも緑になる

```text
✔ 整合 — 空間 0 / 境界 0
```

`check` は「書かれた構成が成立しているか」だけを見る。**緑は「書けている」ことの証拠ではない。** 中身を見るには `stats` (面積)・`graph` (隣接)・`doors` (動線)・`light` (採光)・`site` (敷地) を使う。

### 13. check の境界数と正準 JSON が合わない

```text
✔ 整合 — 空間 2 / 境界 1
```

```text
  "boundaries": []
```

同じファイルの結果である。`check` は導出後のモデルの本数を数え、正準 JSON は**書かれた構成だけ**を保存する。既定境界は正準 JSON に出ない ([spec/semantics.md §2](../../spec/semantics.md))。正準 JSON から意味を読む側は `deriveDefaultBoundaries` を適用してから読む ([spec/tools.md](../../spec/tools.md) 公開 API 節)。食い違いではなく、二つの層の役割の違いである。

## 診断コードを出す

人向けの出力に診断コードは出ない。コードで引きたいときは `--json` を使う。

```sh
npx tsx src/cli.ts check corner.muro --json
```

```text
[
 {
  "code": "BND04",
  "severity": "error",
  "message": "空間が接していないため境界を導けません: /L1/a | /L1/b",
  "line": 6,
  "file": "corner.muro",
  "path": [
   "/L1/a",
   "/L1/b"
  ]
 }
]
```

構文・合成エラーも `SYN01` の1件に写して有効な JSON で返るので、パイプラインが壊れない。コードごとの意味は [診断コード一覧](../diagnostics.md)、規範の台帳は [spec/semantics.md §5](../../spec/semantics.md)。
